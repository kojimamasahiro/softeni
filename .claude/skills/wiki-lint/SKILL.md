# wiki-lint（意味の点検）

設計は [ADR-024](../../../docs/adr/ADR-024-llm-wiki-operating-model.md)。検査は3段あり、この skill は**3段目（意味 lint）**。

| 段 | 性質 | 内容 |
|---|---|---|
| ゲート | CI で落とす。誤検知がほぼ無く、直し方が自明 | リンク切れ・SQL 台帳・frontmatter・`code:` の実在・`index.md` の鮮度・Compile Log の行き先 |
| 報告 | CI のサマリに出す。止めない | 文字数の予算・孤立ページ・ADR の Status 書式・Compile Log の欠落 |
| 意味 lint | **この skill**。判断が要る | 主張と実装の突き合わせ・所有者の重複・解けた問い・実施予定を過ぎた運用 |

## いつ使うか

- **大きめの実装のあと**（`AGENTS.md` の書き戻しの規則）。
- **月次**。過去の lint の間隔は3〜6週だった。

## 手順

### 0. 機械から先に回す

```
npm run check:wiki -- --strict   # ゲート。落ちたら先に直す
npm run check:wiki               # 報告（文字数・孤立・Compile Log の欠落など）
npm run wiki:index -- --check    # index.md が最新か
```

機械が見つけたものは、意味 lint の仕事ではない。直し方が自明なものはその場で直す。

### 1. 範囲を決める

直近の変更範囲か、全体か。変更範囲なら、触ったコードの所有ページを引く:
`git diff --name-only <基準>... | xargs npm run -s wiki:for --`

### 2. 主張を実装と突き合わせる

ページの主張を、実装で1つずつ確かめる。結果は **一致 / 矛盾 / 確認できない** の3つに分ける。

- 状態語（「未実装」「未公開」「実装済み」「Deprecated」）。
- パス・コマンド（`npm run <名前>` が `package.json` にあるか、本文のパスが実在するか。
  「削除済み」「まだ作らない」「〜ではなく」と断っている行は意図的な記述）。
- 数値（閾値・件数・字数）。測り方は下の「測定の落とし穴」。

### 3. 所有者を点検する

- `code:` の各項目が、そのページが**定義・決定している対象**か（言及だけ・対比で名前が出ただけのパスが入っていないか）。
- 同じ `code:` の項目を複数ページが持っていないか。持つなら、同じファイルの別側面を書いているときだけ正当。
- 同じ事実を2ページが書いていないか（事実の所有者は1つ）。

### 4. 滞留・古さを探す

- **解けているのに残っている Open Question**（`docs/wiki/open-questions.md`）。実装や別ページで決着していないか。
- Deprecated にすべき記述、日付だけが古い「現況」。
- 行き先の無い Compile Log、孤立しているページ、ADR の Status と実装のずれ。
- **実施予定を過ぎた運用**: ランブックの「いつやるか」に対して、`docs/raw` に実施記録（ファイル名の範囲でよい）があるか。
  無ければ「宿題」として報告する。本文のずれではなく運用の遅れ。

### 5. 直すものと聞くものを分ける

- 自明な機械的問題（旧パス、リンク、frontmatter、索引）は、その場で `wiki-compile` の手順で直す。
- 判断が要るもの（仕様の矛盾、どちらを正とするか、運用の優先度）は直さず、**要判断**として挙げて聞く。

### 6. 記録する

`docs/raw/YYYY-MM-DD-llm-wiki-lint.md`（先頭に `kind: research`）に残す。見本は `docs/raw/2026-08-12-llm-wiki-lint.md`・`2026-09-30-llm-wiki-lint.md`。
節は サマリー / 修正済み / 矛盾・ドリフト（要判断）/ 孤立 / 知識ギャップ / 次に聞くべき問い / Compile Log。
Compile Log の書式は `wiki-compile` の `references/compile-log.md`。

### 7. 昇格させる

**同種の指摘が2回出たら**、機械検査（報告）に落とす。誤検知が小さいと確認できたらゲートに上げる。
履歴で実際にこの経路を辿った: Compile Log の欠落 → 報告 → 後に行き先の実在をゲート、SQL の適用台帳の漏れ → 報告 → ゲート。
昇格の検討は意味 lint の出口の仕事で、検査の追加は `scripts/check-wiki-size.mjs` に足す。

## 測定の落とし穴（実際に踏んだもの）

- **文字数を `wc -m` で測らない。** `LANG` が空の環境ではバイト数を返し、日本語が約3倍に見える。
  `npm run check:wiki` か `[...s].length` を使う。
- **git の標本は `main` の範囲で取る**（`git log main ...`）。作業ブランチの大きなコミットが混ざると数字が歪む。
- **「ディレクトリが本文にある」を数えない。** `scripts/` や `lib/` のような1階層の文字列はほぼ全ページに出るので、再現率が水増しされる。
- **「言及と同じ行だけ」を見る機械検査は、隣の行の対比語をすり抜ける**（「〜とは別物」が次の行にある、など）。
  所有者の点検は、機械検査のあとに本文を読んで確かめる。
- 正規表現のエスケープを誤ると全件ゼロ件に見える。0件が出たら、まず**検査自体が動いているか**を疑う。

## 完了の目安

- ゲートが通り、報告の項目の増減を確認した。
- 主張の突き合わせの結果（一致 / 矛盾 / 確認できない）と、直したもの・聞くものが lint ノートにある。
- 実施予定を過ぎた運用があれば、宿題として挙げた。
