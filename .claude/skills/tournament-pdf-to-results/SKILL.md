# 大会結果PDF → matches / results

## このスキルの位置づけ

エントリーの抽出は `tournament-pdf-to-players` の担当で、成果物は
`tools/<大会>-<年>/<種目>.initialPlayers.json` にステージングされる。
このスキルはその**続き**で、同じPDFから勝敗とスコアを読み、
`data/tournaments/details/<大会>/<年>/<種目>.json` を組み上げるところまでを見る。

エントリーがまだ無ければ先に `tournament-pdf-to-players` を通すこと。
エントリーの並び（entryNo）はドローの席順そのものなので、
結果の読み取りはその席順に完全に依存している。

**予選リーグを含む大会はこのスキルの対象外。** 決勝トーナメントの枠がリーグ順位で決まり、
entryNo のドロー順と対応しないので、ここで説明する「枠数から逆算する」やり方が成立しない。

## 手順の全体像

1. PDFの様式を見極める（下記の5つの問い）
2. 既存パーサで通るか試す。通らなければ差分だけ足す
3. **検算する**（ここが本体。読み取り誤りは静かに紛れ込む）
4. 共通モジュールで details 形式に組み上げる
5. 後処理（学校名の正規化・information への年度追記）
6. docs/raw と docs/wiki に書き戻す

## 1. 様式を見極める

いきなりパースを書き始めず、次の5つを先に確定させる。ここを外すと後の全部が崩れる。

**(a) テキストレイヤーがあるか。** `pdfplumber` で `extract_text()` が空なら全ページが
スキャン画像。2013年以前のインターハイと全中2019がこれで、ベクター図形が無いので
座標ベースの手法は一切使えない。**画像処理の経路は全中2019で確立済み**
（勝ち上がりが色付きなら色分離、`references/layouts.md` の「スキャンPDF」）。
まずここを確認する。

**(b) 勝者のスコアが印字されるか。** 丸数字（⑤④③）があれば勝者側にもスコアがある。
裸の数字しか無ければ**敗者のスコアだけ**の様式で、勝者スコアは種目の規定値で補完するか、
別ページのスコア表から採るしかない。ページ全体のスコア字を数えて丸数字の有無を見る。

**(c) 1ページに何エントリー入っていて、何回戦まで載っているか。** 左右のエントリー番号列を
拾って行数を数える。行数以下で最大の2の冪が「枠数」で、そこから各ラウンドの試合数が決まる。

**(d) ページ最終戦は何回戦か。** ページの左半分の勝者と右半分の勝者が突き合わされる試合が
準々決勝そのものの年度もあれば、5回戦どまりで準々決勝は別ボックス／別ページの年度もある。

**(e) 準々決勝以降がどこにあるか。** 多くは末尾のスコア表ページ。
**ドローページとスコア表の両方に準々決勝が載っていることが多く、これが最良の検算材料**になる。

## 2. 既存パーサ

| スクリプト | 想定様式 | 検証済み |
|---|---|---|
| `scripts/pdf/zennihon_championship_results.py` | 汎用。丸数字あり／なし両対応、枠数から逆算 | 天皇杯 2017-2019 |
| `scripts/pdf/highschool_championship_results.py` | 実線の矩形を幾何的に追跡 | インターハイ 2014 |
| `scripts/pdf/zenchu_results.py` | 結果一覧ページ／**スキャン画像（赤インクを色分離）** | 全中 2018・2019 |

**新しい大会・年度はまず `zennihon_championship_results.py` を試す。** 枠数から逆算する方式は
座標のブレに強く、`--page-final-round` / `--drop-last-row` / `--loser-only` の3つのフラグで
既知の3様式を切り替えられる。それでも通らないときだけ、そのPDF専用の読み取りを足す。

読み取り方の詳細と、これまでに当たった様式の一覧は
`references/layouts.md` を読むこと（新しい年度で詰まったら、まずそこの「落とし穴」を当たる）。

## 3. 検算 ― ここを飛ばさない

抽出の誤りは例外を出さずに「もっともらしい別の結果」になる。だから
**独立した情報源との突き合わせを必ず1つ以上通す**。使えるものは大会によって違う:

- **準々決勝の二重掲載**: ドローページ側とスコア表ページ側を別々に読んで一致を確認する。
  完全に独立な2経路なので最も強い。
- **ページ勝者の顔ぶれ**: ドローに準々決勝が無い様式なら、各ページの勝者の集合が
  スコア表の準々決勝の出場者と一致するかを見る。
- **エントリー数**: `tools/` のステージングと一致すること。
- **ラウンドごとの試合数**: 枠数の理屈と合うこと（例: 128枠なら2回戦64・3回戦32…）。
- **優勝ペア**: 実在の記録と照らす。ここが違えば全部疑う。

スクリプトにはこれらを `assert` として埋め込み、**食い違ったら止まる**ようにしておく。
あとから人が気づける保証は無い。

読み取りが疑わしい箇所は、その領域を画像に切り出して実際に目で見る:

```python
page.crop((x0, y0, x1, y1)).to_image(resolution=200).save("/tmp/check.png")
```

## 4. details 形式への組み立て

`scripts/pdf/tournament_results_common.py` の `build()` に渡す。試合の一覧はこの形:

```python
{"round": "3回戦", "entries": [12, 35], "winner": 12,
 "winnerScore": 5, "loserScore": 3, "retired": False}
```

`build()` が `matchId` の採番、`nextMatchId` / `prevMatchIds` の張り替え、
`entries[].type`（seed / packing / extra）の逆算、`results[]` のラベル、
`participants[]` の生成と並び順を全部引き受ける。**ここを大会ごとに書き直さないこと**——
規約（特に `type` の逆算）を間違えるとブラケット表の描画が静かに壊れる。

続けて `check()` を呼び、`assert not problems` で止める。リンク整合・勝者の進出・
同一ラウンドの重複・results のラベルまで見る。`write()` は既存ファイルと同じ整形で書く。

勝者スコアがPDFに無い様式では `winner_score_default` を渡す。
**その値は仮定なので、必ず「なぜその値か」を明記する**
（例: 個人戦ダブルスは4本先取なので常に4。団体戦は年度で3試合消化か2勝先取かが変わる）。

## 5. 後処理

**学校名の正規化を忘れない。** PDFの表記のまま入れて、名寄せは対応表に任せるのが
この repo の流儀:

```bash
node scripts/normalize-team-names.mjs --scope=<大会ID> --dry-run   # まず差分を見る
node scripts/normalize-team-names.mjs --scope=<大会ID>
```

`尽誠学園高等学校` → `尽誠学園` のように既存の団体マスタへ寄る。冪等。
これを飛ばすと同じ学校が別チーム扱いになり、選手ページの集計がずれる。
対応表に無い表記が残る場合は `data/tournaments/team-name-aliases.json` への追記を検討する
（`tools/<大会>-<年>/team-alias-proposal.json` に候補が置かれていることがある）。

**`data/tournaments/information/<大会>.json` に年度の項目を足す。**
公開ページの年度一覧はここから作られる（`getAllAvailableYears`）ので、
details を置いただけでは表に出ない。`startDate` / `endDate` / `location` が
**結果PDFに書かれていないことは珍しくない**。その場合は推測で埋めず、
要項や連盟サイトで確定するまで未了として残し、ユーザーに伝える。

最後に repo の検査を通す:

```bash
node scripts/check-tournament-entries.mjs
node scripts/check-orphan-entries.mjs
node scripts/check-duplicate-placements.mjs
npm run bracket:verify
```

## 6. 書き戻し

`AGENTS.md` の LLM Wiki 運用に従い、`docs/raw/<日付>-<大会>-<年>-results-from-pdf.md` に
実施記録（様式の見極め・詰まった点・検算結果・未了）を書き、そこから
`docs/wiki/data-import.md` へ「次の年度でも使える知見」だけを compile する。
raw ノートの末尾に Compile Log（何を載せ、何を意図的に載せなかったか）を付ける。

**その年度限りの数値（試合数の内訳・優勝ペア名）は raw に留める。**
wiki に載せるのは「次に別の年度を触る人が最初に踏む落とし穴」だけ。

## よくある落とし穴

- **ラウンドの切り分けをスコアのx座標でやる。** ページ最終戦のスコアが1つ手前の列に
  置かれる年度があり、素直に列で切ると静かにずれる。枠数から個数を出して切る。
- **点線のダッシュを幅と高さの大小で横線/縦線に分類する。** ほぼ正方形（0.9×0.96pt）の
  年度があり、判定が反転して行が丸ごと落ちる。「y方向に薄いもの」を横線候補にする。
- **`R`（棄権）を1文字前提で弾く。** `4R`（4ゲーム時点で棄権）という1語表記がある。
  出力は `retired: true` ＋ 読めた本数（無ければ0）。
- **勝ち上がりの色付き太線を「その試合の勝者」と読む。** 色は「1つでも勝った競技者の経路」を
  敗退まで塗るので、水平線の色では2回戦以降の勝敗が決まらない（1回戦だけ正しく出るので気づきにくい）。
  **合流点の縦線**を見ること。勝者側の脚だけが色付きで、敗者側は黒。
- **スキャンの数字をコンタクトシートで通し読みする。** 行内で位置がずれて写経ミスをする。
  クラスタリングを正とし、目視は代表字の同定と外れ値の確認だけに使う。
- **エントリー番号を「ブラケット帯の外側の数字」で拾う。** 所属名に数字が入る例
  （`ｔｅａｍ 87 ｔａｂａ`）がある。左右いちばん外側の桁列に限定する。
- **ドローの外に印字された数字を試合として拾う。** ページ勝者のその後の本数が
  最終行より下に置かれる年度がある。エントリー行の範囲外は落とす。
- **選手名を囲む枠を合流点と誤認する。** 「入力2・出力1」という形が試合の合流と同じなので、
  エントリー番号に紐づかない合流は読み飛ばす。
- **合流の出力ラインを入力2本の中点と仮定する。** 席順の都合でずれる。
  垂直線の切れ目に始まる水平線を出力として拾う。
