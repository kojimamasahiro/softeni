# ADR-012: サイト本文でのLLM利用を「機械照合を通ったものに限り可」として解禁する

## Status

Accepted。決定日: 2026-08-01。現状仕様: `docs/story-yaml/README.md` / `docs/story-yaml/PROMPT.md` /
`docs/raw/2026-08-01-idea-news-fact-based-story-categories.md`。

ADR-005（文脈ブロック）の「本文はテンプレートのみ・LLM不使用」を **Superseded**（その一点のみ）。
文脈ブロックを一次成果物とする中核方針、既存ページへの差し込み、テンプレート由来のバッジ表示は
ADR-005 のまま有効。

## Context

ADR-005 は「本文はテンプレートのみ生成し、LLMは使わない」と決めていた。理由は
**誤った事実を載せると信頼を損なうから**で、これは当時「LLMの捏造を機械的に検出できない」
という前提に立っていた。

2026-08-01、この前提が崩れた。

1. 大会データから「確定した過去の事実」だけを決定的に抽出する
   `scripts/generate-story-yaml.mjs` を実装した（LLM不使用）。
2. 出力された本文が実データと一致するかを照合する `scripts/verify-story-text.mjs` を実装した。
   照合先はストーリーYAMLではなく**生データ**（`data/tournaments/details/**`）で、
   生成スクリプトのバグとLLMの捏造の両方を同じ仕組みで捕まえられる。
3. 実効性は実測で確認済み。試作YAMLに紛れ込んでいた「もっともらしい」事実誤り3件
   （選手の成績・連続年数の取り違え）を検出し、正しい投稿案には誤検知ゼロだった。

つまり **「LLMを使わない」ではなく「LLMの出力を検証する」という選択肢が実在するようになった**。
一方で、テンプレート文には表現力の限界がある。複数年・複数種目にまたがる文脈
（例: 尽誠学園が団体で3連覇後に後退する一方、個人では優勝している）は、バッジの羅列では
伝わらず、散文でしか書けない。

## Decision

**サイト本文にLLMが執筆した読み物（大会インサイト）を掲載してよい。ただし機械照合を
通ったものに限る。**

1. **保存先**: `data/tournament-insights/<tournamentId>/<year>/<categoryId>.json`。
   `state`（draft / review / published）・`paragraphs`・`usedStoryIds`・`scopeNote`・
   `writtenBy`・`verifiedAt` を持つ。state の語彙は既存の news レコードに揃える。
2. **公開条件**: `state === 'published'` かつ `verifiedAt` が入っていること。
   判定は `lib/tournamentInsight.ts` の `getPublishedInsight()` に集約し、描画側では判定しない。
3. **ビルドで強制する**: `scripts/check-tournament-insights.mjs` を prebuild に組み込み、
   公開済みインサイトを**その場で照合し直す**。`verifiedAt` の値は信用しない。
   本文を後から書き換えて `verifiedAt` を残す事故を防ぐ唯一の方法であり、実際に
   本文改竄でビルドが落ちることを確認済み。1件でも不合格ならビルドを止める。
4. **掲載先は既存ページのみ**: 年度別結果ページの「注目ポイント」（`ResultContextBlocks`）を
   拡張する。**新規URLは作らない**ため、ADR-010（同一実体の二重ページ禁止）と抵触しない。
5. **`usedStoryIds` を必須にする**: 根拠を追跡できない本文は公開しない。
   照合が警告を出したときに原因のストーリーを特定できる。

## Alternatives

- **ADR-005 のままテンプレート文のみで通す**: 安全だが、複数年にまたがる文脈が書けない。
  実測でも「団体で3連覇後に後退／個人では優勝」のような筋はバッジの羅列では伝わらない。
  検証手段が手に入った以上、リスクを理由に選択肢を閉じ続ける根拠が弱い。不採用。
- **LLM散文はSNSにのみ出し、サイトには載せない**（2026-08-01の初期判断）: SNSとサイトで
  同じ事実を二重に運用することになり、せっかく検証を通した本文が1回で捨てられる。不採用。
- **人のレビューのみを公開条件にする**: 実測で見つかった誤り3件はいずれも「もっともらしく」、
  人のレビューを素通りする性質だった。人手の注意力に依存する設計は取らない。不採用。
- **照合を CI ではなく手順書で担保する**: 手順書に書いただけの条件は必ず抜ける。不採用。

## Consequences

- 利点: テンプレートでは書けない複数年・複数種目の文脈をサイトに載せられる。SNS用に書いた
  読み物をサイトでも使えるため、1回の執筆が2箇所に効く。
- 利点: ADR-005 の目的（誤った事実を載せない）は、方法を変えて維持される。むしろ
  **テンプレート文より強く担保される**（テンプレート文は生成ロジックのバグを検出できないが、
  照合スクリプトは生データに当たるため検出できる）。
- 欠点: 照合スクリプトが検証できる主張の型（年×成績・連続年数・連覇・スコア・固有名詞）に
  限りがある。ベスト8未満の成績は「N回戦敗退」がドロー規模依存のため原理的に照合できず、
  素通りする。**執筆側でベスト8以上の事実だけを扱う**運用で回避する。
- 欠点（2026-08-01 追記）: **照合を通っても誤りは残りうる**。インターハイ2026女子ダブルスで
  「就実は勝ち残りが無くなった」と誤って公開した実例がある（3組目が試合データに現れず、
  集計から黙って落ちていた）。「何組残っているか」は照合できる主張の型に無いため
  `verify-story-text.mjs` は素通りした。**機械照合は捏造を防ぐが、集計ロジックの
  取りこぼしは防がない**。生成側の分類に「不明」を持たせ、断定できない場合は
  断定しない文言を出す設計（`watched-school-progress` の `unknown`）で補う。
- 欠点: 公開ごとにLLM実行と人のレビューが発生する。全大会に展開できる作業量ではないため、
  当面は供給量の多い一般カテゴリと全国大会に絞る。
- 影響: prebuild が1ステップ増える。公開済みインサイトが0件のうちは実質ノーコスト。

## Open Questions

- 照合できない主張の型（ベスト8未満の成績、大会をまたぐ事実）をどう扱うか。現状は
  執筆側の自制に頼っている。
- インサイトを置く単位。現在は「大会×年×種目」だが、記事の単位は「大会×年（全種目束ね）」と
  決めており、粒度が一致していない。大会ハブ側に束ねたものを置くかは未決（ADR-010 の
  「ハブを歴代横断統計で強化する」方向と重なる）。
- 検索面での扱い。インサイトが増えた場合に構造化データ（JSON-LD）へ載せるか。
