# ADR-016: 広告は自動広告のページ内挿入をやめ、手動枠（AdUnit）で位置と高さを固定する

## Status

Accepted

## Context

本サイトの Web 本体の主収益源は AdSense である。当初は自動広告（Auto ads）に全面的に
任せていたが、次の不具合が続けて起きた。

- 自動広告のページ内自動挿入が、テーブルの途中やファーストビューへ割り込み UX を壊す。
  挿入位置を指定する手段が無い。
- 挿入時に高さが確保されないためレイアウトシフト（CLS）が出る。Core Web Vitals は
  SEO・収益の双方に効くため放置できない。
- モバイル全画面（ビネット）で、閉じた後もページがスクロールできなくなる事象
  （2026-08-20、`docs/wiki/monetization.md`）。

これらを避けるため、ページ内フォーマットとビネットを管理画面でオフにし、下部アンカー広告
だけの運用にした。結果としてレイアウトは安定したが、**広告売上が旧水準の約1割まで落ちた**
（ユーザーの体感値・Assumption）。

つまり「自動広告に戻せばレイアウトが壊れ、アンカーだけでは収益が立たない」という
二択になっていた。どちらも選ばずに済ませる第三の道が必要になった。

なお 2026-06-12 の `docs/adsense-ui-proposal.md` に手動枠の設計案が既にあったが、
未実装のまま残っていた。

## Decision

**自動広告のページ内挿入は使わず、手動広告枠コンポーネント `AdUnit` で、
掲載位置と占有高さをコード側で固定する。**

- 枠は `src/components/AdUnit.tsx` の1コンポーネントに集約する。
- スロットIDは `lib/ads.ts` の `AD_SLOTS` で**ページ種別ごとに分けて**一元管理する。
  分けるのは、AdSense レポートで面ごとの RPM を比較できるようにするため。
- 空のスロットIDは「未配信」を意味し、`AdUnit` は DOM ごと描画しない。
  これによりコードを本番に入れたまま、面ごとの有効化タイミングを管理画面側で制御できる。
- 掲載面は**PV の多い順**に決める。第1段階は選手一覧 / 大会結果 / 大会一覧 / news展望 の
  4面へ**1枠ずつ**。
- 密度の歯止めは「ファーストビューに置かない」「1ビューポートに2枠出さない」
  「表・カード・トーナメント表の内部に入れない」の3点。外部基準としては Lighthouse
  Publisher Ads Audit のビューポート垂直方向30%を上限の目安に置く。
- 段階導入する。1面ずつ有効化し、CLS・ページRPM・回遊の3指標で2週判定してから次の面へ進む。
- **選手結果ページ（最大母数）には枠を置かない**。回遊検証ランブックが対照群として使う面で、
  ここに広告を入れると回遊施策の効果判定が成立しなくなるため。

自動広告は補完用途（下部アンカー）に限定して併用を続ける。

### 追記（2026-08-23）: 掲載位置を「ファーストビュー回避」から「ファーストビュー内」へ変更

上の Decision のうち、密度の歯止めの1つ「ファーストビューに置かない」だけを覆した。
残り（1ビューポートに2枠出さない・表やカードの内部に入れない・1ページ1枠・選手結果ページは
対象外）は変更していない。

**変更内容**: 4面すべてで、枠を「そのページの主目的の操作・リード文を終えた直後」へ移した。
375×812 の実測で枠上端は 402〜492px、枠高280pxなので4面とも枠全体がファーストビューに収まる。

**理由**: 当初配置はスクロール下方（例: 大会結果ページならトーナメント表の直後）で、
視認率が低く、そのぶんページRPMも上がりにくい。「レイアウトを崩さない」という本 ADR の
主眼は高さの事前確保で担保されており、位置がファーストビュー内かどうかとは独立している。
つまり原案の「ファーストビュー回避」は本 ADR の中核ではなく、上乗せの UX 方針だった。

**受け入れたリスク**: アバブザフォールドの広告密度が上がる。280px / 812px = 34% で、
Lighthouse Publisher Ads Audit の30%目安をモバイルでは超える。1ページ1枠を守る前提で
許容している。2枠目を検討するときはこの数字が制約になる。

**運用上の注意**: 「ファーストビュー内」は節を1つ足すだけで壊れる。実際、大会結果ページは
最初 年度/カテゴリ切り替えの後ろに置いて top=628px となり枠の下半分が折り返し下へ落ちた
（切り替えUIの前へ移して 408px に修正）。配置を触ったら 375×812 で枠上端を測り直すこと。
実測値は [monetization.md](../wiki/monetization.md) の掲載面テーブルに列として持たせてある。

### 追記（2026-08-25）: 掲載面の拡大と、面の増やし方の仕組み化

想定より収益が出たため掲載面を拡大した。Decision 本体（手動枠で位置と高さを固定する）は
変えていないが、**面の増やし方**と**歯止めの置き方**を次のとおり改めた。

**1. フッター直上の枠を追加し、ページごとの設置をやめた。**
`AppShell` の `<main>` と `{footer}` の間に1箇所だけ置き、`FOOTER_AD_PAGE_TYPES`
（`lib/ads.ts`）の許可リストで出し分ける。面を増やすのがリスト1行になる。
判定に既存の `getPageType()` を使ったので、`/matches/*` と `/beta/matches-results/*` の
ように実体が同じコンポーネントでも beta 側だけ除外できる。
広告の載るページは 433枚（9.9%）→ 約3,900枚（約89%）。

**2. 「1ページ1枠」を撤回した。**
ファーストビュー枠とフッター枠の2枠になる面がある。375×812 の実測で、最も短い大会結果
ページでも2枠の間隔が1,078px（>812px）あり、同一ビューポートには入らないことを確認した。
薄い種別にはファーストビュー枠を置かずフッター枠だけにしている。
なお 8/23 の追記で「2枠目を足すときは30%目安が制約になる」と書いたが、**同時に見えないので
ビューポート密度としては1枠のまま**であり、この制約には抵触していない。

**3. 種別の許可リストだけでは不十分だと分かり、本文量の下限を足した。**
`/tournaments/local/<県>/` は種別としては `tour_hub` だが、その県の大会が未登録だと本文が
「現在登録されている大会はありません。」だけ（`<main>` 実測78文字）になる。AdSense は
コンテンツのないページへの掲載を禁じているため、種別で一括許可すると違反面を作ってしまう。
`AppShell` がマウント後に `main.textContent` を測り、400文字未満なら枠を出さない
（`FOOTER_AD_MIN_CONTENT_CHARS`）。閾値は `out/` 全4,346枚の実測分布から決めた。
除外リストの保守が要らず、データが増えれば自動的に広告が出るようになる。

**4. 「選手結果ページは対照群だから対象外」を撤回した。**
8/23 の Decision に書いたこの制約は過剰だった。回遊検証の判定式は水準差ではなく
**変化の差**（学校ページの変化 − 選手結果ページの変化）を見るので、要件は
「対照群に広告を入れないこと」ではなく**「測定期間中に両群が別々に変化しないこと」**。
両群へ同時に入れて9月末のベースライン取得前に定常化させれば判定は成立する。
これで全ページの62%（選手結果43.6% + 高校学校18.2%）が解禁された。
**代わりの制約**: ベースライン取得後・測定期間中はこの2種別の広告設定を一切触らないこと。

**未確認のリスク**: モバイルの下部アンカー広告（自動広告）は `position: fixed` で最下部に
貼り付くため、フッターまでスクロールすると「フッター枠280px + アンカー約50px」が同一画面に
並ぶ（812pxの41%）。ローカルでは自動広告が配信されず確認できないため、本番で見て
アンカーを切るかフッター枠を切るかを判断する。

### 追記（2026-08-25）: `/tournaments/` の枠位置を「フィルターバーの直後」から「これから開催の直後」へ

Decision 本体も、2026-08-23 追記の「ファーストビュー内に置く」方針も変えていない。
**同じ方針を保つために位置を動かした**という記録。

**きっかけ**: `/tournaments/` に「これから開催」ブロックを追加した
（[public-pages.md](../wiki/public-pages.md)「開催前の大会を出す」）。当初はフィルターバーの下＝
広告枠より後ろに置いたが、「探しに行かないと見つからない」問題を直すためのブロックが
折り返しの下にあっては意味が薄い。

**実測（375×812）**:

| 構成 | ブロック高 | 枠上端 | 枠下端 | 折り返し(812px)内 |
|---|---|---|---|---|
| 変更前（枠→ブロックの順） | — | 492px | 772px | 収まる（ただしブロックが折り返し下） |
| ブロック5件を枠より上へ | 314px | 624px | 904px | **収まらない** |
| ブロック3件を枠より上へ（採用） | 155px | 499px | 779px | 収まる |

**したがって「これから開催」の最大3件は、UIの好みではなく広告枠の制約から決まった数値**である。
増やすときは必ず 375×812 で測り直すこと（`UPCOMING_LIMIT` のコメントにも同じ注意を書いた）。

**副作用**: ブロックはフィルターより上＝絞り込みの外側になったため、
絞り込み結果ではなく全件から作るようにした（絞ると消えるのは挙動として不自然なため）。

## Alternatives

1. **自動広告のページ内挿入を再度オンにする** — 収益は最も手早く戻るが、レイアウト崩れと
   CLS という元の問題がそのまま戻る。この二択を避けるのが本 ADR の目的なので却下。
2. **アンカー広告だけの現状維持** — レイアウトは安定するが、実際に売上が約1割まで落ちた。
   課金以外の収益源が事実上消える。
3. **手動枠を最初から全面展開（原案どおり選手詳細2枠・チーム2枠・試合詳細3枠）** —
   原案 `adsense-ui-proposal.md` の配置。却下理由は2つ。(a) 原案の面は PV 上位ではなく、
   同じ実装コストならPV上位面に入れた方が効く。(b) 一度に複数枠を入れると、
   CWV や回遊が悪化したときにどの枠が原因か切り分けられない。
4. **`data-full-width-responsive="true"` で端末幅いっぱいの枠にする** — モバイル収益は
   上がりうるが、実測で AdSense が `ins` を 375×375 に広げ `margin-left: -16px` で
   PageLayout の左右パディングの外へはみ出し、確保した `min-height` も超えてシフトが出た。
   「レイアウトを崩さない」という本 ADR の前提と衝突するため `false` にした。
   収益目的で反転させる場合は CWV を見る前提の実験として扱う。

## Consequences

メリット:

- 広告の位置と高さがコードで確定し、レビューできる。自動広告のように「本番でだけ壊れる」
  現象が原理的に起きにくい。
- 高さを事前確保するため CLS が出ない（未配信時の畳み込みを除く）。
- ユニットを面ごとに分けたので、どの面が収益に効いているかをレポートで直接読める。
- 空スロット＝非描画にしたので、コードのデプロイと配信開始を切り離せる。

デメリット・注意点:

- 新しいページ種別に枠を足すには、コード変更（`AD_SLOTS` へのキー追加と設置）が要る。
  自動広告のような「勝手に増える」性質は無い。これは意図した制約。
- 未配信時に枠を畳む判断のため、僅かなレイアウトシフトが残る。本文途中に数百pxの空白が
  残り続けるよりは良いという比較で選んでいる。
- 手動枠と自動広告のページ内挿入が併存すると密度の歯止めが崩れるため、管理画面側の
  「ページ内フォーマットをオフ」は本 ADR の前提条件になる。コードだけでは担保できない。
- 段階導入の合否閾値は現時点で自サイト実測ではなく暫定値である（`monetization.md`）。

## Open Questions

- 段階導入の合否閾値（CLS 0.1 / 推定収益 / 回遊20%）は暫定。1面目の実測が出た時点で
  自サイトのベースラインに差し替える。
