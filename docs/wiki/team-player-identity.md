# チーム・選手の名寄せと識別

大会結果データ（`data/tournaments/details/**`）の表記揺れを正準化し、チーム／選手を一意に
識別するための仕組みと運用をまとめる。設計の経緯・判断は
`docs/raw/2026-06-26-team-identity-design.md` を参照。

## 全体像

- **都道府県**: 47都道府県の正準形へ正規化（接尾辞・地域接頭辞・外国名・崩れ字を吸収）。
- **チーム**: NFKC で安全な揺れを畳み、人手レビューで略称・省略を `team-name-aliases.json` に
  集約 → 大会データへ適用。`data/teams/teams.json` を連番idのマスタとして生成。
- **選手**: 氏名ベースの id（`data/players/index.json`）を基本とし、確実な同姓同名の別人だけ
  `data/players/homonyms.json` でチーム単位に分割。
- **姓名の分割**: 取り込み由来で切り位置がぶれる（`谷|明日里` / `谷明|日里`）。人手判断を
  `data/players/name-split-aliases.json` に集約 → 大会データへ適用。

## 都道府県の正規化

- スクリプト: `scripts/normalize-prefectures.mjs`（既定スコープ `all`、冪等、`--dry-run` 可）。
- ルール（`participants[].prefecture` は必ず正準形・省略しない）:
  - 接尾辞（都/道/府/県）を必ず付ける（`徳島`→`徳島県`、`東京`→`東京都`）。
  - 地域接頭辞を付けない（`関東・埼玉県`→`埼玉県`）。NFKC で全角半角・区切り（`•`→`・`）統一。
  - 崩れ字・OCR は明示マップで復元（`奈川県`→`神奈川県`、`愛緩県`→`愛媛県` 等）。
  - 県でない値（連盟・外国）は「別の都道府県扱い」の値として保持（`日本学連` `高体連` `韓国` 等）。
- `participants[].id`（`姓_名_team_都道府県`）と `entries[].playerIds` も追従。
- 一括修復済みデータバグ: **primaryschool-championship 2024** は全3,244人が開催地の `秋田県`
  になっていた。他大会から各チームの実県を復元（2,226件）、復元不可は `null`（1,018件）。
- 同型の修復（2026-08-31）: **zennihon-indoor 2025** も boys / girls 両ファイル計48人が全員
  開催地の `秋田県` だった（2022〜2024 は正常）。他大会から**同一人物（姓・名・チーム）の県の
  最頻値**で復元し、48人すべてが一意に決まった。経緯・残課題は
  [2026-08-31-player-registered-name-change.md](../raw/2026-08-31-player-registered-name-change.md)。
  **この型のバグは大会単位で再発するので、新規取り込み時は「1ファイル内の `prefecture` が
  1種類しか無い」を疑うこと**（開催地が流し込まれた形）。

## チームマスタ `data/teams/teams.json`

- 生成: `scripts/build-team-master.mjs`。
  `{ id(連番), name(最頻出表記), prefecture, count, boysCount?, girlsCount?, mixedCount?, aliases?, reviewPrefectures? }`。
- **男女別の収録数**（2026-08-11 追加、`/teams` の男女切替用）: 大会ファイル名（カテゴリID）の
  `-` 区切り**最後のセグメント**から性別を判定して数える（`boys`/`men`→男子、`girls`/`women`→女子、
  `mixed`→ミックス）。部分一致だと `tournament` の `men` に誤ヒットするため厳密一致
  （`src/utils/team-data-aggregator.ts` の `parseGenderFromCategory` と同じ規約）。
  ミックスは男女ペアなので boys/girls には寄せず別に数える。**ミックス種目にしか出ていないチームが
  78件あり**（全日本ミックスダブルスのみのクラブ）、この場合 `boysCount`/`girlsCount` とも付かない。
  実測（count>=2 の3,861チーム）: 男子2,873・女子2,405・ミックスのみ78。
- **表示名の全角ASCIIは半角へ寄せる**（`ＹＫＫ`→`YKK`、`Ｊ－Ｋｉｄｓ`→`J-Kids`）。
  `scripts/lib/halfwidth.mjs` の `toHalfWidthAscii()`。全角英数はほぼ入力・OCR由来の揺れで、
  正式表記が全角の団体は実質ないため。半角化前の生表記は `aliases` 側に残るので情報は失われない。
  NFKC ではなく U+FF01–FF5E 限定の変換を使う（NFKC は半角カナ→全角カナ、㈱→(株) 等も巻き込むため）。
  なお **大会データ本体は書き換えない**（表示名のみ）。
- `prefecture` は実県の最頻値だが、**実県カバー率が低いチーム（大学・連盟系など）は信頼できない
  ため null**（社会人/学校は県が安定するので付与される）。
- id は count 降順→名前で決定的に採番（再生成で安定）。
- 文脈サイドカー `data/teams/team-context.json`（id→選手名/年範囲/主な大会/ジャンル/大会インスタンス）。
  レビューと自動判定に使用。

## 機械的な揺れの正準化（データ本体）

`scripts/normalize-team-spacing.mjs`: NFKC で同一になる生表記（全角半角・スペース・中黒記号の差）を
大会データ本体で**最頻出の表記へ寄せる**（人手不要・冪等）。例: `one team`/`oneteam`→`one team`、
`Up Rise`/`UpRise`→`Up Rise`、`ＵＢＥ`/`UBE`→片方へ。`team`/`id`/`playerIds` を追従。
注意: **大文字小文字差は NFKC で畳まれない**（`UpRise`≠`Uprise`）。必要なら別途対応。
注意: ここは**頻度依存なので、データが増えると採用表記が入れ替わりうる**（NFKC等価ペアに限る）。
表記を固定したい場合は alias 表に canonical として明示的に書くこと。

**`prebuild` で自動実行される**（2026-08-30 追加）。人手不要・冪等なため、新規大会データを
取り込んだ後に手動で回さなくても `npm run build` / `npm run prebuild` のたびに全角半角・
スペース揺れが正準化される。実例: `zennihon-workers` 2026年の新規取り込みだけ `ＮＴＴ西日本`
（全角）と入り、過去年の `NTT西日本`（半角）と表記が割れたため、
`generate-story-yaml.mjs` の学校単位集計（`watched-school-progress`）がこのチームを
「前年に記録がない」と誤判定し、大会インサイトの注目ポイントから丸ごと欠落した
（4年連続優勝中の主力チームが記事に出ないという実害）。以後はビルドのたびに解消される。

## 異体字・旧字体の扱い（照合と表示の分離）

NFKC は**字体差を畳まない**（`鄉`≠`郷`、`髙`≠`高`、`﨑`≠`崎`、`學`≠`学`、`應`≠`応`）。
このため字体だけ違う同一チームが別チームとして分裂する。実例: `西鄉第一` と `西郷第一中学校`
（福島県西郷村の同一中学校）が別チーム扱いになり、選手ページのキャリア年表で所属が割れていた。

対応方針は**照合と表示を分ける**こと:

| 用途 | 方式 | 理由 |
| --- | --- | --- |
| 照合（マージ候補検出） | 新字体へ畳む | 機械的・再現可能。取りこぼしを無くす |
| 表示（canonical） | **正式名称** | 公開サイトなので正確さ・検索流入を優先 |

- 対応表: `scripts/lib/kanji-variants.mjs`（`foldKanjiVariants()`）。
- 照合キーの算出は `scripts/lib/team-core.mjs`（`teamCore()`）に集約。
  **`build-team-merge-candidates.mjs` と `check-identity-health.mjs` は必ず同じ定義を使うこと。**
  以前は両者が `core()` を各自複製しており、候補生成側だけ異体字対応を入れた結果、
  ヘルスチェックが未統合候補を 8件→2件 と過少報告した。判定ロジックを増やすときは
  共通モジュール側を直す。
- **この畳み込みは候補検出専用**。データ本体の表記を自動で書き換えてはいけない
  （正式名称に旧字体を使う学校・大学があるため）。実際の名寄せは従来どおり人手レビュー →
  `team-name-aliases.json` 経由。
- 表示まで新字体に統一するのは**不採用**。`國學院大學`→`国学院大学`、`慶應義塾大学`→`慶応義塾大学`
  となり正式名称と乖離する。
- **canonical は「正式名称」を採る**。最頻出表記は初期候補にすぎない（多くの場合一致するが、
  一致は保証されない）。
- canonical は alias 表に文字列で固定されるため、**後から出現数が逆転しても入れ替わらない**。
  ただし `build-team-master.mjs` の表示名はグループ内の生表記の最頻出なので、
  **`normalize-team-names` を流さずに `build-team-master` だけ回すと表示名が alias 側に振れる**。
  下記の実行順序を必ず守ること。
- 誤爆を避けるため、対応表には「明らかに同字の異体字」のみ入れる。意味の異なる別漢字は入れない。

## チーム名寄せの運用

正準名の対応表 `data/tournaments/team-name-aliases.json`（`canonical ← aliases`）に人手判断を
蓄積し、大会データへ適用する。

1. **候補生成** `scripts/build-team-merge-candidates.mjs`: 2つのシグナルで抽出し、
   `data/teams/merge-candidates.json` に `signal` つきで出力する。
   - `signal: "core"`（コア一致）: 県内ブロックで接尾辞除去後のコアが完全一致
     （高校/中学校/中/少年団/各種クラブ等を除去、付↔附を同一視、NFKC＋異体字を畳む）。
   - `signal: "players"`（選手共有 / 2026-09-05 追加・[ADR-017](../adr/ADR-017-team-merge-signal-player-overlap.md)）:
     **同一年度に同じ氏名の選手が2チームへ出場**しており、共有が2名以上（`scripts/lib/team-player-overlap.mjs`）。
     名前の類似度を一切使わないので、コア一致の盲点である**語中の脱落**（`岡山理大附` ⇔ `岡山理科大附高校`）に届く。
     県ブロッキングは同条件、コア一致するペアは除外（二重計上しない）。
     偽陽性は「同年に同じ選手が両方へ登録される別チーム」（`大館ジュニア` と `大館市協会` 等）で、
     **このシグナルのクラスタは自動OKにせず常に人手レビュー**。
2. **レビュー** `scripts/build-team-review-html.mjs` → `data/teams/team-merge-review.html`
   （ブラウザでクリック判断）。各メンバーに選手名・年・大会を表示。
   - **裏付けの無い統合は自動で通さない**（2026-09-06 追加）。出場大会の記録が無い
     （`genres` が空の）メンバーが他のメンバーと同じグループに入る場合、名前の段階だけを
     根拠に統合することになるので、**自動OKにせず人手レビューへ回す**。
     抜き取り監査でこの型の自動統合は**8件中4件が誤り（50%・下限21.5%）**だった
     （常磐大/常磐大学高校、国府台/国府台高校 ほか）。正しく統合できる例
     （大田原女子/大田原女子高校）も構造が同一で、手元の情報では区別できない。
     **賢く判定するのではなく、機械が決めないのが正解**という結論。
   - **自動判定（大会の共起ベース）**: ジャンル（出場大会の段階）が違えば自動で別チーム。
     段階の判定は**出場大会由来を優先し、無ければ名前から推定する**。
     どちらの由来でも段階が同じなら同じグループにする（2026-09-06 修正。
     以前は由来ごとに別キーにしていたため、片方だけジャンルを持つクラスタが必ず分割され、
     自動OK 350件のうち実際に統合が起きるのは1件だけだった）。
     同一グループ内で2表記が「同一大会(大会id+年)」に同居していれば要確認、そうでなければ自動OK。
   - 段階ジャンルは大会から判定（`team-context.json` の genres）。**社会人とシニアは同じ成人
     カテゴリに統合**（同一人物が両方に出るため）。
   - 「確認済にする」を押したものだけが反映対象。
   - **判断は `data/teams/review-decisions.json`（判断台帳）に保存する**（2026-09-06 追加）。
     localStorage は作業用キャッシュで、正は台帳のほう。台帳はクラスタを
     **メンバーのチーム名を正準化して昇順連結したキー**（`scripts/lib/review-ledger.mjs` の
     `clusterKey`。NFKC＋空白除去）で識別するので、
     **候補一覧をいつ作り直してもよい**（旧実装は配列インデックス保持だったため、再生成すると
     判断を取り違えるか捨てるかしかなく、「レビュー中は候補を作り直さない」運用でしのいでいた）。
     **team id は使えない**（2026-09-06 に実測して判明・台帳 v2 で修正）。`build-team-master.mjs` は
     `const id = teams.length + 1` と**位置でIDを振る**ため、alias を反映してマスタを作り直すと
     IDが総入れ替わりになる（実測: 5,520件中5,220件が移動）。id をキーにすると候補の再生成で
     判断の一致率が **0%** になり、直そうとした問題を再現してしまう（名前キーなら 79.6% が引き継がれる）。
     台帳は v1（idキー）を読み込み時に自動で v2（名前キー）へ移行する。
   - 台帳には「**統合しない**」という否定の判断も `verdict: "separate"` として残す。
     あわせて機械が何を提案していたか（`proposedAutoOK`）と誰が決めたか（`decidedBy`）も持つので、
     **「自動OKにしたが人が覆した」件数＝自動判定の誤り率**が後から数えられる。
   - **抜き取り監査はチーム名寄せでは廃止した（2026-09-12・Deprecated）。**
     実測すると 2026-09-06 以降に新しく生まれた自動OKクラスタは**1件**しかなく、
     母集団1件では誤り率を測れない。抜き取り検査は「全数検査が高くつくほど流入がある」
     場所でしか成立しないので、この規模なら**全件を人が見るほうが素直で正確**。
     そこで**機械の自動統合をやめ、人が判断したものだけを適用する**運用に変えた
     （`apply-auto-merges.mjs` の役割変更。下記「反映」参照）。
     抜き取り監査の仕組み自体は、一度に数百件が流入する PDF 取り込み系
     （`scripts/pdf-to-players/`）へ移す。
     `audit-review-sample.mjs` と `review-audit.json` は当時の記録として残置する。
     以下の記述は**当時の設計の記録**であり、現在の運用ではない。
   - ~~**自動判定の誤り率は抜き取り監査で測る**~~（2026-09-06 追加・`npm run review:audit`）。
     母集団は「**機械が決めて人が一度も見ていない**」判断（`decidedBy: "auto"`）で、
     人が既に見たものは**選び方が無作為でないので使わない**。手順は2段階:
     1. `node scripts/audit-review-sample.mjs --draw 20 [--seed S]` で標本を引き
        `data/teams/review-audit.json` に記録する。**引いた時点の機械の判定も保存する**
        （人が判断すると台帳が上書きされ、機械が何と言っていたか消えるため）。
     2. レビュー画面の「**監査対象**」フィルタで標本だけを判断し、
        `node scripts/audit-review-sample.mjs --report` で誤り率と95%信頼区間を出す。

     **引いてから判断する順序を必ず守ること。** 逆にすると「都合のよい結果だけ採る」ことが
     構造的に可能になり、測定が無意味になる。
     **誤りは向きを分けて見ること**（2026-09-06 の実測で判定基準を修正）。
     `merge → separate`（**誤統合**・別チームを1つにした）は**データが壊れる方向**で、
     これだけが「自動OKを締める」根拠になる。`separate → merge`（**見逃し**・統合すべきものを
     残した）は安全側で、締めても減らない——対処は**既定グループ分けの見直し**。
     判定は誤統合の率の下限が閾値（既定5%）を超えたときだけ**自動OKの範囲を締める**。

     **分母を層ごとに分けること。** 誤統合は「機械が統合と判定した」標本でしか起こり得ないので、
     「別チーム」判定を分母に入れてはならない（検証していない安全性を検証したかのように見せる）。
     母集団は「別チーム」判定に大きく偏っているため、全体から無作為に引くと危険な層がほとんど
     入らない。**危険な方向を測るには層を指定して引く**:
     `node scripts/audit-review-sample.mjs --draw 20 --stratum merge`。
     **分母が0のときは率を出さず「未測定」と読むこと。「0件」は「起きていない」ではない。**

     **前提の限界を承知して読むこと。** 監査は「人の判断が機械の判定と独立している」ことを
     前提に誤り率を測るが、**レビュー画面は機械の判定を初期状態として表示する**ため、
     人は機械の答えを見てから判断している。2026-09-06 には監査結果（誤統合50%）を見た後に
     同じ4件が再判断されて反転し、誤り率が 0% になった。
     **標本が少ないうちに機械側の判定ロジックを動かさないこと**（同日 n<10 の数字で2回動かし、
     2回とも戻した）。

     **重大な制約（2026-09-06 判明・2026-09-11 実装で解決）: 誤統合はこの設計では監査できなかった。**
     機械が「統合する」と判定したクラスタは「確認済を反映」で alias が適用され、
     表記が1つになって `merge-candidates.json` から消えるため、**人がレビュー画面で
     確認する前に視界から消えていた**（実測で merge 層の標本48件は1件も画面に出なかった）。
     さらに `apply-auto-merges.mjs`（自動OKクラスタを一括適用する別スクリプト）は
     判断台帳を一切参照・記録していなかったため、そちら経由の統合は監査の母集団に
     一度も入らなかった。**2026-09-11 に実装で解決**:
     - 抜き取り監査の母集団を「台帳に記録済みのもの」（＝既に適用済みで手遅れ）から
       「`merge-candidates.json` 上でいま自動OKと判定されていて、まだ台帳に記録が無いもの」
       （＝これから適用されようとしているもの）に変更（`audit-review-sample.mjs --draw`）。
     - `scripts/lib/review-ledger.mjs` に `heldAuditKeys()` を追加。抜き取り監査で引かれたが
       まだ人が判断していないクラスタのキー集合を返す。
     - `apply-auto-merges.mjs` を改修: 独自実装だった判定ロジックを
       `scripts/lib/team-grouping.mjs`（レビュー画面・監査と共通）に差し替え、
       `heldAuditKeys()` で監査保留中のクラスタを適用対象から除外し、
       適用したクラスタは判断台帳へ `decidedBy:"auto"` として記録するようにした。
       あわせて、台帳に既に人の判断（別チーム、等）があるクラスタを機械の判定だけで
       無条件に上書き適用していた別バグも見つけて直した（改修前はそもそも台帳を
       見ていなかったための欠落）。
     - 動作確認はまず scratchpad の合成データで実施

     `st()`は`state[k]`が未キャッシュのときだけ台帳から初期値を作るため、**一度でも
     `localStorage`にキーが乗ると、以後リポジトリ側の台帳がどう更新されても参照されない**。
     「確認済を反映」は`buildOutput()`が**画面に読み込まれている全クラスタを毎回無条件で
     再送信する**設計のため、古いキャッシュが残ったブラウザで押すと、他の誰か・他のセッションが

     ある1件だけを確認しようとした操作で、無関係な41件の`decidedBy`が巻き戻った

     `git checkout`で復元・`team-name-aliases.json`自体への実害は無かった）。

     不変条件**として直した。古いタブ・古いキャッシュからの送信も同じ経路を通るので、
     画面側だけ直しても防げないため。
     1. **中身が同じ再送信は記録しない**（`verdict`・`groups`・`canon`・`merges` が一致すれば無視）。
        `auto` → `human` の昇格（人が見て同意した）だけは反映する。
     2. **`human` → `auto` の巻き戻しを拒否する**。中身が違ううえに `decidedBy` を下げる更新も拒否する。

     この修正のきっかけで、**`revisions` と `decidedAt` が最初から汚染されていた**ことも判明した。
     「確認済を反映」は画面上の全件を毎回再送信するため、1件だけ直した操作で 358件の
     `revisions` が一斉に +1 される。実際、台帳には `revisions:25` が264件並んでいた
     （人が25回判断し直したのではなく、ボタンが25回押されただけ）。

     今後は上記1により、触っていないクラスタの値は動かない。

     補正が走り、`reviewed` が false に巻き戻されていた。補正を state 初期化時にだけ適用する

   - 進み具合は `data/teams/review-history.json` に時系列で残る

   - **候補とチームマスタのIDは必ず揃えること**（2026-09-06 追加）。

### alias の大会スコープ `scope`（2026-08-12 追加 / [ADR-013](../adr/ADR-013-scoped-team-name-aliases.md)）

alias 表はもともと**文脈を持たない**ため、`--scope=all` で全大会へ流すと壊れるエントリがあった。
そこでエントリに任意の `scope` を持たせ、その大会文脈でだけ適用できるようにした。

```json
{ "canonical": "昇陽中学校", "aliases": ["昇陽"],
  "scope": { "tournamentPrefix": ["secondaryschool-", "zennihon-secondaryschool"] } }
```

- `scope.generation`: 大会の `generationId` が含まれるときだけ適用
- `scope.tournamentPrefix`: 大会IDがいずれかで始まるときだけ適用
- `scope.prefecture`: **参加者の都道府県**が含まれるときだけ適用（他の2つと違い参加者単位で効く）
- 複数あれば AND。**`scope` 無しは従来どおり全大会に適用**（後方互換）
- 同じ別名を別 canonical へ割り当てるのは**双方が `scope` を持つ場合のみ**許可。
  解決時は `scope` 付きを先に評価する
- **`scope` の付け忘れは、付け忘れた時点では検出できない。** 判定材料は「素の略称が中学以外の
  大会に実在するか」なので、**まだその大会データを取り込んでいなければ何も引っかからない**。
  2026-08-12 の一括対応で `下吉田` `九度山` `余目` には `generation: ["junior"]` が付いたのに
  `吉田` `増田` `三国` に付かなかったのはこれが理由で、**2026-09-01 にインターハイ2016/2017を
  取り込んだ瞬間、新潟県の高校「吉田」が山梨県の「吉田中学校」へ書き換わった**
  （秋田県「増田」・福井県「三国」も同様。いずれも `--scope=all` 実行で6レコード）。
  → **新しい年度・カテゴリを取り込んだら `normalize-team-names.mjs --scope=all` の差分を
  必ず目視すること。** 中学校名・小学校名へ寄る改名が高校/一般の大会ファイルに現れたら、
  ほぼ確実に `scope` の付け忘れ。2026-09-01 時点で `scope` 無しの中学校 alias は107件残っており、
  同名の高校が入るたびに同じことが起こりうる（現時点で誤爆しているものは0件）。
- `normalize-team-names.mjs`（`scopeMatches`）と `check-identity-health.mjs`（`scopedAliasLeft`）は
  **必ず同じ規約で解釈する**。`teamCore()` と同じく、片方だけ変えると過少/過大報告になる

**2026-09-05 に18件目が出た**（`春日部クラブ ← 春日部`／埼玉）。`春日部クラブ` は社会人クラブ
（全日本実業団・東日本・全日本ミックス over35 にしか出ない）だが、素の `春日部` は
**インターハイ2012 男子ダブルス・埼玉県**に2件あり、`--scope=all` で高校がクラブ名に書き換わった。
`generation: ["all", "corporate", "masters"]` を付けて解決。**社会人クラブの略称も
このパターンに入る**（中学・小学だけの話ではない）。なお当該インターハイの `春日部` が
どの高校かは確定できず、素の表記のまま残している（→ [open-questions](./open-questions.md)）。
検出は**差分の `"team"` 値を集計し、増えた側に 中学/クラブ/高校 の接尾辞が付いたものを見る**方法。

`scope` が必要になるのは次の3パターン（2026-08-12 時点で 30件）:

1. **中学・クラブの文脈でだけ正しい略称**（17件 / 2026-09-05 に `春日部` が加わり18件）。`日高` はインターハイ・和歌山県にも
   出場があり（＝和歌山県立日高高校）、無条件に `日高中学校` へ寄せると高校が壊れる。
   同型に `柏崎`（→柏崎ジュニア）`名寄` `阿波` `甲府西` など。`generation: ["junior"]` で限定する
2. **中高一貫校**（7校）。`昇陽` `京都光華` `就実` `明徳義塾` `明豊` `昭和学院` `札幌大谷` は、
   **素の略称が高校側の canonical でありながら、中学の大会に出るときは中学校を指す**。
   ただし `zennihon-junior`（全日本ジュニア）での出場はすべて u17/u20 で高校生なので、
   `generation: ["junior"]` では足りず `tournamentPrefix` で中学校の大会に限定する
3. **同名の別団体が他県にもある**（3件）。`朝日`（愛知＝朝日中学校／兵庫・長野は別団体）、
   `野木`（栃木）。`野木` に至っては**大会の系統で指すものが変わる**（中学校大会→`野木中学校`、
   小学生大会→`野木クラブ`）ため、`tournamentPrefix` × `prefecture` の組み合わせで2エントリに分けた。
   判定根拠は**選手名の突き合わせ**（素の略称の選手が、どちらの団体の顔ぶれと一致するか）

**運用上の注意**: 素の略称を alias にするときは、**その名前が他の generation に出現しないかを必ず確認する**。
確認は `data/tournaments/details/**` の `participants[].team` を `index.json` / `local_index.json` の
`generationId` で集計すればよい。誤ると静かに誤変換される。

`apply-auto-merges.mjs` は `scope` を出力しないため、自動マージが作ったエントリは人手確認が要る。
2026-08-12 の作業では自動マージが `野木中学校 ← 野木STC`（地域クラブを学校へ統合）と
`府中STC ← 府中クラブ`（本ページに「意図的に統合していない」と明記済み）を作ったため巻き戻した。
また canonical が最頻出＝略称になる問題により**77件を正式名称へ反転**した（`名寄`→`名寄中学校` 等）。

### カテゴリ横断の落とし穴: 棚卸しの母集団を「専用大会」にしない（2026-08-14）

大学のチーム名を整理したとき、**大学専用大会（`zennihon-university*`）だけを母集団にして
棚卸しし、取りこぼした**。大学生は一般大会（全日本選手権・全日本シングルス・東日本・西日本・
国際予選）にも出るので、大学名は大学大会の外にも現れる。
`teams.json` を再生成して初めて `神松蔭大学` `神戸松蔭学院大` `立教大` `石川工業高専` が見つかった。

**棚卸しの母集団は「そのカテゴリの所属として現れる全出場」にする。**
大学なら `participants[].prefecture` が `日本学連` / `学連` になるのでこれで拾える。
適用後に `build-team-master.mjs` を回して**もう一度点検する**手順も必須。

括弧除去・語尾除去といった通常の正規化では別キーのまま残り、表記ゆれとして検出されない**
（`岡大学` ← 福岡大学）。「他のチーム名の末尾一致／先頭一致の断片になっている名前」を
探すと拾える。確定は**同一選手が他の年に正準名で出場しているか**の突き合わせで行う
（名前の一意性だけでは `西大学` を `城西大学` と `関西大学` のどちらにも寄せられてしまう）。

### 略称そのものが高校と大学で衝突する（2026-09-09 追加）

`scope` が要る3パターンは**alias 表に載る略称**の話だったが、**チームマスタの canonical
そのものが衝突する**型もある。`data/teams/teams.json` の `kitakadai` は `name: "北科大"`
（＝北海道科学大学高校）だが、**北海道科学大学（大学）も現場では「北科大」と書かれる**。

インカレ2026 男子ダブルスの4選手が `team: "北科大"` で入っていたため、
高校パイプラインが**大学の出場を高校（北科大高）の実績として集計していた**
（`prefecture` が `日本学連` でも高校側に寄る）。2026-09-09 に大学側を
`北海道科学大学` に直して解消（`data/highschool/prefecture-summary.json` から
該当2ペア・4選手が落ち、`kitakadai` の `totalAppearances` 63→61 / `uniquePlayers` 56→52）。

- **alias 表では防げない**。素の表記がマスタの canonical と完全一致するので、
  alias の `scope` を付ける機会がそもそも無い
- 対処は**大学側を正式名称で入れる**こと（略称のほうを直さない）。
  高校側の canonical を変えると高校大会の全データが影響を受ける
- 全数確認: `北科大` の残りの出現（`east-japan` 2025 / `zennihon-championship` 2019）は
  いずれも `prefecture: "北海道"` の高校生の出場で、誤帰属ではない
- **同型を探すときの目安**: 大学のチーム名は `participants[].prefecture` が

## 姓名の分割ゆれ `data/players/name-split-aliases.json`（2026-08-29 追加）

チーム名とは別に、**姓と名の切り位置**もぶれる。大会 PDF では氏名が 1 つの文字列として
現れることが多く、境目は推定するしかないため、取り込みバッチごとに `谷|明日里` と
`谷明|日里` のように割れる。

**なぜ実害があるか**: 選手 id の解決は `姓::名` の完全一致
（`lib/playersIndex.ts` の `getPlayerNameToId`）。分割がぶれると 1 人の戦績が 2 つの id に割れ、
`count>=5`（結果ページ生成の閾値）を**両方とも下回って結果ページが消える**。
2026-08-29 の全数調査では衝突 147 件のうち両方が `count>=5` だったものは 0 件で、
壊れ方は「2 ページに分裂」ではなく「片方が沈む」だった。141 件を直した結果、
`count` が 5 を跨いで結果ページが新規に立つ選手が 35 名出た。

### 運用（チーム名寄せと同じ形）

1. **検出** `scripts/check-name-splits.mjs`（`temp/` は除外）。**`prebuild` のゲート**
   （`--strict` 付き）。検出器は 3 つあり、取りこぼす理由がそれぞれ違う。
   - **A 分割衝突**: 同じ氏名が 2 通りの切り方でデータに同居している。確実だが
     **2 通り無ければ気づけない**。1 シリーズの大会にしか出ない氏名が全体の **64%**
     （23,889 中 15,214）あり、そこに紛れた誤りは原理的に見つからない。
   - **B 辞書照合**: 現在の切り方の片側がコーパスに 1 例も無く、かつ**別の切り位置なら
     姓・名の両方に実例がある**氏名を挙げる。**1 度しか出ない氏名にも効く**ので、
     新しい大会を取り込んだ直後の点検はこちらが主役。ヒューリスティックなので
     `--strict` のときだけ終了コードに影響する。
     見て正しかったものは表の `verified` に足すと消える。
   - **C 既知の誤分割の再混入**: 表で `aliases`（＝誤り）と決めた綴りがデータに入っている。
     **A も B も「人が判断済みの氏名」は見ない**ので、一度直した誤りが取り込みで 1 件だけ
     戻ってきた状態は、C が無いと**誰も検出できない**。ゲート化の前に実際に退行を注入して
     試したところ A も B も素通りしたので追加した。人が誤りと断定済みの綴りなので常にエラー。
2. **判断**（人手）→ `data/players/name-split-aliases.json` に
   `{ canonical: [姓, 名], aliases: [[誤った姓, 誤った名], …], reason }` として蓄積する。
3. **適用** `scripts/normalize-name-splits.mjs`（冪等・`--dry-run` 可）:
   `participants[].lastName` / `firstName` / `id` と、それを参照する
   `playerIds` / `pair` を書き換える。`normalize-team-names.mjs` と同じくテキストへ
   ピンポイント置換して整形を壊さない。`lastName` と `firstName` は**隣接ペアとして
   まとめてマッチ**させる（姓だけ一致する別人への誤爆を構造的に防ぐ）。
   続けて `data/players/index.json` の **該当氏名の `count` だけ**を数え直し、
   `count>=5`（結果ページの有無）を跨いだ選手を報告する。

辞書は `data/tournaments/details` の `participants` からだけ作る。`data/players/index.json` は
誤分割側の行が `count: 0` で残るため、辞書に混ぜると誤りを正例として学習してしまう。

**裏づけが 1 件しかない別解は、その 1 件自体が壊れていないかを確かめる。** 実例: 正しい
`林|楓恋` が「別解 `林楓|恋` の姓が 1 人実在する」として疑われたが、その 1 人の正体は
**同じ誤りの別レコード**（ペアの境界ずれ）だった。壊れたデータは自分の誤りの裏づけを作る。

### 表で扱えない型: ペアの境界ずれ

`林楓|恋荒` ＋ `川|琴美` → `林|楓恋` ＋ `荒川|琴美` のように、**ダブルスのペア 2 人の氏名の
境目**がずれることがある。alias 表は「連結後の氏名は正しく、切り位置だけが違う」ことを前提に
`誤った姓+誤った名 === 正しい姓+正しい名` を検証しているため、この型は表では表現できない
（連結文字列そのものが人ごとに変わる）。一回限りの修復スクリプトで直す
（例: `scripts/fix-versus-2024-name-boundary.mjs`）。
**検出器 A / B のどちらにも掛からない**ので、他に同じ型が残っているかは分かっていない。

**判断をやり直すとき**は、表の `canonical` と `aliases` を**入れ替えて**再実行すればよい。
現データの綴りが alias 側になるので、逆方向へ書き戻される。
確定済みの判断は `scripts/check-name-splits.mjs --list` で1行ずつ見直せる。

### 判断の物差し（多数決は使えない）

- **多数決は誤る**。2026-08-29 の 141 件のうち **12 件は多数派のほうが誤り**だった。
  1 回の取り込みが 10 ファイルに分かれると件数は簡単に水増しされるため。
- 見るのは**出典の系列数**（別の大会シリーズがいくつ支持しているか）。
  例: `谷|明日里` は 6 系列、`谷明|日里` は `zennihon-university` のみ。
- **姓の頻度・名の頻度は単独では逆の結論を出す**。境目を右にずらした誤りは
  「存在しない姓＋よくある短い名」（`森優|士郎`）を、左にずらした誤りは
  「よくある姓＋存在しない名」（`小野|寺結`）を作る。必ず両方を見る。
  2026-08-29 の確定 141 件でも、姓が他に無い型が 72%・名が他に無い型が 64% と**両方向に出た**
  （片側だけ見ると 3 割前後を取りこぼす）。ただし「姓も名も他に無い」だけを条件にすると
  ローマ字表記の外国人選手が大量に当たる（1,134 件）ので、**別解が存在するか**まで見て絞る。
- いちばん強いのは**別人による姓の裏づけ**（`小津和|悠` は別人の `小津和|翔` が支える）。
  次に「もう一方が日本語の氏名として成立しない」こと（踊り字始まりの `々花`、
  カタカナ・かなの途中切り `ャン瑠加` `こ|ころ` 等）。

### 注意

- **`data/players/index.json` を `extract-players.mjs` で丸ごと再生成しない**。
  同スクリプトは既存行を消さず、閾値未満の名前も既定（`minOccur=1`）で新規採番するため、
  現データにあって index に無い名前を一気に採番してしまう。
  対象は**増え続けている**ので、取り込みが進むほど誤爆の規模が大きくなる。

  | 時点 | 一括採番されてしまう人数 |
  |---|---|
  | 2026-08-29 | 5,523 |
  | 2026-09-11（インカレ2022取り込み後）| **11,618**（18,543 → 30,161 行）|

  `normalize-name-splits.mjs` が**該当する名前の `count` だけ**を更新するので、そちらを使う。
  誤分割側の行は `count: 0` で残るが、`count>=5` でしか参照されないので無害。
- **分割を直したとき、index の行は「改名」でよい**（2026-09-11 追加）。
  `normalize-name-splits.mjs` は `count` しか触らないため、
  誤分割の行（例 `磯美|咲希`）が残り、正しい分割（`磯|美咲希`）の行は存在しないままになる。
  正しい分割の行が**まだ無ければ**、誤分割の行の `lastName` / `firstName` を書き換えて
  `count` を実データで数え直すのが素直（**id を保てる**）。
  正しい分割の行が**既にある**なら改名すると重複するので、誤分割の行は消すか `count: 0` で残す。
  どちらにせよ**行単位の手編集**で足り、`extract-players.mjs` を回す理由にはならない。
  1行1エントリの整形を崩さないよう、JSON を読み書きし直すのではなく**文字列置換**で直すこと。
- `data/tournaments/details/**/highschool-*` を書き換えたら
  `npm run highschool:pipeline` の再実行が要る（`data/highschool/**` の `playerIds` にも
  誤分割 id が焼き込まれている）。
- `data/tournaments/details/**/temp/` は取り込み途中の作業ファイルなので対象外。
  再取り込みしたら `normalize-name-splits.mjs` を流し直す。
- 分割を直すと**2 人が 1 つの id に統合されてしまう**ことがある（同姓同名で所属が繋がらない場合）。
  切り位置の正しさと同一人物かどうかは別問題なので、疑わしいものは直さずに保留し、
  [open-questions.md](./open-questions.md) に残す。

## 選手の登録名変更（改名）— 設計のみ・未実装（2026-08-31）

同一人物が**登録名そのものを変えている**ケース。姓名の分割ゆれ（切り位置）とも
同姓同名（別人）とも別の軸で、既存の3つの仕組みではどれも扱えない。

| 既存 | 何をするか | なぜ使えないか |
|---|---|---|
| `homonyms.json` | 同姓同名の**別人**を記録 | 逆方向 |
| `name-split-aliases.json` | 姓名の**切り位置**ゆれ | 適用側が「alias姓+alias名 === canonical姓+canonical名」を assert するため、**文字が変わる改名は原理的に通せない** |
| `team-name-aliases.json` | チーム名の改称・略称 | チーム専用 |

実例: 高田商（奈良）の `林 湧太郎`（2017・2018 のインターハイ2件）と NTT西日本（広島）の
`林 佑太郎`（2022〜2026 の22件）が同一人物。現行の登録名は `佑太郎` 側で、
`data/players/index.json` に `林|湧太郎` は存在せず、高校時代の2件がどの選手ページにも
紐づいていない。統合すると `count` 22 → 24 でキャリア年表が高校→実業団で繋がる。

**決めたこと（2026-08-31・未実装）**:

1. 対応表 `data/players/player-name-aliases.json` を新設し、**`scope` を必須にする**
   （`team` / `prefecture` / 年レンジ）。チーム名 alias（[ADR-013](../adr/ADR-013-scoped-team-name-aliases.md)）では
   `scope` は任意だが、人名は「別の場所に居る同名の別人」に当たる確率が高く、無条件適用は
   `homonyms.json` が防ごうとしている誤マージを自分で作ることになるため。
2. **アプリ層（id 解決）でのマージではなく、データ本体を書き換える。**
   姓名の完全一致で人を引く箇所が独立に5系統ある（`participants[].id` / `index.json` の数値 id /
   `playerKey` / 進路照合（[ADR-014](../adr/ADR-014-pathway-name-match.md)）/ story 照合）ため、
   1箇所直しても残りが割れたままになる。チーム名・姓名分割と同じ形に揃える。
   「人物別 id の払い出し」は 2026-07-26 に見送り済みで、その判断は動かさない。
3. **正準は現行の登録名（＝改名後）に寄せる**。旧名は alias 表に残る。ただし公開面では
   旧登録名を併記する（`information.json` の `formerNames`。curated 選手に改名が出てきたときに効く）。

**検出は自動化できない**（このケースは同音異字＋所属・県・年がすべて変わっており、
`homonyms.json` の検出器 D/E/F はいずれも原理的に引っかからない。読み仮名データも無い）。
一次ソースは人の知識で、対応表の価値は「見つける」ことではなく
**一度分かった判断を失わずに全系統へ効かせる**ことにある。

## 選手の別人判定 `data/players/homonyms.json`

- 基本は氏名ベース id（`data/players/index.json`、team非依存）。同姓同名の別人だけ分割する。
- 生成: `scripts/build-player-homonyms.py`。
- **別人とみなす根拠**（検出器3つ。いずれか1つでも成立すれば登録する）:
  - **D**: 同一年に「**非隣接の学校段階**」（小↔高 / 小↔大 / 中↔大 / 高↔成 等＝物理的に不可能）が
    共存する。隣接段階（中3→高1 等の卒業境界）は同一人物として除外。
  - **E**（2026-07-26 追加）: **出生年の許容レンジが交差しない**。`generationId` ＋ `categoryId` の
    age 部から 1 観測ごとにレンジを引き、全観測の積集合が空なら別人。D が「同一年」しか見ないため
    取りこぼしていた (a) 年をまたぐ矛盾 (b) `cat()` が `None` を返す大会（`zennihon-championship` /
    `east-japan` 等）(c) `overNN` のマスターズ区分 を拾う。レンジは**わざと広め**に取る
    （広い＝矛盾しにくい＝過小検出側）。
  - **F**（2026-07-26 追加）: **同一大会・同一年に異なる都道府県で出現**する。1 人が同じ大会で
    2 県を代表することは不可能。世代が同じで E に掛からない同姓同名を捕まえる唯一の信号。
    所属校名は略称ゆれがあるため**県のみ**で判定する（`学連` / `高体連` 等は県ではないので除外）。
  - どの検出器が発火したかは各レコードの `detectors` フィールドに残る。
  - 人物への割り当て（`persons`）も D/E/F の衝突判定を使う。別人確定なのに 1 人にまとまって
    しまった場合は `needsReview: true` になる。
  - 名（`firstName`）が空の participant は「姓だけの一致」であり根拠にならないため除外し、
    データ側の氏名分割の不備として別途報告する。
- **識別キーはチーム**: 1人＝氏名＋その人のチーム集合。参加者は `(氏名, チーム)` で person に解決。
  割り当ては「同一チーム／共通の相棒（ダブルスペア）／段階進行」で同一人物へ寄せ、衝突は別人。
- 中間段階の所属が曖昧・3人以上等は `needsReview: true`。~~2026-06 時点で確実な別人 **16名**を登録。~~
  **2026-07-26 に E / F を追加して再生成し 65 名**（明快 43 / 要確認 22）。既存 16 名の退行はなし。
- 限界: **同じ学校に別々の年に在籍した同姓同名**（同年に重ならない）は段階もチームも同じため
  自動では分けられず、1人に残る。

### 実測（2026-07-26）: 登録 16 名は実態の 17% にすぎない

検出条件を広げて全データ（`data/tournaments/details` 455 ファイル）を走査したところ、
**別人であることが証明できる同姓同名が 70 名**見つかった。`homonyms.json` の 16 名でカバーできて
いるのは 12 名で、**カバー率 17%・未登録 58 名**。

| 検出器 | 根拠 | 件数 |
|---|---|---|
| 既存 D（同一年 × 非隣接段階） | `build-player-homonyms.py` と同条件 | 0（＝既に登録済み） |
| **E: 出生年レンジ矛盾** | `generationId` ＋ `categoryId` の age 部から出生年の許容レンジを引き、積集合が空なら別人 | 33（うち未登録 21） |
| **F: 同一大会 × 異なる都道府県** | 1 人が同じ大会・同じ年に 2 県を代表することは不可能 | 37（すべて未登録） |
| **合計（重複除く）** | | **70（未登録 58）** |

**なぜ既存の D が 0 と報告していたか**: D の判定は「**同一年** かつ 段階 ORD 差 2 以上」に限定されて
いた（`check-identity-health.mjs` チェックD）。このため (a) 年をまたぐ矛盾、(b) `catOf()` が `null` を
返す大会（`zennihon-championship` / `east-japan` / `zennihon-mixed` 等）、(c) `overNN` のマスターズ
区分、がすべて対象外だった。都道府県シグナルもチーム側にしか使われていなかった。
**物差しが無かったのではなく、物差しの感度が足りず 0 と出ていた**。

E / F は `check-identity-health.mjs` に実装済み（2026-07-26）。測定の手順・生データ・
機能別の誤マッチ率は [raw/2026-07-26-homonym-measurement.md](../raw/2026-07-26-homonym-measurement.md)。

**対応済み（2026-07-26）**: 検出器 E / F を `build-player-homonyms.py` と
`check-identity-health.mjs` の両方に実装し、`homonyms.json` を **16 名 → 65 名**に再生成した
（既存 16 名の退行なし）。これにより `PlayerStatisticsSections.tsx` の警告
「※ 同姓同名の別選手の成績が含まれている可能性があります。」が出るページが
**12 → 39** に増えた（index 対象は 5）。ヘルスチェックの同姓同名シグナルは 3 つとも 0 になった。
なお `homonyms.json` への登録は**警告表示が正しく出るようになる**だけで、id の分割ではない
（下記「既知の残課題」参照）。

**この 70 名は下限**。E は世代が違うことを、F は県が違うことを信号にしているため、
**同世代かつ同一都道府県の同姓同名**（高校生 2 人が同じ名前で同じ県）は 3 つとも原理的に検出できない。
F が「両者が同じ大会に同時出場している」ことを要求する点でも取りこぼしが大きく、実数はこれより
確実に多い。

**影響**: `data/players/index.json` は **18,543 名前 = 18,543 id** で、同姓同名に別 id が 1 つも
割り当てられていない。つまり検出した 70 名は全員 **1 つの選手ページに複数人の戦績が融合**している。
うち 61 名が id を持ち、**37 名は結果ページが生成済み**、**4 名は `totalMatches >= 15` で
index 対象**（[seo.md](./seo.md) #2）。`homonyms.json` への登録は「危険な名前の記録」であって
id の分割ではない点に注意（残課題の「アプリの選手解決へ統合する実装」がそれに当たる）。

```
npm run playerstats:facts                       # .playerstats/_facts の再生成（キャリア年表の元データ）
node scripts/check-identity-health.mjs          # 未対応項目のヘルスチェック
```

**`normalize-team-names` → `build-team-master` の順序は必須**（逆順・片方だけの実行は表示名が
alias 側に振れる）。また `.playerstats/_facts/**` は選手ページのキャリア年表・所属推移の元データで、
チーム名を焼き込んでいるため、名寄せ後は再生成しないと**画面上は分裂したまま**になる
（`prebuild` でも生成されるが、ローカル確認時は明示的に実行すること）。

## 運用: 対応忘れを防ぐヘルスチェック

`scripts/check-identity-health.mjs` が、人手対応が必要な未処理項目を1か所に件数つきで一覧する
（問題があれば終了コード 1。CI・定期実行のゲートに使える）。**新データ取り込み後に必ず実行**する。
検出項目と対応:

- 未解決の県値 → `normalize-prefectures.mjs` の明示マップに追加、または列ずれ破損レコードを手動修復。
- playerIds 参照切れ / id 重複 → 該当レコードを手動修復。
- 別名のまま残る出場 → `normalize-team-names.mjs --scope=all` を実行。
- 未統合候補（機械は自動OK可と判定）→ `npm run team:review` で人が判断する
  （2026-09-12: 自動統合は廃止。`apply-auto-merges.mjs` は人の判断を反映するだけになった）。
- 要人手レビュー候補（同一大会同居等）→ レビューHTMLで同一/別を判断。
- **未統合候補（選手共有・同年共起2名以上）**（2026-09-05 追加）→ レビューHTMLで同一/別を判断。
  自動OKには絶対に載らない（[ADR-017](../adr/ADR-017-team-merge-signal-player-overlap.md)）。
- 同名別校の疑い（reviewPrefectures）→ 参考表示。別チームでよければ放置可。
- 未登録の同姓同名（同年×非隣接段階）→ `build-player-homonyms.py` で再生成し確認・登録。
- **未登録の同姓同名（出生年レンジ矛盾）**（2026-07-26 追加）→ 同上。`generationId` ＋ `categoryId` の
  age 部から出生年の許容レンジを引き、積集合が空なら別人。レンジは**わざと広め**に取ってあり
  （過小検出側）、挙がったものは確実に別人。
- **未登録の同姓同名（同一大会 × 異なる都道府県）**（2026-07-26 追加）→ 同上。世代が同じで E に
  掛からない同姓同名を捕まえる唯一の信号。所属校名は略称ゆれがあるため**県のみ**で判定する。
- **名(firstName)が未分割の同姓衝突**（2026-07-26 追加）→ 同姓同名ではなく**取り込み元の氏名分割の
  不備**。D/E/F が姓だけで発火してしまうため別枠にした。該当データの氏名分割を修正する
  （地区大会 PDF 取り込みの `needsReview` 案件と同根）。

なお **姓名の分割ゆれは `check-identity-health.mjs` では検出できない**（同じ人物が別の姓名として
入るので「同姓同名」にも「参照切れ」にもならない）。こちらは `scripts/check-name-splits.mjs` の担当で、
**`--strict` 付きで `prebuild` のゲートに入っている**（2026-08-29）。新データ取り込み後は両方を実行する。

検出できないもの（信号が無い）: 同じ学校に別々の年に在籍した同姓同名。これは外部情報や気づきに依存する。
**内部略称（理大/理科大）は 2026-09-05 に選手共有シグナルで検出できるようになった**が、
**同年に両表記へ出た選手が1人も居ない表記揺れ**は依然どちらのシグナルにも掛からない。**同世代かつ同一都道府県の同姓同名**も D/E/F すべての盲点で、
上記の検出数は常に下限である（実測と限界の詳細は「選手の別人判定」節を参照）。

なお **異体字差は 2026-07 以前は検出できていなかった**（`西鄉第一` がレビューに一度も上がらなかった）。
`kanji-variants.mjs` の対応表に無い字体は今も検出できないので、気づいたら表に追加する。

## 性別判定の部分一致バグ（2026-08-11 修正済み）

`src/utils/team-data-aggregator.ts` はカテゴリID（例: `singles-tournament-girls`）の
文字列から選手の性別を判定する。以前はこれを `category.includes('boys') ||

  の女子選手8名が、アジア競技大会代表予選2025の男子として `aggregateTeamResults` の

- 影響範囲: 全371大会ファイルのカテゴリ文字列を新旧ロジックで総当たり比較し、
  **差分が出たのはこの1ファイルのみ**と確認済み。
- 修正: `parseGenderFromCategory()` を新設し、`category.split('-')` の**最後のセグメントを
  厳密一致**で判定するよう統一（部分一致による事故を構造的に防ぐ）。
  `generateTeamInfo` / `aggregateTeamResults` 内の性別判定2箇所を両方この関数に統一した。

## pid の重複と、チームの年度別メンバー（2026-08-11）

`generateTeamInfo()` の `players` は生の `participant.id`（`姓_名_チーム_都道府県`）をキーに
するが、都道府県サフィックスの有無や所属表記が大会ファイルごとに揺れるため、
**同一人物が複数の pid 変種として重複する**。実測: 日本体育大学は生 pid 249件に対し、
`normalizeJa(姓+名)` で dedup すると 118件（53%減）。

チームページの年度別メンバー（`buildTeamRosterByYearGender()`）はこの正規化キーで dedup する。
併せて注意すべき2点:

- `results[].playerIds` / `matches[].pair` は**エントリー全員**の pid（他チームの相方を含む）。
  必ず `generateTeamInfo().players` の集合で交差を取る（日体大で他チーム pid 38件）。
- 団体戦では pid が選手ではなくチームを指し（`FUJITSU_東京都` 等）、氏名が `null` になる。
  メンバー一覧からは除外する。
- 同一年度・同一チームの本物の同姓同名は dedup で1人に潰れる（`homonyms.json` の
  D/E/F 検出器は個人選手ページ向けで、チームの年度別名簿には適用していない）。
- 詳細: [st-league.md](./st-league.md)「『メンバー』クエリの受け皿」、
  [raw/2026-08-11-teams-tournament-roster-design.md](../raw/2026-08-11-teams-tournament-roster-design.md)

## 表記の欠落（先頭1文字・末尾1文字）の検出と修正（2026-09-12 追加）

PDF取り込みで**名前の一部が落ちたまま公開データに入る**ことがある。表記ゆれと違い、
チームマスタに**別のチームとして実体が登録され**、公開ページにも出るので実害が大きい。
2026-09-12 に15件見つけて直した（経緯: [raw 2026-09-06 追記21・22](../raw/2026-09-06-idea-autonomous-improvement-agent.md)）。

### 見つけ方

1. **PDFと突き合わせる**（唯一確実な方法）。既に公開済みの大会でも、
   `scripts/pdf-to-players/` で抽出し直して既存データと比較すると、取り込み当時の誤りが出てくる。
   全中2024では178エントリー中7件の誤りが公開データ側にあった。
2. **チームマスタの総当たり**（補助）。「ある名前に1文字足すと別の既存チーム名になる」組を探し、
   **同一県**かつ**短い側の出現数が長い側の1/3以下**に絞る（総当たり70件 → 10件）。

**2の走査には原理的な穴がある**: 正しい表記がデータ中に1件も存在しない場合
（`長崎南山中学校` など5件）は対にならず、絶対に出てこない。走査だけを信用しないこと。

### 裏の取り方

次のいずれかが取れたものだけ直す。

- 同じ選手が両表記で登場する（最も強い）
- 同一ファイル（同じ大会・同じ年）に両表記が並ぶ
- 正しい表記がデータ中に1件も無く、短い方が名前として成立しない

**確証が無いものは直さない。** 2026-09-12 時点の保留:

- `市立柏`(2件) ↔ `柏市立柏`(14件) — **柏市立柏高校の正当な略称**でありうる。選手の重なりも無い
- `出雲JST`(28件) ↔ `東出雲JST`(4件) — 短い側の方が多く、出雲市と東出雲町で**別クラブ**の可能性

### alias表自体が誤りを固定していることがある

`広島大曲中学校`（先頭の「北」が落ちた誤り）が canonical になっており、さらに別エントリで
`北広島大曲中 ← 北広島大曲中学校`（正式名称を略称へ寄せる）があった。**同じ学校が3つの名前に
割れていた。** 誤った表記を見つけたら、alias表に正準名として登録されていないかも必ず確認する。

### 修正後に走らせるもの

[実行順序（フル再構築）](#実行順序フル再構築)に従う。特に次の2つを忘れないこと。

- `npm run playerstats:facts` — チーム名を焼き込んでいるので、再生成しないと選手ページが分裂したまま
- `npm run secondaryschool:build` — **pykakasi（Python）が必要**。素の `python3` では
  `ModuleNotFoundError` で落ちる。`PATH="$PWD/.venv/bin:$PATH" npm run -s secondaryschool:build` で通る。
  新しいチーム名のローマ字IDを作るときだけ呼ばれるので、名寄せ直後は必ず踏む

## 既定グループ分けの規則（2026-09-12 改定）

**名前から読める段階を、出場大会のジャンルより優先する**（`level(name) ?? memGenre(member, context)`）。

改定の根拠は実測。機械だけで決めた統合49件から20件を無作為抽出して人が点検したところ、
**誤統合が11件（55.0%・95%区間 34.2〜74.2%）**あった。原因は段階を
`memGenre(出場大会のジャンル) ?? level(名前)` の順で決めていたことで、
`仙北STC` が「中学の大会にしか出ていない」という理由で段階「中」と判定され、
中学校と同じグループに入りうる状態だった。名前は**その団体が何と名乗っているか**そのものなので、
出場大会からの推定より強い証拠として扱う。

人が示した規則（2026-09-12）:

- **小学・中学・高校は同時に発生しない。** 段階が違えば必ず別チーム
- **「学校」と付く名前と、クラブ・STC などのクラブチームは別**
- 正式名称と略称（`長岡商業` ↔ `長岡商業高校`、`式下中` ↔ `式下中学校`）は同一でよい

この20件の判断は `scripts/lib/team-grouping.test.mjs` に固定してあり、CI のゲートで回る。
規則を変えるときはこのテストを先に更新すること。

### 誤って適用した統合を戻す（`scripts/undo-team-merge.mjs`）

統合は alias を当ててデータ本体の表記を書き換えるため、**元の名前は現在のデータに残らない**。
ただし **git 履歴から統合直前のコミットを引けば復元できる**
（2026-09-11 に「統合済みのものは遡って検証できない」と書いたが、これは訂正）。

戻すときは次の3つを必ず揃える。どれか1つでも欠けると元に戻らないか、再発する。

1. details の表記を戻す（id ごと置換すれば `playerIds`・`matches` の参照も直る）
2. alias 表から該当の別名を外す（残すと次の `normalize-team-names` で再統合される）
3. 判断台帳へ `decidedBy:"human"` / `verdict:"separate"` と記録する（残すと機械が再び提案する）

落とし穴:

- **`git log -S` は引用符込み（`"南方"`）で引くこと。** 素の `南方` では `南方JST` の中にも当たり、
  別の名前が変化したコミットを掴む
- **台帳の記録とデータの実態はずれうる。** 2026-09-12 の修復では18クラスタ中3件
  （杉戸・清武・甲賀）が既に正しいクラブ名へ移っており、データ修復は不要で台帳にだけ古い記録が残っていた
