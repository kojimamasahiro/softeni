# 回遊検証ランブック（GA4 / AdSense）

回遊施策（着地したユーザーに「次の1クリック」を作る施策）が**実際に効いたか**を判定するための
手順書。**このページ単体で、当時の文脈を覚えていなくても実行できる**ことを目的に書いている。
[高校SEO M4検証ランブック](./highschool-seo-m4-verification.md) の回遊版であり、構成を意図的に揃えている。

背景と最初の施策候補は
[raw/2026-08-15-idea-highschool-school-page-cross-links.md](../raw/2026-08-15-idea-highschool-school-page-cross-links.md)。

## なぜランブックが要るのか

SEO には GSC という共通の物差しがあり、施策の合否を後から答え合わせできた（M4検証）。
**回遊にはそれが無い。** GA4 は導入済みだが、同意率も、着地ページ別の次クリックも、
一度も読まれたことがない。この状態で内部リンクを数千本足しても、効いたか効かなかったかを
判定できず、採択も棄却もできない。**施策より先にこのランブックを整える**のはそのため。

## 目的（KPIの上位概念）

**PV増＝AdSense収益**（2026-08-15 決定）。したがって最終判定は「回遊が増えたか」ではなく
**「収益が増えたか」**で行う。回遊はその手段であり、増えたPVの単価が落ちれば収益は増えない
（詳細は手順3の注意）。

## 計測を難しくしている3つの前提（先に把握しておくこと）

### 1. 同意がデフォルト拒否で、同意率が未計測

`src/pages/_app.tsx` は Consent Mode v2 を正しく実装している（`consent default` は
`analytics_storage: 'denied'`、`wait_for_update: 500`、再訪ユーザーは初回 page_view より前に
localStorage から復元）。実装の質は問題ない。**問題は、同意したか拒否したかを一切送っていない**こと。

- 未同意状態でも GA4 には cookieless ping が届くので、**イベント（`page_view` を含む）は計上される**。
- ただし `_ga` cookie が無いため **client_id が固定されず、ユーザー識別とセッション結合が成立しない**。
  未同意ユーザーは分析上「1PV＝1セッション」に近い形で現れる。
- Google の同意モードのモデリングはトラフィック量の要件があり、**当サイトの規模では適用されない
  可能性が高い**（Assumption・GA4 側で「モデリングされたデータ」の表示有無を確認すること）。

**帰結**: 「セッションあたりの表示回数」は、施策と無関係に**同意率が動いただけで上下する**。
セッション系の指標を主指標にしてはいけない。

### 2. 8月は季節ピークで、平常期と比較できない

インターハイ2026の会期最終日は2026-08-07。高校カテゴリの検索需要はこの前後がピークで、
着地ページの構成そのものが平常期と別物になる。M4検証ランブックが「2026年9月末に平常期チェック」を
置いているのと同じ理由で、**回遊のベースラインも平常期に取る**。

### 3. ページ単位では母数が足りない

学校ページ698枚のうち68%は本文リンク10本以下の長いテールで、1枚あたりのセッション数は
ごく小さい。**ページ種別に束ねて見る**こと。束ね方は
[raw/2026-08-15-idea-highschool-school-page-cross-links.md](../raw/2026-08-15-idea-highschool-school-page-cross-links.md)
の実測表と同じ区分を使う（正規表現は手順2に記載）。

## 指標の定義

| 区分 | 指標 | 定義 | 同意の影響 |
|---|---|---|---|
| **主** | モジュールCTR | `internal_link_click`（該当module）のイベント数 ÷ そのページ種別の `page_view` 数 | **受けない**（どちらもイベント数の比） |
| 副1 | セッションあたりの表示回数 | GA4 探索の同名指標。着地ページ種別ごと | 受ける（同意率とセットで読む） |
| 副2 | エンゲージメント率／平均エンゲージメント時間 | GA4 探索の同名指標 | 受ける |
| 副3 | AdSense のページビュー数・ページRPM・推定収益 | AdSense レポート | 受けない |
| 前提 | 同意率 | `consent_accept` ÷（`consent_accept` + `consent_decline`） | — |

**主指標をイベント比に置く**のがこのランブックの肝。セッション結合に依存しないので、
同意率が動いても、季節でトラフィックが動いても、比として読める。

### 対照群を必ず取る

施策は**高校学校ページにだけ**入れる。**選手結果ページ（1,916枚）は触らない**ので、
同じ期間の選手結果ページの数値を対照群として使える。判定は絶対値の増減ではなく

> （学校ページの変化）−（選手結果ページの同期間の変化）

で行う。季節変動・アルゴリズム変動・同意率の変化はおおむね両者に共通で乗るため、差分を取れば消える。
母数が小さくp値で判定できないのはM4と同じなので、**閾値判定＋対照群**で代替する。

> **対照群を汚さないこと（2026-08-23 追記）**
> 手動広告枠（[monetization.md](./monetization.md)「手動広告枠」）の掲載面から
> **選手結果ページは意図的に外してある**。対照群に広告を入れると、そのページの回遊・
> エンゲージメントが施策とは無関係に動き、上の引き算が成立しなくなるため。
> 広告の掲載面を増やすときは、**選手結果ページだけは回遊検証が終わるまで触らない**。
> 逆に、他の4面（選手一覧・大会結果・大会一覧・news展望）への広告投入は、
> このランブックのベースライン取得**より前**に済ませて定常化させておくこと。

## 手順

### 0. 計測の下ごしらえ（(a)(b) はコード実装済み・2026-08-15 / (c) は GA4 画面での作業が未了）

**(a) 同意イベントを送る**（同意率を読めるようにする。これが無いと副1・副2が解釈不能）— **実装済み**

`src/pages/_app.tsx` の `handleAccept` / `handleDecline` から `trackConsentChoice()`
（`lib/analytics.ts`）を呼び、`consent_accept` / `consent_decline` を送っている。
バナー自体は `src/components/CookieConsent.tsx`。**バナーを操作せず離脱したユーザーは
どちらにも計上されない**ので、同意率は「操作した人の中での同意率」であることを記録に明記する。

**(b) 回遊モジュールのクリックイベントを送る**（主指標）— **実装済み**

`lib/analytics.ts` の `attachInternalLinkTracking()` を `_app.tsx` から張り、
**`<main>` 内のリンククリックを委譲リスナー1つで一括計測**している。個々のリンク
コンポーネントには手を入れていないので、**既存の本文内リンクも最初から計測対象**。
これにより、新モジュールが「既存リンクのクリックを食っただけ」なのか「新しいクリックを
生んだ」のかを判別できる（手順4の共食い判定）。

```ts
// 送られるイベント
gtag('event', 'internal_link_click', {
  module: 'same_pref_schools',   // data-link-module 属性の値。無ければ 'unclassified'
  from_type: 'hs_school',        // 出発ページ種別（getPageType が URL から判定）
  to_type: 'hs_school',          // 到達ページ種別
});
```

**新しい回遊モジュールを作るときは、その節の要素に `data-link-module="..."` を1つ付けるだけ**でよい。
付けるまでは `unclassified` にまとまる。ページ種別の判定は `out/` 全4,243 URL で静的解析の分類と
一致（差0件）を確認済みで、回帰テストは `npm run analytics:test`。

**(c) GA4 でカスタムディメンションを登録する**（**未了・画面での作業**）

管理 → データの表示 → カスタム定義 → カスタムディメンションを作成（スコープ: イベント）で
`module` / `from_type` / `to_type` の3つを登録する。

> **登録前に届いたデータは遡って探索で使えない。** 必ず (a)(b) のデプロイ**前か同時**に登録すること。
> ここを忘れると、初回のベースラインを丸ごと取り直すことになる。

### 1-0. デプロイ直後の動作確認（28日待たない・所要5分）

イベントが本当に届いているかは、ベースライン期間に入る**前**に確認する。
ここを飛ばすと「28日待った結果、実は1件も送れていなかった」という最悪の失敗をする。

1. デプロイ後、本番サイトの学校ページを開き、本文内のリンクを1つクリックする
2. GA4 → レポート → **リアルタイム** で `internal_link_click` が出るか見る
   （`module` に `unclassified`、`from_type` に `hs_school` が入っていること）
3. Cookie バナーの「同意する」を押し、`consent_accept` が出るか見る
   （`localStorage` の `cookieConsent` を消せばバナーは再表示される）
4. サイドナビのリンクをクリックし、**イベントが出ない**ことを確認する（`<main>` 内限定の逆チェック）

カスタムディメンションは登録直後は探索に反映されるまで時間がかかることがある。
リアルタイムでイベント名とパラメータが見えていれば計測自体は成立しているので、
探索に出ないだけなら翌日に再確認する。

### 1. ベースライン取得（施策実装より前・平常期）

**ベースラインとは**: 施策を入れる前の「今の回遊の姿」を数字で固定したもの。
回遊には GSC のような外部の基準が無く、他サイトの平均値も当サイトの構造（検索から深いページへ
直接着地する DB サイト）には当てはまらない。**自分の過去だけが唯一の基準**になるので、
施策前に一度記録しておかないと、施策後の数字が良いのか悪いのか永久に言えなくなる。

- **時期**: **2026年9月の連続28日**（例: 9/1〜9/28）。インターハイ2026の会期最終日が8/7で、
  8月は着地ページの構成が平常期と別物になるため8月は使えない。
  M4検証の平常期チェック（2026年9月末）と読む時期を揃えると、GSC と GA4 を一度の作業で済ませられる。
- **逆算**: 9/1 から計測するには**8月中にデプロイを済ませる**必要がある（手順0の実装＋1-0の動作確認まで）。
  ここが間に合わないとベースラインが1か月後ろにずれ、施策の着手も同じだけ遅れる。
- **前提**: 手順0 の (a)(b) はコード実装済み（2026-08-15）。(c) の GA4 カスタムディメンション登録は
  **登録前のデータを遡って参照できない**ので、必ずデプロイ前か同時に済ませること。
- **期間中は対象ページを触らない**。学校ページ・都道府県ページの構成やリンクを変えると、
  ベースライン自体が「途中で定義の変わった数字」になり、比較対象として使えなくなる。
  データ投入（大会結果の追加）は通常運用なので止めなくてよいが、記録に一言残す。
- 手順2・手順3の表を埋めて `docs/raw/` に記録する（手順5）。

**ベースラインを取ったあとの使い道は3つある**（このうち2つは施策前に効く）:

1. **合否判定の基準線**。施策後に同じ表を埋め、対照群との差の差で判定する（手順4）。
2. **施策を打つ価値があるかの事前判定**。手順2-2の経路データ探索で、学校ページから
   **都道府県ページへのクリックがどれだけ発生しているか**が分かる。ここが厚ければ
   「他校を見たい」需要が実在する証拠になり、横リンクは県ページ経由の2クリックを1クリックに
   縮める施策として効く見込みが立つ。逆にほぼゼロなら、そもそも次を求められていないので、
   横リンクを足しても動かない可能性が高く、**施策自体を再検討する材料**になる。
3. **閾値の根拠**。手順4のCTR閾値（5% / 1%）は現状 Assumption で根拠がない。
   ベースラインでは既存の本文内リンクが全て `module: unclassified` として計測されるので、
   **当サイトの本文内リンクの平均CTR**が実測できる。以降は「既存リンクが平均X%だから
   新モジュールはX%を超えれば合格」という自サイト実測の閾値に置き換え、本ランブックの数値を書き換える。

**2 と 3 は施策の前に効く。** ベースラインは「後で比べるためだけの作業」ではない。

### 2. GA4 での読み方（画面操作）

**ページ種別の正規表現**（探索のフィルタに貼る）:

| 種別 | ランディングページの正規表現 |
|---|---|
| 高校学校ページ（施策対象） | `^/highschool/(boys\|girls)/[^/]+/[^/]+/$` |
| 選手結果ページ（**対照群**） | `^/players/[0-9]+/results/$` |
| 大会年度別結果 | `^/tournaments/[^/]+/[^/]+/[0-9]{4}/` |
| 高校 都道府県ページ | `^/highschool/(boys\|girls)/[^/]+/$` |
| 中学チームページ | `^/secondaryschool/[^/]+/[^/]+/$` |
| 大会ハブ | `^/tournaments/[^/]+/[^/]+/$` |

**2-1. 種別ごとの回遊（探索 → 自由形式）**

- ディメンション: 「ランディング ページ + クエリ文字列」
- 指標: 「セッション」「セッションあたりの表示回数」「エンゲージメント率」「平均エンゲージメント時間」
- 上表の正規表現でフィルタを掛け、**種別ごとに1行ずつ**記録する。**学校ページと選手結果ページは必ず両方**取る。

**2-2. 次の1クリック先（探索 → 経路データ探索）**

- 開始点: 「ページパスとスクリーンクラス」＝学校ページ（上の正規表現、または代表的な数枚）
- ステップ+1 に何が並ぶかを記録する。

実測（`out/` の静的解析、2026-08-15）では、学校ページの本文内リンクは中央値7本で、その内訳は
トップ・県・性別・大会一覧の**定型4本＋大会年度別3本**。したがってベースラインの経路は
**県ページと大会年度別結果に強く偏るはず**。施策後にこの偏りが崩れて同種ページ（他校）が
現れるかどうかが、そのまま合否になる。

**2-3. 同意率（レポート → エンゲージメント → イベント）**

`consent_accept` / `consent_decline` のイベント数を記録し、比を出す。

**2-4. モジュールCTR（施策後・探索 → 自由形式）**

- ディメンション: カスタムディメンション `module`
- 指標: イベント数
- 分母にする `page_view` は 2-1 の表示回数、または同じ探索に「ページパス」で並べて取る。

### 3. AdSense での読み方

レポートで**ページビュー数・ページRPM・推定収益**の3つを、GA4 と同じ28日間で記録する。

> **注意（判定を誤りやすい点）**: 回遊で増えるのは**2ページ目以降のPV**で、検索着地ページより
> RPMが低くなりやすい（Assumption・未検証）。**PVが増えてもページRPMが希釈されて収益が横ばい**、
> という結果があり得る。目的は収益なので、**PV・RPM・収益の3つを必ずセットで記録し、
> 最終判定は収益総額で行う**こと。PVだけを見て成功と判定しない。

### 4. 判定基準と次のアクション

初回（ベースライン）は**判定しない**。実測値を基準線として記録するだけ。
2回目以降（施策後）に以下を当てはめる。

| 観測結果 | 判定 | 次のアクション |
|---|---|---|
| モジュールCTR 5%以上 | 成功 | 中学チームページ293枚へ横展開（同じく同種横リンク0本・88%が10本以下） |
| モジュールCTR 1〜5% | 部分的に機能 | 位置・見出し文言・件数を変えて再計測。モジュール自体は残す |
| モジュールCTR 1%未満 | 失敗（見られていない or 動機が無い） | 位置を1段上げて再計測。それでも動かなければ**モジュールを撤去**し、絞り方（強豪上位5校／全列挙）を変えて再検討 |
| CTRは出たが、既存リンクのクリックが同量減った | 共食い | PVは増えていない。手順0(b) を既存リンクにも入れていないと判別できない点に注意 |
| 学校ページの「セッションあたりの表示回数」が上昇、選手結果ページ（対照群）は横ばい | 施策が効いている | AdSense の収益変化を確認して最終判定へ |
| 両方とも同じ方向に動いた | 施策とは無関係（季節・同意率・アルゴリズム） | 差分がゼロなら効果なしと判定する |
| PVは増えたがページRPMが同率で低下し収益が横ばい | 目的未達 | 回遊の量ではなく**着地ページ自体の収益性**へテーマを移す判断材料にする |
| 同意率が前回から10ポイント以上動いた | セッション系の指標が信用できない | 副1・副2は参考値扱いにし、主指標（モジュールCTR）とAdSenseだけで判定する |

**CTRの閾値5%/1%はAssumption（実測に基づかない粗い目安）。** 初回計測でこの水準が現実的か
見直し、必要なら本ランブックの数値を書き換えること。

### 5. 記録（必須）

`docs/raw/YYYY-MM-DD-circulation-review.md` を新規作成して記録する。テンプレ:

```markdown
# 回遊検証 第N回（YYYY-MM-DD）

## 計測期間: YYYY-MM-DD〜YYYY-MM-DD（比較: 前期間 / ベースライン）
## 前提: 同意率 X%（操作した人の中での比率・母数N）、モデリングされたデータの有無
## 種別ごとの回遊（手順2-1）: 学校ページ / 選手結果ページ（対照群）/ その他の表
## 次の1クリック先（手順2-2）: 経路データ探索の上位ステップ
## モジュールCTR（手順2-4）: module別のイベント数 / 分母 / CTR
## AdSense（手順3）: ページビュー数 / ページRPM / 推定収益
## 判定と次のアクション: 手順4の表に当てはめた結論（対照群との差分を明記すること）
## ドキュメント更新箇所:
```

あわせて、判定が出たら
[highschool.md](./highschool.md) の Idea Backlog 行と
[idea-backlog.md](./idea-backlog.md) の一言サマリを更新する。

## このランブックの適用範囲

回遊テーマ全般に使う。最初の対象は高校学校ページの横リンクだが、
中学チームページ293枚（`jhs:team → jhs:team` も0本・88%が本文リンク10本以下）、
大会ハブ127枚、チーム年度ページ306枚も同じ手順で測れる。
**施策を1種別ずつ入れて、他の種別を対照群として使う**進め方を維持すること。
複数種別に同時に入れると対照群が消え、判定できなくなる。
