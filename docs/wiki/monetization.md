#### ハイドレーション不一致（Minified React error #418）との競合（2026-07-05）

`/tournaments/local/` で本番のみ次の2つが連続して発生する事象を確認:

1. `Minified React error #418`（ハイドレーション不一致。React 側がツリーを再生成）
2. 直後に adsbygoogle 側 `Error: no_div`

原因: Auto ads の script を `_document.tsx` に素の `<script async>` として置いていたため、
キャッシュが温まっている等の条件でスクリプトの実行が React のハイドレーション完了より
早くなることがあり、Auto ads が DOM へ広告枠を挿入 → React のハイドレーション対象ツリーと
不一致 → React が該当ツリーを破棄・再生成 → Auto ads 側が挿入済みの div を見失い `no_div`、
という連鎖が起きていたと推定（ローカルでの完全な再現は取れていないため Assumption）。

対応: AdSense script を `_app.tsx` で `next/script` の `strategy="lazyOnload"` に変更し、
ハイドレーション完了後・アイドル時にのみ読み込むようにした。`_document.tsx` からは script
タグを削除済み。

補足:

- 広告枠コンポーネントの網羅確認までは未実施
- 少なくとも AdSense 読込はドキュメント全体で有効化されている

#### 自動広告とサイドバー（AppShell）の競合（2026-06-23）

ADR-006 の2ペイン化（`AppShell`）でヘッダーが `sticky top-0` になった結果、
モバイルで AdSense 自動広告との競合が発生していた。

- 症状1: 上部アンカー広告（`position: fixed` で最上部）とヘッダーが最上部で
  重なり、左上のハンバーガーが押しにくい。
- 症状2: 自動挿入広告／アンカー予約枠が未配信のとき、ヘッダーとコンテンツの間に
  大きな空白だけが残る（本番の自動広告時のみ再現）。

コード側の対応:

- `globals.css` に `ins.adsbygoogle[data-ad-status='unfilled'] { display:none }` を
  追加し、未配信枠の空白を畳む。
- 補足: 2026-06-24 のレイアウト刷新でヘッダーは左固定サイドバー + 上部固定
  ヘッダー（モバイルでも sticky）構成に変更した。モバイルでヘッダーを sticky に
  保つため、上部アンカー広告との競合は下記の管理画面設定（アンカーを下部に）で
  回避する方針とする。

AdSense 管理画面側の推奨設定（コード変更不要、`docs/adsense-ui-proposal.md` §3 と整合）:

- ページ内フォーマット（自動挿入）をオフ。空白の主因。
- **アンカー広告は下部（bottom）に設定**。上部に出すと sticky ヘッダーと重なり、
  モバイルのハンバーガーが押しにくくなるため。
- モバイル全画面（ビネット）はオフ。
- `/beta/*` `/contact` `/privacy` `/about` を除外 URL に登録。

##### 掲載面と枠数（第1段階）

**PV の多い順に4面へ1枠ずつ**入れる。原案（選手詳細2枠・チーム2枠・試合詳細3枠）は
PV 実績と突き合わせて差し替えた。原案の面は PV 上位ではなかったため。

**枠はファーストビュー内に置く**（2026-08-23 変更。当初は原案どおり「ファーストビューには
置かない」でスクロール下方に置いていたが、視認性＝ページRPM を優先して覆した。
判断の経緯は [ADR-016](../adr/ADR-016-manual-adsense-units-over-auto-ads.md) の追記）。

| ページ種別 | URL | 枠数 | 位置 | 375×812 実測の枠上端 |
|---|---|---|---|---|
| 選手一覧 | `/players/` | 1 | 検索ボックスの直後・「出場数の多い選手」の前 | 402px |
| 大会結果 | `/tournaments/<...>/<gender>/` | 1 | リード文の直後・年度/カテゴリ切り替えの前 | 408px |
| news 展望 | `/news/<articleId>/` | 1 | リード文の直後・最初のカテゴリ節の前 | 460px |
| 大会一覧 | `/tournaments/` | 1 | フィルターバーの直後・件数と年度ブロックの前 | 492px |

「実測の枠上端」は 375×812（モバイル）でのビューポート上端からの距離。枠高は280pxなので、
4面とも**枠全体がファーストビュー内に収まる**（上端 + 280 < 812）。この数字は配置を変えたら
測り直すこと。**大会結果ページは当初 年度/カテゴリ切り替えの「後」に置いたが top=628px となり
枠の下半分が折り返し下に落ちたため、切り替えUIの「前」へ移した**——「ファーストビュー内」は
節の順序を1つ変えるだけで簡単に破れるので、目視ではなく実測で確認する。

配置の原則:

- **ファーストビュー内に置く**（2026-08-23 変更）。ただし置くのは**そのページの主目的の操作・
  リード文を終えた直後**であり、h1 の上や主目的の操作より上には置かない。
  選手一覧なら検索ボックスの下、大会一覧ならフィルターバーの下。
- **本文・読み物は一切分断しない**。4面とも、枠より下にある読み物（表・トーナメント表・
  カテゴリ節・年度ブロック一覧）は枠をまたがない位置に置いてある。
- **表・カード・トーナメント表の内部には入れない**。分断すると読めなくなる。
- **1ビューポート内に2枠を同時に出さない**。現状は1ページ1枠なので自動的に満たしている。
- **薄いページには置かない**。`/beta/*` `/contact` `/privacy` `/about` は対象外（管理画面の除外URLと同じ）。
  news 記事は掲載データが無いとき（`categories.length === 0`）は枠を出さない。
- 密度の外部基準は Lighthouse Publisher Ads Audit の**ビューポート垂直方向30%**。
  Google は2016年に「1ページ3枠まで」の枠数上限を撤廃済みで、現在の基準は枠数ではなく密度・UX。
  280px / 812px = 34% なので、**モバイルではこの目安を超えている**。1ページ1枠を守る前提で
  許容しているが、2枠目を足すときはこの数字が効いてくる。

##### CLS を出さないための実装上の決めごと

`AdUnit.tsx` のコメントにも同じことを書いてあるが、要点は3つ:

1. **`ins` はマウント後にだけ描画する**。サーバー出力の DOM に置くと 2026-07-05 と同じ
   ハイドレーション不一致（#418）→ `no_div` の連鎖を招きうる。高さを持つラッパーだけは
   サーバー出力に含めるので、マウント前後で位置はずれない。
2. **`ins` に `router.asPath` の key を付ける**。SPA 遷移で同じ `ins` ノードを使い回すと
   描画済みノードへの再 push になり、2ページ目以降で広告が出なくなる。
3. **`data-full-width-responsive="false"`**。`true` にすると AdSense がモバイルで `ins` を
   端末幅いっぱい（375px幅なら 375×375）に広げ `margin-left: -16px` で PageLayout の
   左右パディングの外へはみ出す（実測）。確保した `min-height`(280px) も超えるため
   レイアウトシフトも出る。`false` なら本文カラム幅・高さ280pxに収まり CLS ゼロ。

未配信（`data-ad-status="unfilled"`）のときは枠ごと畳む（高さも上下マージンも消す）。
畳むと僅かにシフトするが、本文の途中に数百pxの空白が残り続ける方が実害が大きいという判断で、
自動広告向けに `globals.css` へ入れた unfilled 非表示ルールと同じ考え方。

##### 段階導入の手順と合否閾値（暫定）

有効化は `lib/ads.ts` の `AD_SLOTS` に AdSense 管理画面で発行したスロットIDを貼ることで行う
（空文字なら `AdUnit` は DOM ごと出さないので、コードは入れたまま配信だけ止められる）。

**実際の運用（2026-08-23）: 4面ぶんのスロットIDを同時に反映した。**
当初は「面ごとに1枠ずつ」と書いていたが、管理画面で4ユニットまとめて発行したためそうしていない。
この選択の帰結を明記しておく:

- **できること**: ユニットを面ごとに分けてあるので、AdSense レポートでの**面別RPM比較は成立する**。
  どの面が稼いでいるかは同時投入でも読める。
- **できないこと**: CWV や回遊が悪化したときに**どの面が原因かを切り分けられない**。
  同時に4面が変わるため。悪化が出た場合は、`AD_SLOTS` の該当キーを空文字に戻して
  1面ずつ消し込むことで切り分ける（デプロイは要るがコード変更は1行）。
- 2枠目を足すとき（長尺の大会結果ページが候補）は、1面ずつに戻すこと。
  枠を増やす方向の変更は密度に効くため、同時投入の影響が大きい。

| 指標 | 見る場所 | 撤退ライン |
|---|---|---|
| CLS | PageSpeed Insights / CrUX（該当ページ種別の代表URL） | 導入前より悪化し 0.1 超 |
| ページRPM・推定収益 | AdSense レポート（ユニット単位） | 導入2週後の推定収益が導入前2週を下回る |
| 回遊 | GA4 `internal_link_click` ÷ `page_view`（該当 `from_type`） | 相対20%以上の低下 |

閾値は自サイトの実測ベースではなく**暫定（Assumption）**。1面目の実測が出たら差し替える。
測定手順そのものは [回遊検証ランブック](./circulation-verification.md) の手順2・3をそのまま使う
（AdSense のページビュー数・ページRPM・推定収益は既に副3指標として組み込まれている）。

##### 選手結果ページに枠を置いていない理由

選手結果ページ（1,916枚）はサイト最大の母数で広告面としては最有力だが、
[回遊検証ランブック](./circulation-verification.md) が**対照群**として使う面なので
**意図的に空けてある**（`AD_SLOTS` にキー自体を作っていない）。ここに広告を入れると
「学校ページの変化 − 選手結果ページの変化」という判定式の引き算側が汚れ、回遊施策の
効果を測れなくなる。入れるなら回遊検証のベースライン取得前か、検証完了後に限る。

## 計測

- `src/pages/_app.tsx` で Google Analytics (GA4, Consent Mode v2) を読込
- Cookie 同意 UI は `src/components/CookieConsent.tsx`
- 同意前は `ad_storage` / `analytics_storage` を denied（cookieless ping は送信される＝advanced consent mode 相当）
- 同意後に granted へ更新
- 再訪ユーザーの同意は inline スクリプト内で `localStorage` を同期読みし、**初回 page_view より前**に復元する（hydration 後に復元すると初回PVが denied 計測になるため）
- `wait_for_update: 500` / `url_passthrough` / `ads_data_redaction` を設定し、同意確定待ち・クッキー不可時の計測ロスを軽減
- SPA 遷移は `gtag('config')` 再実行ではなく `gtag('event','page_view')` で送信（二重計上・セッション分断の回避）
- クッキーは `SameSite=Lax;Secure`（同一ドメイン first-party 用途のため Lax）

### 回遊計測のカスタムイベント（2026-08-15 追加）

回遊施策の合否を判定するために送っているイベント。手順・指標の定義は
[回遊検証ランブック](./circulation-verification.md)が正で、ここは実装の所在だけを書く。

| イベント | パラメータ | 送信箇所 | 用途 |
|---|---|---|---|
| `internal_link_click` | `module` / `from_type` / `to_type` | `lib/analytics.ts` の `attachInternalLinkTracking()`（`_app.tsx` から `<main>` に委譲リスナーを1つ張る） | 主指標「モジュールCTR」の分子 |
| `consent_accept` / `consent_decline` | なし | `_app.tsx` の `handleAccept` / `handleDecline` | 同意率（セッション系指標の解釈に必須） |

- **同意状態に関わらず送る**。未同意でも cookieless ping でイベントは GA4 に届くため、
  イベント数どうしの比（CTR）はセッション結合の成否に影響されない。これが主指標を
  「セッションあたりの表示回数」ではなくイベント比に置いている理由。
- **計測対象は `<main>` 内のリンクのみ**。サイドナビ（`aside[data-sidebar]`）とフッターは
  全ページ共通の定型リンクで、「そのページが次のクリックを作れたか」を測る対象ではない。
  この線引きはランブックの実測（ビルド済み `out/` の静的解析）と同じ定義にしてあり、
  静的解析のリンク本数と GA4 のクリック数を直接突き合わせられる。
- **モジュール分離は `data-link-module` 属性**。リンクを含む要素に付けるとその値が `module` に入り、
  付けなければ `unclassified` にまとまる。新しい回遊モジュールを作るときは属性を1つ足すだけでよく、
  リンクコンポーネント側には手を入れない。
- `from_type` / `to_type` のページ種別は `getPageType()`（`lib/analytics.ts`）が URL から判定する。
  判定はビルド済み `out/` の全4,243 URL に対して静的解析の分類と**一致0件差**を確認済み（2026-08-15）。
  回帰テストは `npm run analytics:test`。
- **GA4 側の設定が別途必要**: `module` / `from_type` / `to_type` をカスタムディメンション
  （イベントスコープ）に登録しないと探索で使えない。**登録前に届いたデータは遡って参照できない**。

### 計測精度に関する注意（2026-06）

- GA4 は client-side 計測のため、広告ブロッカー・Safari ITP・同意 denied により**実トラフィックより常に少なく出る**（一般に10〜40%）。これは実装では完全には解消できない。
- なお GA4 の `_ga` は **first-party クッキー**であり、ブラウザの「サードパーティクッキー許可」設定では精度は改善しない。
- 実数に近い基準値が必要な場合は、Cloudflare 配信を活かして **Cloudflare Web Analytics（cookieless・ブロックされにくい）** を併用し GA4 と突き合わせるのが有効（要 Open Question / 別途導入判断）。
