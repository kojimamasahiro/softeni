# アイデア: 大会メタデータ基盤（会場・施設・日程・大会要項のエンティティ化）

## 状況

Idea Backlog。発散フェーズ（2026-07-26 検討開始）。設計・実装には入っていない。
初回検討で「方向性は正しいが、着手すべきは機能ではなくデータ収集」という暫定結論に至っている。

（2026-08-25 追記: 観戦者視点からの再検討と実測検証により、**次の一歩が具体的に確定した**。
最新の状況・推奨・未解決は追記6・追記7を参照。本節は2026-07-26時点の記録として残す）

## 目的

現在のデータ構造は「大会 → 試合 → 結果 → スコア」という試合データ中心。
ここに **会場・施設・日程・大会要項** を独立したエンティティとして追加し、
「試合を管理するサイト」から「大会を管理するサイト（ソフトテニス大会データベース）」へ広げる。

狙いは3つ。

1. 公開情報から取得できるデータ資産の「種類」を増やす（件数ではなく次元）
2. 大会ページを結果だけでなく大会情報のハブとして完成させる
3. AI検索・API公開・開催地分析の土台にする

## ユーザーが興味を持った点

> この4つだけでも1〜2年は十分戦えるテーマだと思います。
> 重要なのは、「会場」「大会要項」「施設」「日程」を個別機能として考えるのではなく、
> 「大会メタデータ基盤」を作るという考え方です。

> 「大会要項を表示する」のではなく、「大会要項から構造化データを抽出する」

> 今回話していて一番大きかったのは、「試合データを増やす」のではなく、
> 「大会を構成するエンティティを増やす」という考え方です。

優先順位についての発言:

> 一番はやはりSEO、そしてUXの向上、最後に保守のしやすさかと思っている

参考サイト（TheSportsDB / Sofascore / SportsDataIO / Google Maps / Wikipedia）については、
デザインや機能ではなく **どんなエンティティを持ちどう関連付けているか** を学ぶべき、という整理。

## わかっていること

2026-07-26 に実データ・コードベースを調査して確認した事実。

### 出発点は0ではない

- `data/tournaments/information/*.json` は **61ファイル・112レコード**あり、
  `year` / `location` / `startDate` / `endDate` / `sourceUrl` を**全件保持**している
  （`location` 欠損は1件のみ＝`open-questions.md` 記録済みの第59回STリーグ）。
- したがって「日程」と「会場」は新規取得ではなく **粒度を上げる話**（都道府県 → 施設名）。

### 「会場リスト1枚」は実質すでに存在する

- `/tournaments/`（`src/pages/tournaments/index.tsx` ＋ `components/tournaments/TournamentSearchTable.tsx`）は
  大会インスタンスの検索テーブルで、**開催地カラム・開催地フィルタ・年フィルタ・開催日降順ソート**を
  すでに備えている（`prefectureId` で逆引き）。
- よって「会場ごとのページを作らず一覧1枚だけ作る」案の差分は、
  **新規ページではなく既存 `/tournaments/` の軸を会場側に転置した集計ビュー**にとどまる。

### 履歴の蓄積が圧倒的に足りない

年別レコード数: 2019年1 / 2020年1 / 2021年2 / 2022年10 / 2023年10 / 2024年15 / 2025年46 / 2026年27。
**2024年以前は合計24件**しかない。

「開催回数ランキング」「全国大会開催マップ」「年度別開催地」といった提案中もっとも魅力的な機能群は
10年単位の履歴を前提とするため、現時点では中身が出ない。

## 評価（SEO / UX / 保守）

ユーザーの優先順位は SEO > UX > 保守だが、**実際に効く順序はほぼ逆**というのが現時点の見立て。

### SEO: 期待より低い。ただし例外が1つ

- `docs/wiki/seo.md` の通り、当サイトのSEOボトルネックは**ページ不足ではなく薄いページによる
  インデックス枠の食い合い**。選手結果ページ約1,800件に `noindex` 閾値を設け、
  2026-07-26 には `local_index` 由来の誤判定を1,898人分修正したばかり。
  会場ページ生成は **その潰したばかりのパターンを別名で再生産する**。
- 需要側: 「{施設名} ソフトテニス」の検索需要は薄い。プロスポーツで会場ページが成立するのは
  観客が座席・アクセス・キャパを調べるため。ソフトテニス大会の会場を調べるのは出場者と保護者で、
  彼らは主催者サイトの要項PDFを直接見る。
- **例外**: 「インターハイ ソフトテニス {年} 会場」「全中 会場 どこ」という
  **大会×年×会場クエリは実在する**。これは会場ページ不要で、
  既存の年度別結果ページ・大会ハブの title / 本文に**会場名を literal で出すだけ**で取れる。
  `seo.md` #2追記（全国大会優勝の通称を literal で出す・新規URLは増やさない）と同型の手法。
- 結論: **SEO目的なら「会場エンティティ」は不要で「会場名フィールド」で足りる。**

### UX: ここが実は最大の効果

- 現サイトは結果しか出せないため、**大会前は情報が空白**。日程＋会場が入ると
  「開催前トラフィック」という現在ゼロの層が取れる。季節性クエリなので副次的にSEOにも効く。
- 地図・アクセスは保護者が実際に調べるため実用価値がある。
- 逆に「この会場で開催された大会一覧」の回遊価値は、上記の分布（中央値2件）から薄い。
- 効くのは会場ページではなく **大会ページに開催前情報が載ること**。

### 保守: 3番目ではなくリスク側

- 会場名の名寄せはコストを**増やす**。既に `homonyms.json` / `team-name-aliases.json` /
  `playerKey` で名寄せ経路が複数並行している（`team-player-identity.md`）。
- 会場は表記ゆれに加え **ネーミングライツによる改称**で年ごとに名前が変わる。
  「2018年の◯◯コート」と「2024年の△△アリーナ」が同一施設というケースが実際に起きる。
  → **施設ID（不変の実体）と会場名（年ごとの表記）の分離は最初から必要。**
- 保守性が改善する筋があるとすれば Knowledge Graph アイデア経由。会場は選手より規模が小さく
  エッジも「大会↔年↔会場」の1種類のみで、**グラフ層の最初の試作対象としては
  対戦相手ネットワークより筋がよい可能性がある**（既存ロジックと衝突しない・検証が速い）。

### 4つのエンティティは等価ではない

| エンティティ | 取得コスト | 開く機能の数 | 評価 |
|---|---|---|---|
| 日程 | ほぼ0（既存） | 開催前情報 | 最優先。すでに持っている |
| 会場（施設名） | 低〜中 | 開催地履歴・マップ・回数ランキング | 鍵。ただし履歴が貯まるまで機能は成立しない |
| 施設スペック（コート数/サーフェス/屋内/GPS） | 高・欠損多い | 施設検索のみ | 低。利用者は大会運営者で当サイト読者層とズレる |
| 大会要項 | 最高（構造化抽出） | 参加資格・試合方式という新次元 | まずPDFリンク保持のみ。抽出は後 |

### 参考サイトの選び方への指摘

TheSportsDB / SportsDataIO の Venue モデルは**ホームスタジアム前提**で、チーム↔会場が固定だから
Venue がエンティティとして効く。ソフトテニスの大会は毎年持ち回りで、関係は「大会↔年↔会場」の3項。
構造が違うため、モデルとしては**オリンピック・世界選手権のような回遊型イベント**の持ち方
（Wikipedia が実質そうなっている）のほうが近い。**挙げられた5サイトの中では Wikipedia の優先度が最も高い。**

## 追記1（2026-07-26）: 「1枚だけ作る」なら会場一覧ではなく日程カレンダー

「会場ごとのページを作らず、会場リストのページを1枚だけ作るとしたらどうか」という問いへの検討。

結論: **会場を主語にした一覧1枚の価値は低い。同じ1枚を作るなら年間大会カレンダーにすべき。**

- 前述の通り `/tournaments/` が実質すでにその役割を持つ（開催地カラム・開催地フィルタ・年フィルタ・
  開催日降順ソート）。会場一覧案の差分は**軸の転置（大会を並べて開催地を表示 → 開催地を並べて大会を集計）**にとどまる。
- 転置しても行は38個、うち13行が「大会1件」。テーブルとして情報量が出ない。
- 個別ページを生成しないため薄いページ問題は起きない＝**害はないが益も小さい**。
- 新規URL1枚で狙えるクエリは「ソフトテニス 大会 開催地」程度で需要が薄い。

一方、**同じ1枚を「年間大会カレンダー」（日程軸・開催地はカラム）としてフレーミングし直すと評価が変わる**。

- 狙えるクエリが「ソフトテニス 全国大会 {年} 日程」「ソフトテニス 大会 いつ」になり、需要が実在する。
- **開催前トラフィック**という現在ゼロの層に当たる。これは上記UX評価で唯一高得点だった論点と一致する。
- 会場はカレンダーの1カラムとして乗るだけでよく、会場エンティティ化を先行させる必要がない。

したがって、単ページ施策としての優先度は **日程カレンダー > 会場軸の転置ビュー**。

## 追記2（2026-07-26）: データ収集の現状（収集設計を検討する前提として調査）

「まずはデータが必要」という方針を受けて、既存の収集経路を調査した。

- **`data/tournaments/information/*.json` を書き込むスクリプトは存在しない**
  （`grep -rln "tournaments/information" scripts/` の結果は0件。読み取り側は
  `generate-players-json.mjs` / `generate-news-drafts.mjs` 等が複数ある）。
  つまり大会メタデータは現在**完全に手動メンテ**。会場・日程を増やす話は、
  クローラの話である前に**入力運用の話**である。
- `information` のレコードに対する**スキーマ検証は存在しない**
  （`scripts/check-*` は growth / identity / tournament-entries が対象で、information は非対象）。
  フィールドを増やすなら検証も同時に用意しないと、欠損・表記ゆれが静かに溜まる。
- 巡回元 `data/local-sources/prefecture-sources.json` は **47都道府県分**が既に登録済みで、
  `crawlLevel`（`link_only` 等）と複数 `sourceUrls` を持つ。**巡回インフラ自体は既にある**ため、
  要項収集は新規構築ではなく既存クローラの出力先追加で始められる。
- 既存の候補ストア `detected-documents.json` は583件あり、`status`（`new`/`accepted` 等）・
  `inferred`（`year` / `tournamentName` / `confidence`）・`detectedAt` / `lastSeenAt` を持つ
  **人間確認前提のレビュー用ストア**。要項ストアもこの形（自動検知 → 人間が確認 → 本データへ昇格）を
  踏襲するのが自然。

## 追記3（2026-07-26）: jsta.or.jp 実地調査 — 一次ソースの特定と閾値判定

「まず jsta.or.jp を1件辿って会場の記載場所を特定する」パイロットの実施結果。

### 発見1: 年度ごとの「大会日程及び開催地一覧」PDFが一次ソース

`https://www.jsta.or.jp/wp-content/uploads/t_records/{年度}/{年度}_taikai_alle.pdf`

主催・共催・その他の全国大会を**1ファイルで網羅**し、大会名・日程・開催地（市区町村）を持つ。
テキスト抽出可能（スキャンPDFではない）。2024年度版には**次年度予定開催地**の列もあり相互検証に使える。

- **存在確認: 2024年度・2025年度のみ。2023年度・2022年度・2019年度は404。**
- HTML版 `https://www.jsta.or.jp/events/the_yealy_events` は同内容の表を持つが
  **現行年度のみ**（`/2024` を付けても canonical で現行版にリダイレクトされ、年度アーカイブは存在しない）。
  HTML表は `taikai_alle.pdf` にない**大会要項PDFへの直リンク**を持つので、両方を使う。

### 発見2: 大会要項PDFに施設情報がほぼ全部入っている

`t_records/{年度}/{年度}_{分類コード}_10.pdf`（`_10`＝要項）。2024年度・2025年度で取得を確認。

第80回天皇賜杯（2025_A12_10b.pdf）から実際に取れた項目:

- 施設名: 有明コロシアム / 有明テニスの森公園ハードコート / 同ショーコート
- **住所**: 〒135-0063 東京都江東区有明2丁目2-22 / **TEL**: 03-3529-3301
- **コート数・サーフェス・屋内**: ハードコート23面（うちインドア8面）、ショーコート1面
- **駐車場**: 「選手・観客用の駐車場はございません」
- **日程の内訳**: 受付・コート開放・開会式・競技1日目/2日目/3日目（時刻付き）
- 参加資格・試合方法・参加料・使用球

第2回STリーグ（2024_A12_10.pdf）でも同様（スカイホール豊田 メインアリーナ、木床フローリング4面、住所・TEL）。

**本アイデア初回評価の訂正**: 「施設スペック（コート数・サーフェス・屋内・駐車場）は取得コストが高く
欠損が多い」と評価したが、**誤り**。これらは要項PDFの「4. 会場」節にほぼ定型で記載されており、
施設情報と日程内訳は**同じPDF1枚から同時に取れる**。4エンティティを別々に集めるという前提自体が不要だった。

### 発見3: 大会と会場は 1:N（日別に会場が変わる）

天皇賜杯は開会式＝有明コロシアム、競技1〜2日目＝有明テニスの森公園、3日目＝有明コロシアムと
**日ごとに施設が変わる**。`taikai_alle.pdf` の開催地欄にも「北海道 苫小牧市、室蘭市、札幌市」
「兵庫県 神戸市／京都府 福知山市、舞鶴市」のように複数市区町村・複数県にまたがる例が多数ある。

→ `venue` を単一文字列で持つ設計は不可。**`venueIds` を配列で持ち、日付との紐付けを許す構造**が必要。
（既存の `data/st-league/**` の `venue` は単一文字列だが、STリーグが1会場開催なので成立している例外）

### 閾値判定

事前に設定した基準は「**全国大会80件のうち70%（56件）以上で会場が特定できれば進める**」。

`information` の内訳（`index.json` 収録＝全国 / `year` は年度）:

- 全国 80件 … うち **2024年度以降が56件**（＝ちょうど70.0%）、2023年度以前が24件
- 地方 32件 … 全て2024年度以降だが jsta の対象外

jsta の一次ソースが確実に存在するのは2024・2025年度なので、**カバーできるのは56件＝ちょうど閾値ちょうど**。
判定は「**進める。ただしギリギリ**」。2023年度以前の24件は別経路（Wikipedia・都道府県連盟・
結果PDF内の記載）が必要で、ここは未検証。

### 次の一歩（更新）

1. `{年度}_taikai_alle.pdf`（2024・2025）＋ `the_yealy_events` HTML表をパースし、
   大会名・日程・開催地を機械可読化する。まず**市区町村レベル**まで確定させる（施設名は次段）
2. 要項PDFリンクを収集し、「4. 会場」節から施設名・住所・コート数・サーフェスを抽出する
3. 抽出結果を `data/venues/venue-candidates.json`（レビュー用ストア、`confidence` + `status`）に出し、
   人が確定してから `information` へ書き戻す

## 追記10（2026-08-25〜26）: 予選会の最終成績を入れる — 影響調査・訂正・積み残し

ユーザーの指摘「予選会はトーナメント → ラウンドロビンという他に例のない順序なので、
単純に `rank.kind` を指定するとトーナメント形式に影響があるかもしれない」を受けた調査と実施。

### 訂正1: 「ランキングのポイントが動く」は誤りだった

追記9・ランブックM1で「`winner` を書くとランキングのポイントが動く」と書いたが**誤り**。

- `computeSeasonPoints` は `config.ranking.disciplines` すなわち **`['doubles']` のみ**を集計する
  （シングルスは2026-07-11にポイントランキングから撤退）。この予選会はシングルスなので**対象外**
- また「`replayData.mjs` が international を `local` tier にするので加点は小さい」とも書いたが、
  `ranking-config.json` の `tierOverrides` で `asian-games-qualifier` は **`major`（重み100）** に
  指定されている（バックテストで較正済み・「国際予選3つは全員国内選手を確認済み」）。
  local という前提自体が誤り

### 訂正2: 女子決勝リーグの順位を取り違えていた

追記7の表で「女子1位 長谷川憂華 / 2位 宮前希帆」としたが**逆**。正しくは **1位 宮前希帆 / 2位 長谷川憂華**。

ゲーム差で並べたのが誤りで、リーグ戦の序列は **勝数 → 直接対決 → ゲーム差**。
両者2勝1敗で並ぶが、直接対決は宮前が 4-3 で勝っている。

**より本質的な反省**: 順位は `results[].roundrobin.rank` として**既にデータに入っていた**。
自力で計算し直す前にそれを見ればよかった（計算し直した結果、入っている値のほうが正しかった）。

### 調査結果: 「トーナメント形式が壊れる」経路は存在しない

| 箇所 | 結論 | 根拠 |
|---|---|---|
| ブラケット描画 | **影響なし** | `lib/bracketLayout.ts` は `results[].roundrobin.{group,rank}` を読み、`tournament` を一切参照しない。スキーマが「組内順位」と「大会成績」で分離されている |
| 結果カバレッジ | **影響なし** | `lib/tournamentCoverage.ts` は `stage:'knockout'` 限定。roundrobin のみは `unsupported` 扱いで、見るのは `'ongoing'` だけ |
| Elo レーティング | **影響なし** | `matches` 駆動。results の rank を足しても試合は増えない |
| 年度ランキング | **影響なし** | 上記の訂正1のとおり doubles 限定 |

knockout の「決勝」で終わって**おり、2025年の予選会だけが例外だった。2022年の同じ大会は

## 追記15（2026-08-26）: S3・S4 実装

### 訂正: トップページに広告の制約は無かった

S3 の説明で「トップページも広告面なので 375×812 で枠上端を測り直す必要がある」と書いたが**誤り**。
[monetization.md](../wiki/monetization.md) のファーストビュー枠は5面（選手一覧 / 大会結果 / news展望 /
大会一覧 / 選手結果）で、**トップページは対象外**。ビルド済み HTML でも `adsbygoogle` は0件だった。

トップにあるのは `AppShell` のフッター直上枠だけで、ページ最下部にクライアント側でマウントされる。
上に節を足しても折り返しに影響しない。`/tournaments/` を3件に絞る羽目になった制約は
トップには効かないので、**件数を自由に決められる**（5件にした）。

### S3: トップページに「これから開催」

`/tournaments/` の中にあったローカル実装を共有コンポーネント
`src/components/tournaments/UpcomingTournaments.tsx` へ切り出し、トップページでも使った。
同じものが2箇所にあると「これから開催」の定義が割れるため。

| 面 | 件数 | 制約 |
|---|---|---|
| `/tournaments/` | 3 | 広告枠がファーストビューから外れない上限（ADR-016 追記） |
| トップ `/` | 5 | ファーストビュー枠が無いので制約なし |

置き場所は「最近追加された大会」の**直前**。すぐ下が過去形なので対にした。
トップページの入口に未来形が1つも無い状態がこれで解消される。

「今日」の判定は**描画時**（`getTodayInTokyo()`）のままにした。ビルド時刻に固定すると、
再ビルドまで終わった大会が「これから開催」に残るため。呼び出し側は
「会期が終わっていない候補」を全部渡し、絞り込みと件数はコンポーネントが持つ。

リンク先は大会ハブ。トップ側は `getTournamentHubHref()` を通すので、高校全国大会は
歴代記録ページへ振り替わる（汎用ハブが noindex のため。seo.md #3）。

### S4: `/tournaments/major/` に開催前の大会を含める

このページは名前が「主要大会結果」だが、実際は `isMajorTitle` で絞っておらず
**`index.json` の全大会を世代ごとに並べた「収録大会の一覧」**。唯一の絞りが
「結果のある年度が1つ以上ある」（`groups.length > 0`）だった。

実測で**4大会が落ちていた**:

| 大会 | 落ちていた理由 |
|---|---|
| `asian-games` | これから開催（結果なし） |
| `zennihon-club` | 2026-10-24 開催予定 |
| `zennihon-secondaryschool-club` | 2026-11-21 開催予定 |
| **`st-league`** | **結果はあるが `/st-league/` 専用ページにある** |

**STリーグは「開催前だから出ない」ではなく、結果があるのに一覧から抜けていた**。
大会ハブ側には `featurePath` / `resultPath` で専用ページへ導く仕組みがあるのに、
この一覧だけ対応していなかった。S4 の実利はむしろこちら。

対処として、カテゴリのリンクが1本も作れない年度を3通りに分けた。

1. `info.resultPath` がある → 「結果・順位表を見る →」の内部リンク1本（STリーグ）
2. 会期が終わっていない → 「開催予定 2026年9月18日〜9月23日 / 愛知県（結果は大会終了後に掲載）」
3. それ以外（終わったのに結果が無い年度） → 従来どおり出さない

`YearGroup` に `upcomingNote` / `internalResultHref` を足し、`TournamentCard` が出し分ける。
リード文も「大会結果一覧」→「大会一覧」に直し、開催前は日程と開催地を出す旨を1文足した。

## 追記16（2026-08-26）: 開催前ブロックの判定から「結果がまだ無い」を外した

### きっかけ

ユーザーからの指摘——「トップページのこれから開催は**開催回数がタイトルに表示されている**のに、
リンク先が全体ページなのは問題ないか」。

調べると、**リンクではなく遷移先に問題があった**。

| 大会 | 遷移先の状態 |
|---|---|
| 第20回 アジア競技大会 | h1「アジア競技大会 2026年 日程・会場」＋開催前ブロック → 問題なし |
| **第54回 全日本社会人選手権大会** | h1「大会結果（歴代一覧）」、**開催前ブロックが出ない** → その回の会期も会場も出ない |

「第54回」というリンクを踏んだのに、その回の情報が1つも出ない状態だった。

### 原因

開催前ブロックの判定に「その年度の結果がまだ無い」（`!yearsWithResults.has(year)`）が入っていた。
これは `details/{tid}/{year}/` にファイルがあるかを見ているだけで、
**組み合わせだけ投入した未開催の大会**まで「結果あり」と扱ってブロックを消していた。

全日本社会人（2026-08-29 開幕、3日後）は組み合わせが投入済みだったため該当した。
未来の9件のうち該当は**この1件だけ**だが、**最も近い大会**だった。
しかも「開催前の大会を出す」方針を進めるほど組み合わせの先行投入は増えるので、放置すると悪化する。

### 修正

判定を **`endDate >= 今日` だけ**にした。会期が終わっていない以上その大会は未開催なので、
日程・会場を出すのが正しい。会期が終われば条件から外れて自動的に消える。

`upcomingOnly`（h1・title を「歴代結果」から「日程・会場」へ切り替える判定）は
別途 `yearGroups.length === 0` で絞っているので影響なし。全日本社会人は
h1「歴代一覧」のまま、その直下に第54回の開催前ブロックが出る形になる。

ビルド後の実測で、**未来9件すべての大会ハブに開催前ブロックが出る**ことを確認した
（修正前は8件）。

### リンク先を「その回のページ」にしない理由

未開催の大会には**回ごとのページが存在しない**。年度ページは種目ごとの結果ページとして
生成されるので、結果が無ければ作れず、作るなら新規URLを増やすことになる
（「新規URLを増やさない」方針に反する）。

したがって正解は「リンク先を変える」ではなく「**遷移先がその回を最初に見せる**」で、
それが今回の修正。h1 が「歴代一覧」のままなのは過去の結果を持つ大会としては正しく、
その直下に当該回の情報が来る。
