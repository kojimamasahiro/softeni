# 大会成績データに基づく「メンバー」表示の拡張 要件・設計

日付: 2026-08-11（設計改訂）
状態: Draft（実装前の合意用。確定事項は実装の前提とする）

## 背景

`/teams/[teamId]/`（`src/pages/teams/[teamId]/index.tsx`）は STリーグ出場チームについて、
`participants.json` 由来の年度別ロースターを「STリーグ登録メンバー」節として表示するよう
2026-08-11 に実装済み（`docs/wiki/st-league.md`「『メンバー』クエリの受け皿」）。

その実装の過程で、`getStaticProps` が **`hasSubPages`（`team-name-mappings.json` に
登録があるチーム）について `generateTeamInfo(teamId)` を呼び、大会出場記録から選手一覧を
既に集計している**にもかかわらず、その結果（`fullInfo.players`）を noindex 判定用の
`matchCount` 計算にしか使っておらず、**画面には一切表示していない**ことが分かった。
新規データ収集なしで、既に取得済みのデータを表示するだけの拡張余地がある。

## 実データで確認した事実

### 初回調査（2026-08-11）

`team-name-mappings.json` の67チーム（≒STリーグ出場チーム66＋日体大`nssu`）について、
STリーグ側ロースター（`participants.json`、最新の収録がある年度）と、大会成績側ロースター
（`generateTeamInfo` が `data/tournaments/details/**` 横断で集計する選手一覧）を比較した。

- 67チーム中64チームで、大会成績側の方が選手を多く拾える。
- **21チーム**はSTリーグに出場歴があるがSTリーグ側ロースターが全年度で0件（エビス商事・
  日立Astemo・きのくに信用金庫・ルーセント・大阪ガス・YKK 等）。加えて `nssu` はSTリーグ
  出場自体が無いため、メンバー情報が皆無なのは計22チーム。大会成績側には実データがある
  （氏名dedup後の実測: きのくに信用金庫15名、ルーセント26名、YKK24名）。
  ※初稿の「19チーム」は数え漏れ。2026-08-11 の再検証で21（+`nssu`）に訂正。
- `nssu`（日本体育大学）はSTリーグ非出場のためメンバー表示が現状皆無だが、大会成績側には
  **249名**の選手が集計できる（生pidベース。後述のとおりこの数字は過大）。

### 追加調査（2026-08-11・ユーザー指摘を受けて実施）

「年度別にできない理由」「STリーグ側と大会成績側を同一人物として統合できないか」という指摘を受け、
以下を検証した。

1. **年度別化は可能だった**: `generateTeamInfo` の出力（`players: Record<pid, Player>`）自体には
   年度情報が無いが、同じ `hasSubPages` 分岐で既に呼んでいる `aggregateTeamResults(teamId)` は
   `EventResult.year` を持っている。高校学校ページの `membersByYear`（`entries[].playerIds` を
   年度でグルーピング）と全く同じ手法が使える。「性質が違うので通算でしか出せない」という
   初回設計の説明は誤りだった。
2. **氏名の正規化dedupで人数が大きく減る**: `generateTeamInfo` は生の `participant.id`
   （`姓_名_チーム_都道府県` 形式。都道府県サフィックスの有無などがファイルによって揺れる）を
   キーにしており、**同一人物が複数の pid 変種として重複カウントされる**。`nssu` の249件を
   `normalizeJa(姓+名)` で dedup すると **118件（53%減）** になった。
3. **年度別×氏名dedupを両方行うと現実的な人数になる**: `nssu` を年度別・氏名dedup後で見ると
   2022年21名／2023年51名／2024年58名／2025年69名／2026年49名。249名や年度別生pid値
   （84〜144名/年）よりかなり小さい。ただし日本体育大学という大規模大学の性質上、
   STリーグの実業団チーム（1桁〜十数名/年）と比べるとまだ多め。

結論: **年度別グルーピング＋氏名正規化dedupを両方行う設計に変更する。** これにより
「表示件数が多すぎる問題」と「STリーグ側・大会成績側の重複表示問題」の両方が、
実装を分けて対処するのではなく1つの仕組み（年度別・氏名ベースの統合）で解消できる。

出典: 上記はいずれも一時的な検証スクリプトの実行結果（このドキュメント作成のための
一度きりの調査、スクリプト自体は保存していない）。再現する場合は
`aggregateTeamResults(teamId)` の `results[].playerIds` / `matches[].pair` を年度でグルーピングし、
`generateTeamInfo(teamId).players` で氏名を引いてから `normalizeJa` で dedup すればよい。

### 追加調査2（2026-08-11・男女の重複バグを発見・修正済み）

「69名は男女で分かれているか」という確認から、`nssu` の2025年を男女別に集計すると
**男子45名・女子32名（単純合計77）なのに正規化dedup後は69名にしかならない**ことが判明した。
差の8名（細田美帆・左近知美・五十嵐美結・天間美嘉・松岡琴美・高橋ひかる・吉木理彩・向山せら）を
追跡したところ、**同姓同名や表記ゆれではなく、`src/utils/team-data-aggregator.ts` の性別判定ロジックの
バグ**だった。

- 原因: `descriptor.category.includes('men')` という**部分一致**でカテゴリの性別を判定していたが、
  英単語 "tournament" 自体が部分文字列として "men" を含むため、`singles-tournament-girls`
  （="トーナメント" ブロックの女子シングルス）が `includes('boys') || includes('men')` の
  `men` 側にヒットして**誤って `gender: 'boys'` に判定されていた**。
  実データでの実例: `data/tournaments/details/asian-games-qualifier/2025/
  singles-tournament-girls.json` の女子選手8名が、アジア競技大会代表予選2025の
  男子シングルスの選手として `aggregateTeamResults` の出力に混入していた。
- 影響範囲の確認: 全371大会ファイルのカテゴリ文字列に対し旧ロジックと新ロジックの判定を
  総当たりで比較したところ、**差分が出たのはこの1ファイルのみ**（
  `asian-games-qualifier/2025/singles-tournament-girls`）。他の370ファイルは影響なし。
- **修正済み**: `parseGenderFromCategory()` という共通関数を新設し、`category.split('-')` の
  **最後のセグメントを厳密一致**で判定するよう変更した（`team-data-aggregator.ts` 内の
  性別判定2箇所を両方この関数に統一）。部分一致による事故がなくなる。
  修正後、`nssu` 2025年は男子37名・女子32名（重複0）に修正された。
- **この修正は `aggregateTeamResults` を使う全ページに波及する**（`/teams/[teamId]/`、
  `/st-league/[year]/teams` の選手別成績表、matchCount によるnoindex判定など）。
  影響ファイルが1件のみと確認済みなので実害は小さいが、副次効果として
  `asian-games-qualifier/2025` に関連するページ（該当選手の個人結果ページ等）の
  男女別集計が正しくなる。

## 要件

### 解決したい課題

「{チーム名} メンバー」系クエリの受け皿を、STリーグ出場チームだけでなく `team-name-mappings.json`
に登録があるチーム全般（≒現状ほぼ同じ67チームだが、将来 mapping が増えれば自動的に対象が増える）
に広げる。特に、STリーグ側ロースターが薄い/存在しない19チームと `nssu` で「メンバー節が一切ない」
状態を解消する。

### スコープ

- 対象: `/teams/[teamId]/index.tsx` の `hasSubPages` 分岐（既に `generateTeamInfo` /
  `aggregateTeamResults` を呼んでいる箇所）。
- 新規データ収集は行わない。既に `getStaticProps` 内で計算済みのデータを年度別に組み替えて
  表示するだけ。
- 新規URLは作らない（既存ページの拡張のみ、`docs/wiki/seo.md` の「内部リンク集約」方針と同型）。

### Non-Goals

- STリーグ以外のカテゴリ（成年カテゴリ全体の都道府県ページ化等）は別アイデア
  （`docs/raw/2026-08-11-idea-general-category-prefecture-pages.md`）のスコープであり、
  本ドキュメントには含めない。
- 同一年度・同一チームに本物の同姓同名選手が2人いる稀なケースの判別は行わない
  （高校学校ページの年度別メンバーと同じ前提。`data/players/homonyms.json` の
  D/E/F検出器は個人選手ページ向けで、チームの年度別名簿表示には現状適用していない）。

## 設計（改訂版: STリーグ側と大会成績側を年度別に統合表示）

### 旧設計からの変更点

初回設計では「STリーグ登録メンバー（年度別）」と「大会成績に基づく主なメンバー（通算）」を
**別セクションとして併存**させる案だったが、以下の理由で**1本の年度別メンバー節に統合**する。

- 大会成績側も年度別に組み替え可能だと判明したため、通算表示にする技術的理由が無くなった。
- 氏名の正規化dedupで両ソースの重複（同一人物）を機械的に解消できるため、
  「同じ選手が2セクションに出てくどい」問題がそもそも発生しなくなる。

### データフロー

大会別成績セクション（`TeamYearlyStats`）が既に年度×性別で分けて表示しているのに合わせ、
メンバー節も**年度×性別**で分ける（男女合算だと上記のバグのような事故に気づきにくく、
表示件数も無駄に大きくなるため）。

```
aggregateTeamResults(teamId)      … 既存呼び出し（変更なし。hasSubPages のときだけ呼ばれる）
  → EventResult[]（year, gender, results[].playerIds, matches[].pair を持つ）
  → gender は既に 'boys'/'girls'/'unknown' のいずれか（'mixed' という値は出てこない。
     aggregateTeamResults 内でミックス結果は生成時点で性別ごとの EventResult に
     分配済みのため）

generateTeamInfo(teamId)          … 既存呼び出し（変更なし。hasSubPages のときだけ呼ばれる）
  → players: Record<pid, {lastName, firstName}> で氏名を解決

season.players（STリーグ、aggregateStLeagueTeam 由来。season.gender を持つので同様に年度×性別で紐づく）
  → 同じ年度・性別があれば統合対象に加える

年度×性別ごとに:
  (a) 大会成績由来の playerId（hasSubPages のときのみ存在。無ければ空集合）
      ※必ず自チーム pid 集合で絞る。下記「他チーム選手の混入」参照。
  (b) STリーグ側 season.players（あれば、同じ年度・性別）
  (a)∪(b) を氏名の正規化キーでユニーク化 → その年度・性別のメンバーリスト
```

`nssu` 2025年で実測: 男子37名・女子32名（男女の重複0、上記バグ修正後の値）。

#### 他チーム選手の混入（実装時の必須フィルタ）

`extractTeamDataFromTournament` は、**エントリー内に1人でも自チーム選手がいれば
そのエントリーの playerIds を丸ごと** `results[].playerIds` に push し、`matches[].pair`
も同様に `pair = playerIds`（エントリー全員）としている。つまり合同ペア等では
**他チーム所属の相方 pid がそのまま入ってくる**。

`nssu` で実測すると、`results[].playerIds` / `matches[].pair` に含まれる pid のうち
**38件が他チーム所属**（中央大学・不二越・ベスト・神戸松蔭大学 等）だった。

したがってメンバー構築時は、pid を必ず `Object.keys(generateTeamInfo(teamId).players)` の
集合で絞る（`lib/teamIndexing.ts` の `countTeamMatches(results, teamPlayerIds)` と同じ考え方）。
「`players` から氏名を引けなければ落ちる」という副作用に暗黙に依存せず、明示的に交差を取る。

#### `gender` の型ガード

`EventResult.gender` の型は `string` なので、`'boys' | 'girls'` に落とすガードが必要
（既存の stats 生成と同じ `if (gender !== 'boys' && gender !== 'girls') continue;`）。
`parseGenderFromCategory` は `'unknown'` を返し得るが、全371大会ファイルのカテゴリ末尾
セグメントは boys/girls/mixed のみで、**現状 `'unknown'` は0件**（実測）。よってこの
ガードで落ちるデータは無い。

### ミックスダブルス由来の参加者の扱い（決定）

**大会別成績グリッド（`TeamYearlyStats`）が使う `gendersWithRealPresence` フィルタは、
メンバー節には適用しない。** ミックスダブルスにしか出ていない選手も、その年度・その性別の
メンバーとして掲載する。

理由: `gendersWithRealPresence` は「その性別の**カテゴリ**が実体を伴って存在するか」を見る
フィルタで、大会別成績グリッド（年度別ページへのリンクカード）の目的（薄いリンクカードを
出さない）には合っているが、メンバー一覧の目的（「その年度、誰が所属していたか」）とは
別の基準。ここで同じフィルタを流用すると、ミックスにしか出ていない選手がメンバー一覧から
消えて過小表示になる。両セクションで基準が違うことは、それぞれの目的に照らせば矛盾しない。

ただし**上流の制約**として、`aggregateTeamResults` はミックス結果を性別ごとに分配する際
`findGenderByNormalizedId(pid)` で性別を引けなかった選手を **boys/girls の両方から落として
いる**（`boyPlayerIds`/`girlPlayerIds` のどちらのフィルタにも通らない）。したがって正確には
「ミックスにしか出ていない選手も、**性別が推定できた場合は**掲載する」であり、性別が
推定できない選手は本設計の範囲では表示されない。将来「この選手が出てこない」という報告を
受けたときの調査起点として明記しておく。

### 表示名の解決アルゴリズム（決定）

正規化氏名（`normalizeJa(姓+名)`）を**グルーピングキー**として使い、**表示用の姓名は
別途決める**（`normalizeJa` は照合専用で表示に使わない、という既存規約に従う）。

年度・性別ごとに、`Map<normalizedKey, {lastName, firstName}>` を構築する。同じ
`normalizedKey` の表記が複数見つかった場合、**`playerLinks` で解決できる表記を優先**する
（解決できる表記が複数ある場合は先に見つかった方）。どちらも解決できなければ、最初に
見つかった生の表記をそのまま使う。

これにより、`data/players/index.json` の正式表記と揺れがある pid 由来の表記（例:
異体字違い）が採用されて本来リンクできるはずの選手がリンクされない、という事故を避けられる。

**ただし実測ではこのルールが効く場面はごく稀**。4チーム（`nssu`/`kinokuni-shinkin`/`lucent`/
`ykk`）で確認したところ、同じ正規化キーに複数表記があるのは `nssu` で4件のみ、うち
「一部の表記だけ `playerLinks` で解決できる」ケースは `kinokuni-shinkin` の1件だけだった。
また `index.json` 側のキーを `normalizeJa` して照合しても解決数は変わらない
（`nssu` は 73/118 → 73/118）。実装コストが小さいので入れてよいが、複雑な優先度判定を
作り込む価値は無い（「解決できる表記があればそれ、無ければ先に見つかった表記」で十分）。

```ts
type RosterMember = { lastName: string; firstName: string; linkedPlayerId?: number };
type YearGenderRoster = { year: number; gender: 'boys' | 'girls'; members: RosterMember[] }[];
```

### 選手名 → 選手結果ページのリンク解決

既存の `playerLinks` 構築ロジックは、現状 **`stLeague.seasons[].players` の氏名だけ**を
対象に `data/players/index.json` を引いている（`if (stLeague)` の中でのみ実行）。これを
2点変更する。

1. `if (stLeague)` の条件を外し、`stLeague` が `null`（`nssu` 等）でも実行する。
2. 解決対象の氏名集合を、**STリーグ側（`stLeague.seasons[].players`）と大会成績側
   （`generateTeamInfo(teamId).players` の値）の両方の和集合**に広げる。現状のまま
   `if` を外すだけだと、対象名リストが STリーグ側の氏名のみのままになり、`nssu` は
   相変わらず `playerLinks` が空になってしまう（大会成績側の氏名がそもそも解決対象に
   入っていないため）。

ロジック自体（`${lastName}::${firstName}` → `count>=5` の選手のみ id、同姓同名は先勝ち）は
変更しない。

### `hasSubPages=false` かつ `hasStLeague=true` の場合（現状データでは非該当）

`generateTeamInfo`/`aggregateTeamResults` は `hasSubPages` のときしか呼ばれない。
理論上、STリーグには出場しているが `team-name-mappings.json` に未登録のチームが
将来発生した場合、大会成績側のデータが空集合になる。この場合も**STリーグ側のみで
年度別メンバーを構築できるようにする**（大会成績側を必須の入力として扱わない）。
現状の67チームでは発生しない組み合わせだが、実装のガード条件としては明示的に
考慮しておく（`fullInfo`が存在しない/未計算の場合は空配列として扱う）。

### 表示セクション

「STリーグ登録メンバー」を廃止し、単一の**「年度別メンバー」**節に統合する
（見出し文言は仮）。既存の「大会別成績」セクション（`TeamYearlyStats`）と同じく、
年度の下に男女を分けて表示する。

- 表示条件: 年度×性別のメンバーが1件以上ある組み合わせが存在すること。
- 表示: 各年度の下に男子/女子を分けて見出しを立て、それぞれ氏名の五十音順
  （`localeCompare('ja')`）。`playerLinks` で解決できた選手は `/players/{id}/results/`
  へリンク、それ以外はプレーンテキスト。
- 出典の区別: 画面上は「STリーグ由来」「大会成績由来」を分けて表示しない
  （どちらも「その年度にそのチームに所属して競技していた事実」という点で対等に扱う）。

### 表示件数の絞り込み

年度別×性別グルーピング＋氏名dedupにより、初回設計時の「249名を一度に表示」という
最悪ケースは解消された。**67チーム全件で年度×性別セルの最大人数を実測したところ、
全体最大は `nssu` の37名**（次点: 中部電力愛知24名、東京ガス20名、東ソー南陽20名、
ワタキューセイモア17名）。`nssu` が最悪ケースであることが確認できたため、
**上限なしで実装する**（絞り込みは不要と判断。実際のビルド結果を見てから必要なら追加）。

### noindex 判定との関係（確認済み・変更不要）

メンバー節を足しても `matchCount` は変わらないため、`TEAM_INDEX_MIN_MATCHES = 5` 未満の
薄いチームは「メンバーが表示されるが noindex」になり得る。SEO目的（メンバークエリの受け皿）
との整合を実測で確認した結果、**67チーム中 noindex は3チームのみで、その3チームは
いずれも大会成績側のメンバーも0件**。つまり**メンバー節が表示されるチームは全て index 対象**で、
noindex 側の調整は不要。

### FAQ / title・description（決定: 4パターンの具体文言）

`hasStLeague`（STリーグ成績表を出すか）と `hasRoster`（年度別メンバー節が1件でもあるか、
新設の判定）は独立な軸なので、組み合わせは4通り。それぞれの title を以下のとおり決める
（`description` も同じ分岐に合わせて「メンバー」の有無を反映させる）。

| hasStLeague | hasRoster | title |
|---|---|---|
| true | true | `${teamName}｜STリーグ出場成績・メンバー \| ソフトテニス情報`（既存のまま） |
| true | false | `${teamName}｜STリーグ出場成績・順位 \| ソフトテニス情報`（既存のまま） |
| false | true | `${teamName} 成績・メンバー \| ソフトテニス情報`（**新規**。`nssu`が該当） |
| false | false | `${teamName} 所属別成績 \| ソフトテニス情報`（既存のまま。現状データでは到達不能） |

各パターンの該当チーム（**実装後に全67ページの `getStaticProps` を実行して確認**）:

- `true/true`: **60チーム**。
- `true/false`: **6チーム**（`fujitsu`・`iryohojin-kokoro`・`jr-east-morioka`・
  `jx-saganoseki`・`ome-shinkin`・`takikawa-city`）。初稿の「理論上の稀なケース」ではなく
  実データで発生するので、この分岐は必ず動く。内訳は2種類:
  大会データが1件も無いチーム（`iryohojin-kokoro`・`jx-saganoseki`・`takikawa-city`）と、
  **団体戦のチーム単位エントリーしか無いチーム**（`fujitsu`・`jr-east-morioka`・
  `ome-shinkin`。下記「既知の制約」参照）。
- `false/true`: **1チーム**（`nssu`）。
- `false/false`: **0チーム**。ただし「STリーグ非出場 × 団体戦のチーム単位エントリーのみ」
  という組み合わせなら理論上到達し得る（`stats.length > 0` でも `hasRoster=false` が
  起こり得ることが `fujitsu` で判明したため、初稿の「到達不能」は撤回）。フォールバックとして残す。

### 既知の制約: 団体戦のチーム単位エントリー

団体戦のファイルでは `entries[].playerIds` が選手ではなく**チームを指す pid**
（例: `FUJITSU_東京都`、`日本体育大学`）になっていることがある。年度×性別への紐づけを
`results[].playerIds` / `matches[].pair` 経由で行う以上、この形式のファイルからは
選手を拾えない。また participants 側に氏名が無い（`lastName`/`firstName` が `null`）
チーム pid が混ざるため、**氏名が空の pid はメンバーから除外する**ガードを入れている
（これが無いと `nssu` 2026年度女子に「null null」が1件混入する）。

`fujitsu`・`jr-east-morioka`・`ome-shinkin` はこの理由でメンバー0件。改善するには
participants と大会ファイルの年度・性別を直接結ぶ別経路が要るため、本設計の範囲外とする。

FAQ (`faqItems`) は現状 `hasStLeague` でのみ生成しているが、`hasRoster` に条件を切り替える。
既存のSTリーグ前提の質問文言（「{teamName}のSTリーグのメンバーは確認できますか？」）は
STリーグ非出場チームに出すと文脈が合わないため、**出典を問わない中立な文言に書き換える**。

- 質問例: `${teamName}のメンバーは確認できますか？`
- 回答例: `${teamName}の年度別メンバーを掲載しています。大会成績・STリーグ出場記録から
  確認できた選手を年度・男女別にまとめています。`

STリーグの成績表（W-L・順位・区分）に関するFAQ項目は `hasStLeague` 判定のまま残す
（メンバーFAQとは別項目として扱い、統合しない）。
