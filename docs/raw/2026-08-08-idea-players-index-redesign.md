# アイデア: 選手一覧ページ（/players）の再設計

## 状況

**2026-08-08 実装済み**（実機 `npm run build` は未実行）。発散フェーズから始めたが、調査の過程で
「ページの前提そのものが誤っていた」ことが判明したため、そのまま改修まで通した。

## 目的

`/players` を「選手を探す入口」として機能させる。改修前は SEO・UX・パフォーマンスのいずれの面でも
入口として働いておらず、さらに**ページの名乗り自体が事実と異なっていた**。

## 出発点でわかったこと（実測）

### 1. 「同姓同名選手の一覧」は実装の誤解だった（最大の発見）

生成側の変数名 `sameNameGroups`（`scripts/generate-players-json.mjs`）は、実際には
**全収録選手を氏名でグループ化したもの**にすぎない。

- `count` = 同名人数ではなく**出場した大会カテゴリ数**
- `differentTeams` = 同名別人の所属ではなく**その選手のキャリア変遷**

実例（`players-search.json`）: 松田拳弥 / 所属「東北, 法政大学, 尾上, 尾上中学校, 平川市スポ少」
＝ 1 人のキャリア変遷 ＋ **同一校の表記ゆれ 3 種**（尾上 / 尾上中学校 / 平川市立尾上中学校）。

決定的な検算: 全 9,391 組のうち「複数所属」は 4,512 組あるが、実際の同姓同名を記録した
`data/players/homonyms.json`（65 件）と **1 件も重ならない**。

つまり冒頭の警告ボックス「同じ名前でも異なる選手の可能性があります」は、ほぼ全訪問者に対して
**事実と異なる警告**を出し続けていた。`docs/ui/deliverables/04-site-structure.md` でも
`/players` は「選手入口(検索)」と定義されており、実装が承認済み構造からドリフトしていた。

### 2. パフォーマンス

| 項目 | 実測（改修前） |
|---|---|
| `out/players/index.html` | 1,452,245 B（カード 97 枚に全大会記録を埋め込み。DOM 18,207 要素） |
| `players-search.json` | 2,943,677 B を `useEffect` で**マウント時に無条件** fetch |

検索しない訪問者にも検索インデックスを配っていた。

### 3. 内部リンクのハブとして機能していなかった

| | 件数 |
|---|---|
| 収録選手（`data/players/index.json`） | 18,543 |
| 結果ページ実在（`count>=5`） | 1,917 |
| `/players` から張られるリンク | **97**（5.1%） |

`docs/wiki/players-pages.md` は選手結果ページの GSC「クロール済み - インデックス未登録」に対し
「内部リンク追加は頭打ち」として noindex 選別に踏み切った経緯を記録しているが、
**一覧ページ自体は手つかず**だった。

### 4. ドキュメントのドリフト

| wiki 記載（改修前） | 実測 |
|---|---|
| min20 = 73 組 | 97 組 |
| 検索インデックス 8,174 組 / 2.7MB | 9,391 組 / 2.9MB |
| 結果ページ「約 8,000 組」 | 1,917 枚 |

## ユーザーが興味を持った点

初手は「players/ の選手一覧ページを改良したいがいろんな観点で改善案を検討してほしい。
SEOもそうだが、UXや見た目などもいろんな観点でできる限り改善案を出してほしい」。
提示した改善案に対して「**懸念点がなければすべて対応したい**」。

## 検討の分岐点（3 つの懸念とその決着）

### 懸念1: 姓の頭文字での分割ページ（当初案 F）→ **取り下げ**

`docs/wiki/seo.md` は「入口を1ページに集約し、重複ページ自体を作らない」を一貫方針としており、
`/rankings` も「年度×種目×男女で URL を切らない＝薄いページの量産と枠競合を構造的に回避」と明記。
さらに実測で**姓の頭文字は 342 種、うち 243 種が 5 件未満**＝まさに薄いページの量産になる。

→ 代替として **1 ページ内で全 1,917 人にリンク**する案に差し替えた。名前のみなら約 93KB で収まり、
方針とも整合し、リンク本数は 97 → 1,917（19.8 倍）。

### 懸念2: 一覧への全国大会優勝バッジ → **見送り**（ユーザー判断）

`playerstats:public` が `prebuild` に入っておらず `public/data/player-stats/` は空。
`getStaticProps` でエンジンを直接叩くとビルド時間が約 40 秒増える。
なお表の「最高成績」列は大会結果データ（`res.tournament.label`）由来でエンジンを呼ばないため、
追加コストゼロで実装できたのでこちらは入れた。

### 懸念3: SSR から大会記録全文を削る → **削る**（ユーザー判断）

内容は選手結果ページと完全重複でカニバリ側（seo.md #2）。P3「一覧では要約」にも沿う。

## 実測結果（改修後）

`react-dom/server` でページを直接レンダリングして計測（サンドボックスは Linux 用 SWC バイナリを
取得できず `next build` が走らないため）。

| 指標 | 旧 | 新 | |
|---|---|---|---|
| HTML 非圧縮 | 1,452,245 B | 414,534 B | -71% |
| **HTML gzip** | **55,101 B** | **54,267 B** | **ほぼ変わらない** |
| DOM 要素数 | 18,207 | 5,798 | -68% |
| 検索インデックスの無条件 fetch | 必ず 334KB(gzip) | 0（操作時のみ） | -334KB |
| 内部リンク | 97 | 1,917 | 19.8 倍 |

**当初の見積もりの訂正**: 検討時には「HTML 1.45MB → 100KB 程度でパフォーマンスが大きく改善」と
説明したが、実測すると**旧 HTML は繰り返しが多く gzip が極めてよく効くため、転送量としての
改善は HTML 側にはほぼ無かった**（55.1KB → 54.3KB）。実際の転送量の改善は検索インデックスを
無条件に配らなくなった分（-334KB gzip）で、HTML 側の利得は転送ではなく**パース・DOM 構築コスト**
（要素数 -68%）に出る。今後この数字を引用するときは取り違えないこと。

## 実施した改修

生成（`scripts/generate-players-json.mjs`）:

- `players-index.json` 新設（`featured` 上位 200 人の要約 ＋ `all` 全 1,917 人のリンク用）
- `players-min20.json` 廃止（`git rm`）
- `players-search.json` の `differentTeams` を `team` ＋ `teamCount` に縮約

ページ（`src/pages/players/index.tsx`・全面書き換え）:

- 同姓同名フレーミングと警告ボックスを撤去、役割を入口として定義し直し
- 表形式（上位 200 人）＋ 全 1,917 人のリンク一覧
- 検索インデックスを focus / 入力時に遅延ロード、`useDeferredValue`、50 件ずつの段階表示
- `?q=` の URL 反映（shallow・400ms デバウンス）
- JSON-LD を `CollectionPage` + `ItemList` へ（**ビルド日の偽日付を除去**）、`WebSite` + `SearchAction` 追加
- `MetaHead` の `type` を `article` → `website`、title / description を検索意図に合わせて書き換え
- ハイライトを全語対象に修正（旧は 1 語目のみ）
- `aria-live="polite"` / `type="search"` / `role="search"`
- 所属は最新 1 件＋「他 N」表示（表記ゆれの露出を止める）
- stretched link と `decoration-wavy` を撤去、render 中の破壊的 `sort()` を解消

## 課題・未解決

- **実機 `npm run build` が未実行**。サンドボックスでは `@next/swc-linux-arm64-gnu` が空ディレクトリで
  ダウンロードもできない。`tsc --noEmit` と `eslint` は通過済み、描画は `react-dom/server` で検証済み。
- **読み仮名データが存在しない**ため、かな・ローマ字検索と五十音の見出し・並びが実装できない。
  現状は名前順（`localeCompare('ja')`）＝実質コードポイント順で、日本語話者の期待する五十音順ではない。
  読み仮名を持つなら選手マスタ（`data/players/index.json`）への列追加が必要。
- 0 件時の「もしかして」（編集距離）は未実装。読み仮名が無い以上、打ち間違い救済の価値は相対的に高い。
- 所属チーム名の表記ゆれ正規化（尾上 / 尾上中学校 / 平川市立尾上中学校）は名寄せ側の課題として残る。
- ブラウズ軸は「出場数」「名前順」のみ。都道府県軸は元データに `prefecture` が入っていないため不可。
  世代（`generation`）・直近出場年度は導出可能なので、次に足すならこの 2 つ。
- GSC での効果測定（内部リンク 19.8 倍が選手結果ページのインデックス登録率に効くか）。
  これが本改修の本命仮説なので、noindex 選別・高校 M4 検証と同じ枠組みで観測したい。

## 目指したい方向性

まずは実機ビルドと GSC 観測。ブラウズ軸の追加（世代・直近出場年度）と読み仮名データの整備は、
GSC の結果を見てから優先度を決める。
