# アイデア: 今日のソフトテニスライブ配信一覧（/live/）の自動収集

## 状況

Idea Backlog。**発散フェーズ（2026-09-06 起票・未着手）**。
提案は「YouTube Data API で今日開催の大会に紐づくライブ配信を自動収集し `/live/` に出す」。
このメモは、その提案を**既存構成とこのリポジトリの作法に照らして評価した結果**であり、
実装方針はまだ確定していない。決めるべき論点は「未解決」節に集約した。

## 目的

- 大会当日に「今どこで配信しているか」を1か所に集約し、サイトの入口にする。
- 最終的には「今日のソフトテニス」（今日の大会・今日の結果・今日の配信）へ広げる（提案 §17）。

## わかっていること（既存実装の調査結果・2026-09-06）

### 大会データと「今日開催」の導き方

- 大会マスタ: `data/tournaments/index.json`（`tournamentId` / `generationId` / `label` /
  `isMajorTitle` / `officialUrl`）。
- 開催情報: `data/tournaments/information/<tournamentId>.json` は**年度ごとの配列**で、
  `year` / `location` / `startDate` / `endDate` / `label` / `categories` / `venues` /
  `source` / `sourceUrl` / `guidelineUrl` / `note` / `status`（型は `src/types/tournament.ts`）。
- 読み込みは `lib/tournamentData.ts` の `loadTournamentIndex()` / `loadInformationMap()` に既にある。
- 「今日開催」は `startDate <= today <= endDate` で出せる。**同型の先行実装が2つある**:
  - `lib/upcomingInternational.ts` — `today` を引数で受け取る fs 非依存の純関数（テスト可能）。
  - `lib/highschoolInProgress.ts` — 会期中の勝ち上がりを都道府県別・学校別に引く索引（fs あり）。
- 補助の日程ソース: `data/local-sources/jsta-yearly-events/<年>.json`（JSTA 年間予定・年35件前後）、
  `data/tournaments/local_index.json`（地域大会41件）。

**実測（`information` 全164レコード）**:

| 指標 | 値 |
|---|---|
| `startDate`/`endDate` を持つレコード | 164 / 164（100%） |
| 2026年に大会が登録されている日 | **100日 / 365日 = 27.4%** |
| 同じ日に重なる大会の最大数 | 6件 |
| 2026-09-06（起票日）の該当 | 1件（全日本学生選手権 2026-09-05〜09-09） |

→ **年間の約7割の日は「今日の大会」が0件**になる。`/live/` を単独ページにすると、
空ページが常態化する。これが設計上いちばん効く制約。

### ビルド・配信の構成

- Next.js **Pages Router**。本番は `output: 'export'` の**静的エクスポート**（`next.config.mjs`）。
  **ランタイムが無い**（API routes は開発時のみ）。
- Cloudflare Pages が push 契機でビルド（`wrangler.toml` / `pages_build_output_dir = "out"`）。
  `prebuild` は15段の直列チェーン（正準化・ゲート → playerStats キャッシュ → 生成）で**重い**。
  seo.md #11 の Open Question に「1日1回のビルド・デプロイの運用コスト。`prebuild` が全大会の
  player stats を再生成するため重い」と既に書かれている。
- GitHub Actions は2本: `checks.yml`（push / PR / 週次 cron / 手動。**ゲートと報告を分離**、
  `permissions: contents: read`）、`review-snapshot.yml`（週次・書き戻し専用・`[skip ci]` 付き）。
- **リポジトリ Secrets は現状ゼロ**。`YOUTUBE_API_KEY` はこのリポジトリ初の secret になる。
- 生成物の扱い: `public/data/players-search.json` 等は**ビルドで生成し git 追跡しない**
  （`git ls-files public/data` は beta-matches の67件のみ）。**`live.json` もこの型に乗せられる**。
- 一方 `review-snapshot.yml` は「**生成物を書き戻すな。書き戻すのは再生成できない記録だけ**」と
  明記している（sitemap.yml が2日で無効化された先例）。**`live.json` をコミットして毎回 CF を
  再ビルドする案は、この原則と正面から衝突する。**

### YouTube の既存利用

- API 利用は**ゼロ**。`lib/videoReview.ts` / `lib/youtubePlayback.ts` はユーザーが貼った URL の
  パースと埋め込みだけ。`match_video_sessions` 等は score 側のテーブル。
- `open-questions.md`「YouTube / 動画レビュー」に運用ルール未定の項目が残っている。

### quota（YouTube Data API v3・既定10,000 units/日）

`search.list` = 100 units、`videos.list` = 1 unit（最大50 id/回）、`playlistItems.list` = 1 unit。

| 設計 | 1日の消費 |
|---|---|
| 発見(search) を1日2回 × 大会1件 × クエリ3本 + 状態更新 `videos.list` 48回 | **約 650 units（6.5%）** |
| 同上・最繁忙日（同日6大会） | 約 3,650 units（37%） |
| **30分ごとに search を回す（提案 §9 をそのまま実装）** | **28,800 units（288%）→ 破綻** |

→ **「発見は日次の search、状態更新は `videos.list` だけ」**に分けるのが必須。
既知チャンネルの uploads playlist 走査（`playlistItems.list` = 1 unit）を足しても誤差。

### このリポジトリの作法で、提案がそのままだと引っかかる点

1. **絵文字禁止**（AGENTS.md「UI の表記ルール」・`eslint.config.mjs` で `src/**` に error）。
   提案の `🔴 LIVE` / `📺 ライブ配信` はそのままでは通らない。装飾は inline SVG か CSS。
2. **新規ページ種別を足すときの手続き**（seo.md「新規ページ追加時の運用」）。
   `/live/` は重複マップへの行追加＋制御手段（インテント分割 / canonical / noindex /
   内部リンク集約）の明記が要る。
3. **薄いページ・重複ページを作らない**という強い先例が2つある。
   - ADR-010: 年度ごとに増える結果記事を廃止し大会ハブへ集約。
   - seo.md #11: 会期中SEOで**新規URLを作らず**、既にインデックスされている
     ハブ1枚＋都道府県94枚＋学校243枚を更新して受けた。
4. **LLM を掲載経路に入れるなら ADR-012 の型に従う**（LLM が書いたものは機械照合を通ったものだけ
   公開し、公開条件を prebuild が強制する）。提案 §4 の「LLM だけを信頼しない」は同じ思想。
5. **検出器の置き場**（`prebuild` はゲートのみ、合否の付かない一覧型は `checks.yml` の報告側）。
6. `next-sitemap` は `getStaticProps` を持つページを自動列挙する（`additionalPaths` 追記は不要）。
   `lastmod` は**ビルド日でクランプ**する前例あり（未来日は鮮度シグナルが効かない）。

## 未解決（決めないと実装に入れない）

### Q1. 鮮度をどう出すか — 静的エクスポートとの本質的な衝突

「現在ライブ中」をリアルタイムに主張するには、以下のどれかが要る。

| 案 | 中身 | 代償 |
|---|---|---|
| A. ビルド時生成 | `scripts/generate-live-json.mjs` → `public/data/live.json`（既存の生成物と同じ型・git 追跡しない） | 鮮度＝デプロイ頻度。prebuild が重い（seo.md #11 の既知課題）。CF Pages のビルド環境に API キーが要る |
| B. 生成物を書き戻す | GH Actions が `live.json` をコミット → CF が再ビルド | **「生成物を書き戻すな」原則に反する**。重いビルドが1日48回 |
| C. ランタイムを入れる | Cloudflare Pages Functions + KV（`wrangler.toml` は既にある）、または既存依存の Supabase | サイト初のランタイム面。**アーキテクチャ変更なので ADR 相当** |

**現時点の推奨**: MVP では**リアルタイムの「LIVE中」を名乗らない**。
提案 §13 の最優先が「存在しない配信を掲載しない／過去配信をライブ中と表示しない」である以上、
根拠を持てない状態表示をしないほうが提案の趣旨に合う。出せるのは
「本日の配信予定（開始予定時刻つき）」「最終確認: HH:MM」までにする。
C は、供給量が確認できてから独立の判断として扱う。

### Q2. 掲載面 — `/live/` を作るか、既存ページに差すか

年間7割の日が0件（上の実測）なので、`/live/` を「今日の配信一覧」として作ると空ページが常態化する。
選択肢:

- **B1. 新規URLゼロ**: 大会ハブ・年度別結果ページに「ライブ配信」ブロックを差す。
  seo.md #11 と同じ型で、作法上いちばん摩擦が少ない。ただし提案の `/live/` は満たさない。
- **B2. `/live/` を「今日のソフトテニス」入口として作る**（提案 §17 の最終形を先に器にする）。
  配信が0件でも「今日開催中の大会」「直近で結果が入った大会」「次の大会」で埋まるので空にならない。
  seo.md に重複マップの行が要る。
- **B3. 供給が確認できるまで作らない**。

**現時点の推奨**: B1 を先に出し、供給量の実測後に B2 を判断する。

### Q3. 供給量が未知（これが最大のリスク）

「ソフトテニスの大会が YouTube でどれだけ配信されているか」を**このリポジトリは1件も持っていない**。
機能の価値はここだけで決まるのに、根拠が無い。
このプロジェクトの習慣（実データで検証してから作る）に従うなら、**最初にやるのは実装ではなく実測**:

APIキーを取り、**収集だけして掲載しない dry-run** を1〜2週間回す（GH Actions cron →
`$GITHUB_STEP_SUMMARY` と artifact に出す。`checks.yml` の「報告のみ」と同じ置き方）。
測るのは「1日あたり実在した配信数」「大会に紐づけられた割合」「誤検出の中身」。
2026-09-05〜09-09 の全日本学生選手権が最初の観測機会になる。

### Q4. その他

- 大会が0件の日でも「ソフトテニス」単独検索で拾うか（提案 §2 はノイズを理由に非推奨としている）。
- チャンネル信頼度（`official` / `association` / …）の初期値をどこから作るか。
  実測前に分類表を作っても埋まらない可能性が高い。
- 大会紐づけの confidence 閾値。提案 §5 の「確信が無ければ `tournamentId: null`」は妥当。
- 掲載を止める手段（明らかな誤掲載が出たときの除外リスト）。`ignored-documents.json` の先例がある。

## 追記（2026-09-06）: 抽出精度と収益の見積もり

「精度・ユーザーメリット・売上はどれくらい出るのか」への回答。**測れたものと、測れないものを分けて書く。**

### 精度: 大会名が競技を特定しない（実測）

提案 §2 の「大会名で YouTube 検索する」方式が、このサイトの大会名では成立しにくい。
2026年の全レコード（延べ開催日数156日）を大会名で分類した結果:

| 大会名の型 | 延べ日数 | 割合 | 大会数 |
|---|---|---|---|
| 名前に「ソフトテニス」を含む | 15日 | **9.6%** | 8 |
| **他競技と名前を共有する総合大会名** | 59日 | **37.8%** | 19 |
| その他（全日本◯◯選手権など競技固有だが語に競技名なし） | 82日 | 52.6% | 4以上 |

**他競技と名前を共有する19大会には、配信される可能性が最も高い大会が集中している**——
`令和8年度 全国高等学校総合体育大会`（インターハイ＝全競技）、`第57回 全国中学校大会`（全中）、
高校・中学の各ブロック大会（`第79回 全九州高等学校競技大会` `第47回 北海道中学校体育大会` 等）。
しかも**他競技の同名大会は会期まで重なる**ので、ノイズが最も増える時期が、こちらが最も
配信を拾いたい時期と一致する。

これは新しい発見ではなく、**seo.md「大会名の表記と検索語の乖離」で既に実証済みの構造**
（「全中」は全競技共通の略称で、Google Trends が競技横断の略称に使えないと結論した箇所）。
検索の向きが逆（サイト→YouTube）になっただけで、同じ壁に当たる。

**緩和策と、その代償**:

- クエリに「ソフトテニス」を足す（`大会名 ソフトテニス`）→ 精度は上がるが、**配信タイトルに
  「ソフトテニス」が入っていない配信を落とす**（例: `R8インターハイ 男子団体 決勝`）。
  精度と再現率のどちらを落とすかの選択で、**どちらがどれだけ効くかは実測しないと分からない**。
- 略称マスタの流用: `index.json` の `searchLabel` / `searchAliases` はクエリ生成にも
  タイトル照合にも使えるが、**設定済みは31大会中3大会だけ**（インカレ・王座・全中）。
  流用するなら先に埋める作業が要る。`lib/nationalTitles.ts` にも別系統の aliases が6件ある。
- チャンネル起点に切り替える（既知の連盟・主催チャンネルの uploads を見る）→ 精度は跳ね上がり
  quota も安い（`playlistItems.list` = 1 unit）が、**既知チャンネルの一覧をこのリポジトリは
  持っていない**。最初の一覧をどう作るかが未解決。

**結論**: 精度は「今は見積もれない」ではなく、**大会名起点だと構造的に低くなることが分かっている**。
本命はチャンネル起点で、そのためのチャンネル一覧づくりが実質的な第一歩になる可能性が高い。

### 収益: `/live/` 単独では、そもそも広告が出ない

実装前に効く制約が2つある（どちらも `lib/ads.ts`）。

1. **ページ種別の許可リスト**。`getPageType()` が知らないパスは `other` に落ち、`other` は
   `FOOTER_AD_PAGE_TYPES` から除外されている。`/live/` は種別を足さない限り**広告ゼロ**。
2. **`FOOTER_AD_MIN_CONTENT_CHARS = 400`**（`<main>` の本文400文字未満なら枠を出さない。
   AdSense の「コンテンツのないページ」規定への歯止め）。配信1件あたりの本文は概算80〜100文字
   （タイトル・配信者・大会名・時刻）なので、**閾値を超えるには常時3〜4件の配信が要る**。
   年間7割の日は今日の大会が0件（本メモ上部の実測）なので、多くの日は閾値未満になる。

さらに構造的な問題として:

- **`/live/` は離脱ページである**。リンク先が youtube.com なので、機能として成功するほど
  ユーザーはサイトから出る。これは seo.md #11 が**問題として直した挙動そのもの**
  （会期中の大会ハブが「最新情報は大会公式サイトへ」と書いて訪問者を逃がしていた）。
  回遊＝PV増＝収益、という [circulation-verification.md](../wiki/circulation-verification.md) の
  目的関数と、この機能の成功指標（YouTubeへのクリック）は**向きが逆**。
- **増える広告面は1枚**。直近の収益施策（フッター枠の全面展開）は掲載面を
  433枚（9.9%）→ 約3,900枚（89%）へ**9倍**にした。`/live/` はそこへ +1枚。
  収益 ≒ 面 × PV × RPM なので、1枚で効かせるには PV 側が桁で効かないといけない。

**一方、B1（大会ハブ・年度別結果ページへの「ライブ配信」ブロック差し込み）は向きが違う**。
差し込み先は**既に広告面**であり、**会期中は検索需要のピーク**（seo.md #11 が実証済み）。
新規URLゼロ・広告設定の変更ゼロで、既存面の滞在・回遊に効く方向に働く。
収益の観点では B1 と B2 は同じ機能の2つの見せ方ではなく、**逆方向の施策**として扱うべき。

### 売上の絶対額は、このリポジトリのデータでは出せない

`docs/wiki/monetization.md` は相対値（「旧水準の約1割」「想定より出たので拡大」）しか持たず、
PV・ページRPM・収益の絶対値はリポジトリに無い（AdSense と GA4 の管理画面にしかない）。
したがって見積もりは、**ユーザーが持っている2つの数字を入れれば5分で出せる形**にしておく:

```
/live/ の月間収益 ≈ (月間PV) × (ページRPM) ÷ 1000
損益分岐         ≈ 実装工数 + 恒常運用（quota監視・誤掲載対応・APIキー管理）
```

必要なのは (a) AdSense のページRPM（既にユニット別に取れる）、
(b) `/live/` が取れそうな月間PV。(b) の当たりを付ける最も安い方法は、
**GSC で「ライブ」「配信」「中継」を含むクエリの現状（表示回数・平均掲載順位）を見ること**。
ただし seo.md「GSC の不在は需要の不在ではない」の通り、**表示回数0のクエリは行に出ない**ので、
0件だったら「需要が無い」ではなく「SERP を直接見る」へ進む必要がある（全中のときと同じ手順）。

### ユーザーメリット（定性）

- **有る**: 会期中に「今どこで見られるか」を探す手間は実在する。大会ページから配信へ1クリックで
  行けるのは素直に便利で、B1 ならサイトの既存導線（大会 → 結果 → 選手）に自然に足せる。
- **薄い**: 「今日のソフトテニス配信」を能動的に探す人は、まず YouTube 内で検索する。
  サイトが勝てるのは「大会を知っている人が、その大会の配信を探す」場面であり、
  それは**大会ページで受けるべき需要**（＝ B1）で、`/live/` という別ページである必然性は弱い。
- **前提**: いずれにせよ、配信が実在しなければメリットはゼロ。**Q3 の実測が全ての前提**という
  評価は変わらない。
