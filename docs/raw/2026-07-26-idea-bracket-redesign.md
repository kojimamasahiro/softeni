# アイデア: トーナメント表の作り直し（分割表示・両側対戦・仮定の勝ち上がり）

## 状況

Idea Backlog。発散フェーズ。2026-07-26に着想。
シード（`entries[].type`）が入力できるようになった直後、インターハイ2026の
大会結果ページでトーナメント表が実質機能していないことが判明したのが発端。

## 目的

現在の `src/components/TournamentBracket.tsx`（926行）は **`matches` のツリー構造**
（`nextMatchId` / `prevMatchIds`）を決勝から逆算して描画する。この方式には次の限界がある。

1. **開催前は成立しない**。次ラウンドの試合レコードがまだ無いため `nextMatchId` が
   1件も付かず、全試合が「決勝候補」と判定されて独立した1試合ツリーが並ぶだけになる。
2. **1回戦を戦わない枠が見えない**。シード・足長（`extra`）は `matches` に現れないため、
   インターハイ2026男子ダブルスでは316組中120組（1回戦を戦う分）しか表示されない。
3. **参加者が多いと1画面に収まらない**。316組・512枠のドローを左から右への一方向で
   描くと横に極端に長くなる。

## ユーザーが興味を持った点

> 今後のアイデアとしてトーナメント表を作り直したい。
> 参加選手が多い場合の表示の見せ方を検討する必要があるが、
> ベスト8までの山とベスト8からの山を分けるなど分割したい。また、今は左側からの表しかないが
> 両側から勝ち上がりがわかる見た目にした方がいい気もしている。
> 見た目に関しては色々検討したい。

> **一番やりたいことは、まだ結果が出ていなくても仮定で勝った場合の勝ち上がりで
> 誰と誰が対戦するかを確認できるようにしたい。**

最後の一文が本命。他は見せ方の検討事項。

## やりたいこと（3つ）

### A. 仮定の勝ち上がりシミュレーション（最優先）

結果が未入力でも、任意の枠を「勝ったことにする」と、その先で誰と当たるかを辿れる。
読者が自分の応援するペアの行く先を追える。当サイトが試合単位のデータを持っているからこそ
できる体験で、静的なトーナメント表 PDF では絶対に再現できない。

### B. 山の分割表示

「ベスト8までの山」と「ベスト8からの山」を分けるなど、大きなドローを分割する。
316組を1枚で見せようとしないことで可読性を確保する。

### C. 両側から中央へ向かう見た目

現在は左→右の一方向のみ。左右から中央（決勝）へ向かう対称レイアウトにすると、
勝ち上がりの構造が直感的になる。見た目は他案も含めて検討したい。

## わかっていること

- **ブラケットは `entryNo` ＋ `entries[].type` から完全に復元できる**（2026-07-26 実証）。
  - `entryNo` はドロー順。1回戦は必ず隣接同士で組まれる。
  - `type` が `seed` / `extra` の枠は1回戦が不戦勝なので、スロット列に bye を差し込む。
  - こうして組んだ 512 枠のブラケットで「2つの枠が何回戦で当たるか」を計算し、
    **インターハイ2026男子ダブルスの実データ128試合と 100% 一致**した。
  - つまり **`matches` に依存せずトーナメント表を描ける**。A/B/C いずれの前提もこれで満たせる。
- `type` の内訳（インターハイ2026男子ダブルス）: seed 60 / packing 120 / extra 136＝316組、
  ブラケットは 512 枠。IH2025 も同じ構造（seed 60 / packing 120 / extra 136）。
- 現行 `buildBracket()`（`TournamentBracket.tsx` 173-408行）は `matches` のツリー前提なので、
  ここを差し替える形になる。**完了済み大会（`nextMatchId` あり）の描画を壊さないこと**が
  移行時の主なリスク。`nextMatchId` があれば従来経路、無ければ復元経路、という二段構えが
  安全側。
- シード情報が入るようになったのは 2026-07-26 の入力ツール改修（`buildEntriesMeta`）以降。
  **それ以前に入力された大会には `type` が無い**ものがあり（`null` 5,428件）、
  復元経路が使えるとは限らない。

## 課題・未解決

- **`type` が無い過去大会をどう扱うか**。`matches` から `calculateEntryType()` 相当を
  逆算できるが、完了済み大会は `nextMatchId` があるので従来経路で足りる可能性が高い。
- **仮定の勝ち上がり（A）の状態管理**。静的サイト（SSG）なのでクライアント側の状態になる。
  URL に載せて共有可能にするか、その場限りにするか。共有できると SNS 導線になりうる。
- **B の分割単位**。ベスト8で切るのが良いか、ラウンド数で切るか、ブロック（山）で切るか。
- **C のレイアウト**。左右対称にすると横幅は半分になるが縦が伸びる。モバイルでの見え方が要検討。
- 既存の打ち切り表示（`abandonedAfterRound`）との整合。

## 目指したい方向性

まだ発散フェーズ。ただし **A（仮定の勝ち上がり）が本命**で、B・C は見せ方の検討事項という
優先順位はユーザーの発言から明確。

実装順序としては、まず **`entries` からブラケットを復元する関数を `lib` に切り出して
単体で検証**（IH2025・IH2026の全種目で従来描画と一致するか）し、それが通ってから
`TournamentBracket.tsx` に組み込むのが安全。

  10 件あるため `prebuild` を止めるのは割に合わないという判断（`severity` の概念自体を
  `validate-entries.js` に新設した）。
- 該当 10 大会は前哨戦ブロックの「◯回戦で当たる」が出なくなる（欠落側に倒れる）。

## 追記（2026-07-31 その2）: A「仮定の勝ち上がり」の意味の確定

A を「読者が勝者を選んでシミュレートする機能」と解釈して `advancementPath`（各ラウンドで
当たりうる相手の集合）を作ったが、**これは過剰な解釈だった**。ユーザーの意図:

> 仮定の勝ち上がりというのは、実際にどちらが勝利したかを決めるのではなく、
> トーナメント表として線が繋がっていればいい。

つまり A は**インタラクション機能ではなく、描画の完全性の話**。結果が未入力でも
ブラケットの全ラウンド・全枠と接続線が描かれていれば、読者は「この山を勝ち上がると
あの山の勝者と当たる」を**目で辿れる**。それで足りる。

### この確定で消える論点

- **状態管理は不要**。「どちらが勝ったか」をクライアントで保持しないので、
  `useState` も URL 共有も要らない。SSG のまま静的 HTML で完結する。
  raw の「課題・未解決」にあった「A の状態管理」「URL に載せて共有可能にするか」は**消滅**。
- **`advancementPath` は A の本体ではない**。「候補 158 組」のような集合を出す必要は無い。
  ただし前哨戦ブロック（`meetingRoundIndex`）と同系統の便利関数として残す価値はあるので
  削除はしない。A の実装には使わない。
- **必要なのは「席順 → ラウンド×試合枠のツリー」**。`buildBracketLayout` が返す `slotOf` /
  `size` / `totalRounds` から、各ラウンドの試合枠と、それぞれの供給元（前ラウンドの 2 枠）を
  組み立てる関数があればよい。試合結果はあれば埋め、無ければ空欄のまま線だけ繋ぐ。

### 「シード未入力で復元不可」の内訳を調べ直した（2026-07-31）

当初「復元不可 132 大会＝シード未入力の古いデータ」と一括りにしていたが、
ユーザーの指摘（「シード未入力とはどういうことか。ラウンドロビンということか。
完了しているものは matches から type が分からないか」）を受けて分解したところ、
**3 つの別物が混ざっていた**。

| | 大会数 | 復元できるか |
|---|---|---|
| bye 無しの 2 冪ドロー（全件 `packing`） | 36 | **できる**（実装済み） |
| 予選リーグを含む | 81 | できない（構造的に対象外） |
| 純トーナメント・完了済みで `type` が null | 15 | `matches` から逆算すれば可能 |

- **bye 無しドロー（36 大会）は実装のバグだった**。`seed` も `extra` も無いのは
  「シード未入力」だからではなく、出場数がちょうど 2 冪で **bye が 1 つも要らない**から
  （例: 地区大会の団体戦 16 校）。旧ガードはこれを一律に弾いていた。
  条件を「全件 `packing` **かつ出場数が 2 冪**」に変えて復元対象に含めた。
  検証: **1,670 試合すべて一致**。これで復元適用は 173 → **209 大会**、
  試合数は 18,901 → **20,571 件（不一致 0）**。
  - 「出場数が 2 冪」の条件は必須。予選リーグ大会もリーグ参加者に type が付かず全件
    `packing` になるため、これが無いとすり抜ける。実例
    `zennihon-senior/2025/doubles-over80-girls` は 31 組・全件 packing で、素朴に組むと
    padding 込み 32 枠＝2 冪になり**パリティ検査を通過して誤復元した**（実際に 3 試合
    不一致が出た）。出場数そのもの（31）を見れば弾ける。
- **予選リーグを含む 81 大会は復元対象外**。決勝トーナメントの枠はリーグの順位で決まり、
  `entryNo` のドロー順とは無関係。`calculateEntryType` もリーグ参加者には type を付けない。
  これは欠損ではなく**そもそも別の構造**なので、埋めようとしてはいけない。
- **残る 15 大会は `matches` から逆算できる**（ユーザーの指摘どおり）。純トーナメントで
  完了済み、1/2 回戦のラウンド名も揃っている。`tools/shared/normalize-core.js` の
  `calculateEntryType()` が「実対戦の初出ラウンド」から seed/packing/extra を判定する
  実装を既に持っているので、これを既存データに流せばよい。**未実施**。

### B・C との関係

A がこう定まると、B（山の分割表示）と C（左右対称レイアウト）は
**A と同じ「ツリー構造」への別の見せ方**でしかなくなり、A の後に純粋な描画の問題として
扱える。`opponentSlotRange` は B のブロック切り出しにそのまま使える。

## 追記（2026-07-31 その3）: 描画用ツリー `buildBracketTree` を実装

A が「線が繋がっていればいい」と確定したので、席順から**全ラウンドの枠を先に作り、
分かっている結果だけを後から流し込む**関数を `lib/bracketLayout.ts` に追加した。

```
buildBracketTree(layout, matches) -> { rounds: BracketNode[][], size, totalRounds }
BracketNode = { roundIndex, matchIndex, entries: [no|null, no|null], match, winner, bye }
```

`rounds[0]` が 1 回戦、最後が決勝。`rounds[r][i]` の供給元は `rounds[r-1][i*2]` と
`[i*2+1]` という単純な規則なので、描画側は接続線をこの添字だけで引ける。

### 実測（IH2026 男子ダブルス・開催前で 1 回戦の結果すら未入力）

| ラウンド | 枠 | 対戦確定 | 不戦勝 | 決着 |
|---|---|---|---|---|
| 1回戦 | 256 | 60 | 196 | 0 |
| 2回戦 | 128 | 68 | 0 | 0 |
| 3回戦〜決勝 | 64…1 | 0 | 0 | 0 |

**512 枠・9 ラウンドがすべて存在する**のが要点。旧 `buildBracket()` はここで
60 本の独立ツリーにしかならなかった。2 回戦の 68 枠が結果無しで確定しているのは、
足長同士（どちらも 1 回戦不戦勝）の対戦が席順だけで決まるため。

完了済みの IH2025 では全ラウンド 100% 埋まる（1回戦 60 + 不戦勝 196 → 決勝まで欠けなし）。

### 途中で一度間違えた点（重要）

最初の実装は「片側が null なら不戦勝」としていたため、**1 回戦の結果が未入力なのに
シードが 4 回戦まで勝ち上がってしまった**（IH2026 の 4 回戦に「対戦確定 28」という
有り得ない枠が出た）。片側 null には 2 種類ある:

- 相手の山にそもそも誰も居ない → 不戦勝が**確定**。上がってよい。
- 相手の山に居るが結果が未入力 → **未確定**。上がってはいけない。

正しくは「その側の山（スロット範囲）に居るエントリー数」を見る。0 なら空席、1 なら
戦わずに確定、2 以上なら供給元の勝者次第。これを `occupants()` で数えている。

### 検証

`scripts/verify-bracket-tree.ts`（`npm run bracket:verify:tree`）を追加。
**209 大会・20,571 試合すべてがツリーの正しいラウンドに配置され、欠落 0・ラウンド番号の
不一致 0**。空欄の枠は 11,274（未実施の試合。これは異常ではなく機能の目的そのもの）。

- 検証はラウンド**名**ではなく**番号**で比較している。`highschool-kyushu-block/2026/
  team-none-boys` は 16 校ドローで決勝まで「1〜4回戦」と表記しており、`roundLabelOf` の
  「準々決勝/準決勝/決勝」と一致しない。構造の誤りではなく表記の違いなので、
  **描画では実データの `round` 名がある枠はそれを優先すること**。
- 単体テストは `npm run bracket:test` が 15 ケースに増えた。

### 次にやること

- `TournamentBracket.tsx` の描画差し替え。`nextMatchId` があれば従来経路・無ければ
  `buildBracketTree` という二段構えの方針は変わっていない。
- 512 枠をどう画面に収めるか（B・C）。これは純粋に見せ方の問題として切り出せる。
- `type` が null の完了済み 15 大会の逆算（`calculateEntryType`）。未実施。

## 追記（2026-07-31 その4）: B・C の基準が決まった（1枚64枠・左右対称）

ユーザー決定。B（分割）と C（左右対称）は次の形に確定した。

> ベスト64は1枚になるような基準にしたい。
> できれば1枚ごとは拡大ができればいいのではないかと思っている。
> いわゆるPDFでの表のような形が理想

> いや、512の場合はベスト8までは1つの山にして、重複になるがまたbest64で1枚にしたい

### 決まったこと

- **1 枚 = 64 枠**（`SHEET_SLOTS`）。「ベスト64 が 1 枚に収まる」が基準。
- **山シート**: ドローを 64 枠ずつに割り、各山を**その山の代表が決まるまで**（64→1 の
  6 ラウンド）1 枚に収める。512 枠なら 8 枚で、各枚の中央がベスト8 を決める 6 回戦の枠。
- **ベスト64 シート**: 残り 64 組が決勝まで上がる 6 ラウンドを別に 1 枚。
  **山シートと 4〜6 回戦が重複するが、それは承知の上**（山を追う見方と終盤を俯瞰する
  見方は別物なので両方あってよい、というユーザー判断）。
- **左右から中央へ収束**。64 枠なら左 32・右 32、中央が決着の 1 枠。
- 1 枚ごとに拡大縮小できること。

モックは SVG に変更した（`scripts/preview-bracket-sheets.ts`）。線と文字だけなので

- スロット i の中心 y = `top + (i + 0.5) * ROW_H`

## 追記（2026-07-31 その6）: 線の引き方の欠陥 2 件を修正

ユーザー指摘。**どちらもリリース不可の欠陥**だった。

> シードがあると綺麗につながっていない。勝ち上がりの左右の線が太くなるが、
> 縦の線が太くなっていない。

### ① シードの線が繋がらない — 原因は 2 つあった

**(a) 線を引く判断に `entries`（確定した entryNo）を使っていた。**
`entries` は「今その枠に誰が入るか確定しているか」なので、結果未入力の大会では
2 回戦以降がほぼ全て null になり、**線そのものが引かれていなかった**。
線を引くべきかは席順だけで決まる構造の話なので、`BracketNode.present:[boolean, boolean]`
（上下それぞれの山にエントリーが居るか）を追加してこちらを見るようにした。
「結果ゼロでも線が繋がる」という機能の目的に対して、ここは根本的な設計ミスだった。

**(b) 不戦勝の枠でも出力 y を中点に寄せていた。**
紙のドロー表では、不戦勝の枠は**その選手の高さのまま真っ直ぐ次のラウンドへ通す**。
中点に寄せると線が折れ、シードの線が途中で切れて見える。各枠の「出ていく y」を
次の規則にした:

- 対戦がある枠 … 2 本の横線を縦線で繋ぎ、その**中点**から出る
- 不戦勝の枠 … 縦線を引かず、**居る側の高さのまま**通す

検証: IH2026 第1山のシード（entryNo 1）の線が `164 → 186 → 208` と同じ y=57.5 で
連続し、2 回戦の縦線（208, 57.5→105）で 1 回戦の勝者と合流することを確認。

### ② 勝ち上がりの縦線が太くならない

横線だけ太くしていたので、勝ち上がりの線が縦のところで途切れて見えていた。
縦線は**細く全体を引いた上に、勝者側の半分（勝者の y から中点まで）を太く上書き**する
ようにした。これで横 → 縦 → 横が 1 本の太い線として繋がる。

検証（IH2025 第1山）: 縦線 76 本中 38 本、横線 101 本中 38 本が太線。
決着した試合数と一致する。

### 再発防止

`present` の意味と「entries と混同してはいけない」ことを型のコメントに書き、
単体テストを 2 本追加した（結果ゼロでも present が両側 true になること／
空席の山が false になること）。テストは計 22 本。

### ③ 太線がシードの「根本」から始まらない（同日追加指摘）

> シードや足長が勝った場合の太くなる線が2回戦の勝ち上がりの位置からになるが、根本にして

シード・足長は 1 回戦を**戦わずに通る**ので、その区間を引く時点では勝敗が分からない。
結果として太線が選手名からではなく 2 回戦の位置から始まっていた。

対処: 不戦勝で通した区間の**添字を `chain` に溜めておき、その先で実際に勝った時点で
遡って太くする**。これで太線が名前のところから 1 本に繋がる。

実装は「線を配列に貯めて後からまとめて出力する」形に変えた。引いた直後に太さを
決められない線があるため、文字列を即座に組み立てる方式では対応できない。
出力順は **細線 → 太線 → 文字**（太線が細線の上に来るように）。

検証（IH2025 第1山）: 太線 76 → **87 本**（不戦勝の通し区間 11 本ぶんが加わった）。
シード entryNo 1 の線が `164 → 186 → 208` の全区間で太線になることを確認。

## 追記（2026-07-31 その9）: 本番コンポーネントへ組み込み

### 描き方の最終調整

- **リタイアは「中」ではなく「R」**（ユーザー決定）。
- **負けた枠へ向かう区間も太くする**。「勝ち上がった先で負けた」場合、その区間が細いままだと
  太線が前の枠の中点で途切れて宙に浮く。太線は**その組がどこまで到達したか**を示すので、
  負けた枠まで届かせる。実装は各位置に「直前の枠で勝って上がってきたか」（`prevWon`）を
  持ち回り、`勝った || 勝って上がってきた` で太さを決める。
  実測: IH2025 第1山の太線 87 → 104 本。
- **決勝の横線は両側とも中央まで引くが、太いのは勝った側だけ**（ユーザー決定、3 往復で確定）。
  経緯: 当初は両側を太くしていた（「負けた枠へ向かう区間も太く」の規則をそのまま適用）が、
  決勝は左右の代表が**同じ高さ**でぶつかるため 1 本の長い太線になり、縦線も無いので
  どちらが勝ったか読めなくなった。→ 一度「決勝は横線を引かない」としたが、それだと
  優勝までの線が中央の手前で切れる。→ **両側引く／太いのは勝者だけ**に落ち着いた。
  負けた側の細い線が「決勝まで来た」ことを示し、太線は優勝者の 1 本だけが中央へ通る。
  **決勝だけ他のラウンドと太さの規則が違う**点に注意（他は「勝って来た側」も太くする）。

### モジュール構成

| ファイル | 役割 |

| `lib/bracketLayout.ts` | 席順の復元・ツリー・シート分割（**純粋関数のみ**） |

**`lib/bracketLayout.ts` からファイル読み込みを追い出したのが要点**。ブラウザから読まれる
モジュールに `readYearDetail`（`fs`）が値として入っているとクライアントバンドルが壊れる。

`drawBracketSheet` が SVG 文字列ではなく座標の配列を返すのは、モック（文字列を組む）と

### 分岐

`TournamentBracket` は `describeBracketLayout` が成功すれば `BracketSheets`、
失敗すれば従来描画。**`nextMatchId` の有無では分岐しない**（復元できるなら完了済み大会でも
新描画のほうが山ごとに分かれて読みやすいため）。対戦詳細モーダルは従来のものを共有する
（名前タップで `onSelectEntry`）。

### 太線の規則は 4 回の指摘で固まった

線の太さは目視で気付きにくく、指摘を受けて 4 回直した。最終形は次のとおり。

1. **勝った枠の横線を太く**（当初）。
2. **不戦勝で通した区間も、その先で勝った時点に遡って太く**。でないと太線がシードの
   名前からではなく 2 回戦の位置から始まる。
3. **縦線も勝者側の半分を太く**。でないと横→縦→横が縦のところで途切れる。
4. **負けた枠へ向かう区間も太く**。でないと太線が前の枠の中点で途切れて宙に浮く。
   ただし**その試合が実際に行われている場合だけ** — この条件を落としていたため、
   未開催の大会で 1 回戦の勝者の線が 2 回戦まで太く伸び、勝ってもいないのに
   勝ち上がったように見えていた。
5. 決勝だけは例外で、**勝った側のみ太く**（左右が同じ高さでぶつかるため）。

`lib/__tests__/bracketDrawing.test.ts`（7 ケース）でこれを固定した。座標は検証せず
「どの区間が太いか」だけを見る。実測: IH2026（結果ゼロ）の太線 **0 本**、
IH2025 第1山（完了）**102 本 / 175 本**。

### 逆算のやり方（`calculateEntryType` は使わなかった）

`normalize-core.js` の `calculateEntryType()` は関数内に閉じていて export されておらず、
また「実対戦の初出ラウンド」で判定するため 1 回戦の次が準々決勝と表記された大会で落ちる。
代わりに**1 回戦の対戦カードから席順を組み直す**方式にした。

1. `entryNo` 昇順に見て、隣同士が 1 回戦で対戦していれば実試合の枠（2 枠消費）、
   そうでなければ不戦勝の枠（本人＋bye で 2 枠消費）。
2. できた枠列に対し、実試合の枠の両者は `packing`。不戦勝の枠は隣が実試合なら `seed`、
   隣も不戦勝なら `extra`（`buildEntriesMeta` と同じ規約）。

**要点は検算**。逆算した type でブラケットを組み直し、**knockout の全試合が正しいラウンドに
配置されることを確認できたファイルだけ書き込む**。逆算ロジックを信じるのではなく結果で
検証しているので、1 件でもずれれば見送られる。実際 6 大会が見送りになった。

整形については、JSON を再シリアライズすると既存の整形（1 エントリー 1 行と複数行が混在）が
崩れて差分が巨大になるため、`"type": ...` の値だけをテキスト置換した
（`type` キーは entries にしか無く全 entry が必ず持つことを事前に確認）。

### 逆算できなかった 6 大会 — 共通原因は **entryNo が連番でない**
