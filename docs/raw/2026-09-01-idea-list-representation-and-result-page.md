# アイデア: 一覧表現の方針（カード／リスト／表）と、大会結果ページの第1弾

## 状況

**2026-09-01 実装済み**（大会結果ページの A・B のみ）。出発点は「全体的にカード型をとっているが、
リストが多くなってきたのでリスト型の方がいいのか、別の何かがいいのか」という発散フェーズの問い。
サイト全体の一覧表現の方針はまだ確定していない（本ページの「目指したい方向性」参照）。

## 目的

一覧ページが縦に伸び続けており、モバイル（PVはモバイル > PC）でのスクロール量が実用の限度を
超えつつある。器（カード／リスト／表）を選び直すのか、別の解があるのかを決める。

## ユーザーが興味を持った点

- 「全体的にカード型をとっているが、リストが多くなってきたのでリスト型の方がいいのか、別の何かがいいのか検討したい」
- 「大会結果ページが一番みられてるので、それを中心に考えてみたい。それから他をどうするかに繋げる」
- 「モバイルでの表示の方がPCより多い」
- 「対戦詳細に関してはみたい人が見るという形式なので今のままでもいいのかもしれない」（→ 実測で覆った。後述）

## わかっていること

### 1. 一覧表現の基準は 2026-07-04 に承認済みで、未適用だった

`02-issues.md` の I-14「一覧の表現が3系統あり使い分け基準が文書化されていない」に対し、
`05-page-structure.md` §6 でテーブル／カード／リンクリストの基準が approved になっている。
カードは「異種情報の混在、または状態ラベルが主役の一覧」に限る、が既定の答え。
ところが対応工数が「中（基準定義＋**段階適用**）」で、段階適用の側が実施されないまま新規ページが
増え続けた。つまり**新しい基準を作る問題ではなく、既存の基準を適用する問題**だった。

### 2. サイト全体のスクロール量（375×812 実測、2026-09-01）

| ページ | 件数 | 総スクロール高 | 1件あたり | 器 |
|---|---|---|---|---|
| `/tournaments` | 140 | 19,712px（24画面） | 116px | カード |
| `/secondaryschool/pathways/boys` | 167 | 20,755px（26画面） | 96px | カード |
| `/players` | 200 | 29,716px（37画面） | 89px | **テーブル** |
| `/highschool/boys/tokyo` | 15 | 6,563px（一覧は2,634px） | 176px | カード |

**器を変えても桁が変わらない**のが要点。`/players` はすでにテーブル（＝リスト型）だが一番長い。
375px に4列を詰めた結果、選手名が2行・大会名が3行に折り返している。

長さを決めていたのは器ではなく次の3つだった。

- **1行が詳細を持ちすぎ**（P3違反）。東京都ページの学校カードは3年分の成績＋「ほか8年分は…」まで載る
- **全行に同じ装飾が繰り返される**。`/tournaments` は140枚すべてに同じ「ブロック / ジュニア」チップ
- **見出し前の定型ブロックが重い**。統計カードが `grid gap-4 sm:grid-cols-3` で、640px未満では
  縦積み3枚＝ほぼ1画面を本文前に消費する（`highschool/[gender]/[prefectureId]/index.tsx`、pathways も同型）

## 実施した改修（A・B）

C（注目ポイントを結果より前に出す順序変更）は「注目ポイントがそこまで重要か判断できない」との
ユーザー判断で見送り。

### A. トーナメント表を行き止まりにしない

- `BracketSheets.tsx`: タップできる名前にサイト共通の**点線の下線**（＝選手へのリンク）を引いた。
  ただし **SVG は `text-decoration-style` を無視する**（Chrome 実測で `underline dotted` を
  指定しても computed が `solid` のまま）ため、`text-decoration` ではなく
  **`strokeDasharray` の `<line>` を自分で引いている**。色は図の固定パレット（`#7b8794`＝
  team / entryNo と同じ）に合わせた——図全体が `bg-white` 固定でダークモードを持たないので、
  ここだけトークンを使うと反転してしまう。
  あわせて「名前をタップすると…」の説明文を1行追加。
  下線の長さに要る文字幅は `getComputedTextLength()` がブラウザ専用で SSG では使えないため、
  **文字種からの見積もり**（半角 0.5em / それ以外 1em × fontSize）で出している。
  実測との突合は **3大会・名前ラベル176件で不一致0件**（インターハイ2026 男子ダブルス64・
  同 男子団体48・全日本選手権2025 男子64）。CJK が em 幅の正方形であることに依存した近似で、
  ビルド済み HTML にも `stroke-dasharray` が64件出るので JS 無しでも点線が出る。
- `TournamentBracket.tsx`: モーダルに**学校ページへのリンク**（「◯◯の成績」）を追加。
  `highschoolGender` / `highschoolTeamLinks` を props で受け取り、`TeamResults` と同じ
  `${team}::${prefecture}` の表を使う（リンク先判定をページ内で1か所に揃える・デッドリンク禁止）

### B. 対戦詳細を既定で畳む

- 上位（優勝／準優勝／ベスト4／ベスト8）だけを常時表示し、**成績順に並べる**
  （改修前は entryNo 順で、優勝組が最後に来ていた）
- 残りは `<details>` に格納。**HTML には全件残る**ので選手リンク・氏名テキストは1件も失われない
- 検索中は `<details>` を強制的に開く。検索を消すと畳んだ状態へ戻る
- 0件のときは「「◯◯」に一致する組はありませんでした。」を出す（改修前は無言で空になっていた）
- **24組以下の大会は畳まない**（`COLLAPSE_MIN_ENTRIES = 24`）。全427ファイルの実測で
  中央値48組・p75は104組・p90は271組だが、24組以下も22.7%ある。小さい大会まで畳むと
  「開く」操作が増えるだけでスクロール量は元から問題になっていない
- 「全て / ベスト8以上」のフィルタボタンは `<details>` に置き換えたので削除。
  ページ側の `filter` state も削除
- **並びは上位・その他とも entryNo 順**（ユーザー確定）。一度「上位は成績順」にしたが差し戻した。
  `detail.entries` は全427ファイルで entryNo 昇順であることを確認済みなので、
  `groupedNames` の順をそのまま使えば足りる（明示ソートは不要）
- `<details>` 自体には枠を付けない。**中身がカードの列なので囲むとカードの二重になる**（ユーザー指摘）。
  区切りは `<summary>` の1行だけにする

## 副産物: トーナメント表の決着点のずれ（2026-09-01 修正）

Aの確認中にユーザーが発見（全中2026 男子団体）。決着点（優勝の丸）が決勝のどちらの横線にも
接しない宙ぶらりんの点になっていた。

原因は **「決勝は左右が同じ高さでぶつかる」という前提が誤りだった**こと。`leafYOf` は
不戦勝の空席ぶんの行を確保しない（2026-08 のユーザー指摘への対応）ので、不戦勝の位置が
左右で違うと決勝の高さがずれる。丸は左右の **中点** に置かれていたため、ずれるとどちらにも
接しなくなる（この大会では ly=191.06 / ry=177・中点 184.03）。

`leafYOf` のコメントは「線は各側の実際の y だけで引くため描画上の問題にはならない」と
書いていたが、**決着点だけは左右をまたぐ**ので例外だった。

実測すると **全1,002シート中461枚＝46.0% でずれており、最大 24.2px**。一部の大会の話ではない。

修正は**描く前に左右の高さを揃える**方式に落ち着いた。`convergedYOf`（drawSide と同じ中点の
漸化式を、描かずに走らせるだけの関数）で両側の収束点を先に測り、**低い方の側を丸ごと下げてから
描く**。これで「決勝は左右が同じ高さでぶつかる」という描き方の前提が常に成り立つので、
決勝の線・スコア・優勝の丸に特別扱いが一切要らなくなる。

### そこへ至るまでに2案を捨てている（同じ日のやりとり）

1. **丸を優勝者の横線の端に置き、ずれは中央（決着点のところ）で縦に繋ぐ**
   → ユーザー指摘「中央の点に伸びるように横線を引けないか」。丸の直前で線が折れて
   紙のドロー表に無い形になる
2. **ずれをラウンドの境目で縦に吸収し、決勝の横線は左右とも決着点の高さで引く**
   → ユーザー指摘「最後の縦線の終点がずれたまま」。**段差の縦線を足しても、準決勝を勝った
   太線は元の高さ（ry）で終わったまま**なので、決勝の横線より 14px 突き出た端が残る。
   段差を太くしても細くしてもこの突き出しは消えない——描き終わった線に後から足す方式では
   直らない、というのが分かった時点で「描く前に揃える」へ切り替えた

### 検算

全1,002シートで、決勝の横線2本が違う高さ **0件**（当初461件）、丸がどちらかの線に乗っていない
**0件**、太い縦線が決勝の横線から突き出ている **0件**。左右が同じ高さの大会は下げ幅0なので
見た目は変わらない。`npm run bracket:test` は 7/7 pass、`npm run build` 完走。

副作用として、ずれる大会では**片側の山が最大 24.2px（rowH 19 の約1.3行ぶん）下がる**。
左右の行が横に揃わなくなるが、`leafYOf` が空席を詰める仕様のため元から行は対応していないので、
新しい種類のずれではない。

## 課題・未解決

- **DOM 要素数は減っていない**。`<details>` は閉じていても子を DOM に持つ（レイアウトはされないので
  スクロールと描画コストは消えるが、パース／DOM構築コストは残る）。
  `/players` 改修の教訓（効いたのは転送量でなく DOM 要素数 -68%）を踏まえると、
  ここは次の一手の候補。ただし HTML から消すと選手リンク66本を失うので、消すなら代替の
  リンク在庫を先に用意すること
- **文字幅の見積もりはフォント依存**。半角 0.5em / CJK 1em の前提が崩れるフォントに変えると
  下線の長さがずれる。現時点では176件で完全一致だが、フォントを触るときは
  `estimateSvgTextWidth` の突合をやり直すこと（ブラウザで `getComputedTextLength()` と比較する）
- **効果測定が未実施**。回遊検証ランブックのモジュールCTRで、トーナメント表からのタップが
  増えたかを測りたい。ベースラインは2026年9月末（M4平常期チェックと同時）
- **C（順序変更）は保留**。「注目ポイントがそこまで重要か判断できない」ため。
  注目ポイントの価値そのものを測る手段が無いのが根本原因
- **サイト全体の一覧表現の方針は未確定**。下記

## 目指したい方向性

このページから得られた一般則は「**器を変える前に、そもそも常時出す必要があるかを決める**」。
316枚のカードを軽い行に変えても 30,000px→18,000px で22画面残るが、畳めば1画面になる。
`05-page-structure.md` §6 は器の選び方しか定めていないので、その手前に
「常時表示するか・畳むか・別ページへ出すか」の判断を足すべき、というのが提案。
ただし §6 は approved の成果物なので、改訂は所定の手続きで行うこと（本ノートでは提案に留める）。

残りの一覧ページの着手順（ROI順・未着手）:

1. 統計カードのモバイル横並び化（全ページ横断・1コミット・本文が1画面ぶん手前に来る）
2. `/tournaments`（24画面。AdSense掲載面でもある）
3. `/highschool/[gender]/[prefectureId]`（97ページ。学校ページ回遊強化のターゲットそのもの）
4. `/secondaryschool/pathways`（26画面）
