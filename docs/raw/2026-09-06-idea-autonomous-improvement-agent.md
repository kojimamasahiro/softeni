# アイデア: AIが自律的にサービスを改善する仕組み（検知・検証の全体委譲と自己修復）

## 状況

Idea Backlog。発散フェーズだが**方向は決着した**（2026-09-06）。
出発点となるドメイン（PDF取り込み系）と、成立条件（抜き取り監査＋非対称な境界移動）まで合意。
実装は未着手。

## 目的

サービス運用のうち**検知・検証の全体**をAIに委譲し、人間は方向の判断だけを持つ状態にしたい。
背景にあるのは「AIソロプレナー」的な関心と、「自律して目標を立てて内外のデータを取得して
タスクを完了するAIエージェントを駆使できるようになりたい」という関心。

既存の姉妹スレッド2本との関係:

- [AIとの共同探索と探索プロセスの属人性](./2026-07-11-idea-ai-co-exploration-context.md) —
  **人間が主でAIが従**の前提で探索の質を上げる話。本アイデアはその上位（人間が主導権を持たない層）。
- [skillのローカルLLM代替](./2026-08-14-idea-local-llm-skill-replacement.md) —
  **人間が与えたタスクをAIが遂行する**話。本アイデアはその上位（タスクを誰が決めるか）。

本アイデアは「AI自身が何をやるか決める」層で、バックログでは初。

## ユーザーが興味を持った点

原文（時系列）:

- 任せたいことの正体:
  「**任せたいことはAIの自律性を向上さて "床" を高めて方向を人間が判断できるための土台づくり**」
  「**任せたいことは課題発見かもしれない**」
- 委譲の範囲:
  「**検知や検証の全体を任せていくというのはできないのかどうか。もちろん、最終判断は人間にしたい**」
- 「（検出器の穴を測る案は）**かなり狭い範囲だと感じ、それをすることで仕組み作りにつながる

- 境界（自動でよい範囲）の決め方について:
  「**自動化したい。ただ、そこにも自己修復できるようにして、間違いがないか、改善する余地は
  ないかを判定して、時には人に判断を任せつつ、自己修復されるようにしておきたい**」

## 想定運用 / なぜこのスコープか

### 「充実」を目的関数に置く（PV・収益は置かない）

ユーザーの見立て:「トップページの『ソフトテニスを「記録」としてたどれる場』が充実していくことで、
収益・PV・掲載データ量・手作業時間の削減というのは説明変数になるのか」。

方向は妥当だが、挙がった4つは**役割が3種類に分かれる**（Claude の整理）:

| 変数 | 役割 | 目的関数に置けるか |
|---|---|---|
| 手作業時間の削減 | 真の説明変数（上流の原因。容量が増える） | ○ |
| 掲載データ量・接続性・正確性 | 「充実」の構成要素そのもの（説明変数ではない） | ○（定義が要る） |
| PV・収益 | 下流の結果（遅行指標） | **×** |

PV・収益を自律エージェントの目的関数に置けない理由は、**本リポジトリに4件の実証がある**。
どれもPVが上がる選択肢を、ミッションに反するとして人間が退けたもの:

1. AdSense全面展開時、本文78文字の空ページにも広告が出る穴を見つけ、
   **本文400文字未満は出さないゲートを足して417枚を自ら除外**した
2. **優勝予想はやらない**（2026-07-31決定。2026-08-31に「事前Elo上位4組＝準決勝4組」と
   実測で当たることを確認してもなお見送り）
3. [ADR-010](../adr/ADR-010-retire-result-articles-consolidate-to-hub.md) で結果記事を廃止しハブへ統合（ページを減らす判断）
4. 選手一覧の姓頭文字分割ページを不採用（薄いページの量産になるため）

**PVを目的関数に持ったエージェントなら4件とも逆の判断をする**。しかも短期的にはどれもPVが
上がるので、指標の上では「改善」に見える（Goodhart）。

一方「記録としてたどれる」は機械で測れる概念で、**断片は既に測られている**が一度も束ねられていない:
網羅性（掲載大会数・年）/ 接続性（内部リンク本数 選手一覧97→1,917本、学校ページ間0本、
`check-orphan-entries` の孤立エントリー）/ 正確性（照合カバレッジ26.4%）/
同一人物として辿れるか（識別ヘルスの要対応シグナル72→42、別名残存4→0）。

### 委譲の単位は「機能の一部」ではなく「1ドメイン丸ごと」

理由は下記「わかっていること」の583件（部分適用が実際に止まった実証）。

## わかっていること

### 1. 完成例が既に1つある — チーム名寄せ

「検知・検証の全体委譲」は、本リポジトリで**既に1ドメインだけ完成している**。

```
① 候補を機械が出す         scripts/build-team-merge-candidates.mjs（コア一致／選手共有の2シグナル）
② 自動でよい分を機械が決める  scripts/apply-auto-merges.mjs
③ 残りを人が判断する道具を機械が作る  scripts/build-team-review-html.mjs
④ 判断を機械が反映する      scripts/apply-team-aliases.mjs
⑤ 起動                     ← ここだけ人
```

③は「チーム名だけでは判断できない」ことを前提に**選手名・年代・主な大会の文脈を添え、
1クリックで判断でき、確認済みはリストから消える**設計。人間は判断だけをする。

**②に「最終判断は人間」が思想でなくコードとして書かれている**のが要:

> 自動OK: 同一グループ内で「同一大会(大会id+年)」に表記が同居しなければ自動OK。
> **ただし signal:"players"（選手共有シグナル）のクラスタは常に自動OKにしない（人手レビュー専用）。**

→ **人間が全部を見なくても「最終判断は人間」は保てる。機械が判断してよい範囲を一度定義すれば、
その外側だけが人間に来る。**

### 2. 部分適用は実際に止まった — 外部データ取得クローラーの583件

```
data/local-sources/detected-documents.json
  総数 583件 / status: 全件 "new"
  ignored 0件 / accepted 0件 / appliedAt を持つもの 0件
  検出日 2026-05-24 〜 2026-06-12
```

`crawl:local-tournaments`（県連サイトを巡回してPDFを検出）と
`apply-accepted-qualifiers.mjs`（accepted を反映）は両方実装済みなのに、
**間の仕分けが人手だったため583件が3ヶ月放置され、accepted が1件も無いので反映側は
一度も仕事をしていない。クローラー自体も2026-06-12以降走っていない。**

→ **①だけ自動化すると人の可処分時間が律速になり、仕組みごと止まる。**
同じ兆候が teamId 目視確認252件にもある。

### 3. 「提案はLLM・採否は機械」の型が3回、独立に発明されている

- `scripts/pdf-to-players/tuning.py` の `repair()` — LLMが4段階の温度で列判定を提案 → 機械が採点 →
  外れた内訳をフィードバックして最大3回直させる。docstring に
  **「採否を決めるのは常に機械（`score_entries`）で、LLMの自己申告は使わない」**
- [ADR-012](../adr/ADR-012-llm-authored-insights-with-machine-verification.md) — 記事は機械照合を通ったものだけ公開（prebuild が強制）
- `npm run ranking:backtest` — 過去データで再生して採点

**自己修復ループの型は既にある。** 今回の要求は「この型を②（境界の決定）自身に適用する」こと。

### 4. ②は既に1箇所で自動化されていて、一度壊れている

`scripts/pdf-to-players/tuning.py`:

```python
GOOD_ENOUGH = 0.75   # これ未満ならLLMに聞く＝機械が自分で「自信がない」と判定する境界
if a.score >= 0.95:  # 早期打ち切り
score *= 0.6         # 退化解釈へのペナルティ
```

2026-08-14のインカレ対応時、**「存在しない項目を減点する設計だったため点数の上限が0.74になり、
目安0.75に到達不能」**という形でこの境界が壊れていた。
→ **境界が誤っていても症状は「なんとなく上手くいかない」としてしか出ない。
②を自動化するなら、境界が正しいかを測る仕組みが同時に要る。**

### 5. 学習材料の実測 — 人の判断は6件しかない

| 材料 | 件数 |
|---|---|
| `data/teams/team-alias-additions-auto-reviewed.json`（人が確定した判断） | **6件** |
| `data/teams/team-name-mappings.json` | 67件 |
| `scripts/pdf-to-players/fixtures/` | **PDF 2本**（うち回帰103アサーション） |

レビューHTMLは判断を `localStorage` に持つため、**押した判断の大半がブラウザ内で消えている**。

一方、**二経路照合による正解データは潤沢**:
PDF抽出 vs 人が作った `initialPlayer.js` = **49件全項目一致** /
インカレ姓名分割 vs 既存選手データ = **796名中793名一致(99.6%)、不一致3件は既存データ側の誤り** /
`bracketLayout` vs 全データ = **209大会 20,571試合一致・不一致0**。

→ **「人の判断を学ぶ」経路は今は成立しない（6件）。「独立した第二経路と突き合わせて
自分を採点する」経路なら今日から成立する。** 後者のほうが設計として優れてもいる——
前者は機械が人間の偏りに収束する（[2026-07-11 の論点1「均質化」](./2026-07-11-idea-ai-co-exploration-context.md)そのもの）。

## 設計の骨子（合意済み）

### 人間の判断を「キューの処理」ではなく「機械の抜き取り検査」に使う

機械が全件を処理し、**人は無作為に少数（例:20件）だけ見る**。得られるのは処理結果ではなく
**機械の誤り率**で、これが (a) 境界が正しいかの判定材料になり、(b) 不足していた人の判断ラベルにもなる。

**人の時間が件数に比例しなくなる（線形→定数）。** これが「全体を任せる」と
「最終判断は人間」が両立する形。

自己修復はここから自動的に出る:
**誤り率が許容を超えたら境界を自動で締める、下回り続けたら少しずつ緩める。**

### 境界の移動は非対称にする（Claude の提案・ユーザー未確認）

- **締める方向**（人に回る量が増える）→ 安全。自動でよい
- **緩める方向**（機械が決める量が増える）→ **独立した二経路照合で裏が取れたときだけ**

理由は「わかっていること 7」。緩めれば人の負荷は下がり、指標上は改善に見え、誤りは黙って通る。

### 課題発見の3階層（Claude の整理・ユーザー未確認）

ユーザーの「任せたいのは課題発見」は "床" と "方向" の境界上にあるため分解した:

- **(i) 規約違反の発見** — 決めたルールが守られていない箇所を探す。純粋に床。全部任せてよい
- **(ii) 検出器の穴の発見** — 「守っているつもりのルールが機械で守られていない」を探す。
  メタだが保証範囲の内側なので任せられる
- **(iii) 課題設定** — 何を問題とみなすか。任せると均質化が最も強く出る。**人間に残す**

(ii) には本リポジトリに1例だけ実績がある: 2026-08-14の**逸脱注入テスト**（インサイトに8種の逸脱を
注入し、照合器が落とせたのは2種だけ）。ここから「実効カバレッジ26.4%」「記事の主語が0/24で未照合」
という、人間が気付いていなかった課題が出た。

## 課題・未解決

- **境界の自動調整と「静かな劣化」の切り分け**。緩める方向の非対称ルールは提案止まりで未検証。
- **抜き取り監査の標本設計**（何件で誤り率をどの精度で測れるか、層別が要るか）。
- **人の判断が repo に残らない問題**（`localStorage`）。抜き取り監査を回すなら先に直す必要がある。
- **走る場所（CI/スケジューラ）の選定**。Cloudflare Pages 前提のリポジトリで、
  GitHub Actions を入れるのか別手段かは未検討。
- **「充実」を1つの数字に束ねる作業**は未着手（材料は揃っているが定義が要る）。
  出発点をPDF取り込みにしたため後回しになっている。
- **(iii) の線引きを誰がいつ見直すか**。人間に残すと決めたが、見直しの契機が未定義。
- クローラーの583件は**捨てる**判断（2026-09-06）。ただし
  「残すならクローラーの設計自体を見直したい」とのことで、外部データ取得の再設計は未着手のまま残る。

## 目指したい方向性

**出発点は PDF 取り込み系**。理由は条件が最も揃っているため:

- 境界（`GOOD_ENOUGH = 0.75`）が既にある
- 自己修復ループ（`tuning.repair`）が既にある
- 二経路照合の正解データが潤沢（49件 / 796名 / 20,571試合）
- **境界が一度壊れた実例がある**（上限0.74問題）
- ユーザーが「全部任せたい」と挙げた「PDF取り込みからの試合結果反映」と同じレーン

欠けているのは**抜き取り監査**と**境界を動かす非対称ルール**の2つだけ。

なお **PDF→エントリーは自動化済み**（`scripts/pdf-to-players/`、回帰103 pass）だが、
**PDF→試合結果はskill（`tournament-pdf-to-results`）だけでスクリプトが無い**。
手作業が残っているのは後半。

検出器の実行状況を全数確認した結果:

```
prebuild に入っている（push で自動実行）: 4本
  check-tournament-entries / check-tournament-insights
  check-highschool-pipeline-freshness / check-name-splits --strict

入っていない（人が思い出したときだけ）: 7本
  check-orphan-entries / check-duplicate-placements / check-upcoming-tournaments
  check-identity-health / check-growth-analysis / verify-bracket-layout / verify-story-text
＋ テスト・検証系10本（bracket:test / analytics:test / upcoming:test / club:verify /
  playerstats:verify / playerstats:test / ranking:backtest / bracket:verify:tree / story:verify ほか）
```

**11本中7本が休眠していた。** 原因は忘れっぽさではなく構造で、休眠中の検出器には**2種類ある**:

- **ゲート型**（合否が意味を持つ）: orphan-entries / duplicate-placements / growth-analysis /
  verify-bracket-layout
- **キュー型**（人の判断待ちの一覧。設計上いつも未処理を返す）: identity-health（exit 1 が既定）/
  upcoming-tournaments（「終了コードは常に 0。運用の残タスク一覧であり、ビルドを止めるエラーではない」）

**prebuild はビルドを止める場所なのでキュー型を置けない。置き場が無かったから休眠した。**
これは本文の「①だけ自動化すると詰まる」と同型の現象が、実行環境の側でも起きていたということ。

なお `verify-story-text` は引数必須の**記事単位のツール**（`-t` / `-c` が要る）で、
リポジトリ全体を見る検査ではないため CI 対象外。全体側の強制は prebuild の
`check-tournament-insights` が担っている（ADR-012）。

### 実装したもの: `.github/workflows/checks.yml`

リポジトリは PUBLIC なので **GitHub Actions は無料・無制限**（コスト制約なし）。
Cloudflare Pages と役割を分け、**CF に置けないもの**だけを引き受ける設計にした:

| CF Pages（既存） | GitHub Actions（今回） |
|---|---|
| push 契機のみ | push + **cron（毎週月 09:00 JST）** + 手動実行 |
| ゲートのみ（落ちるとデプロイが止まる） | **ゲートと報告を分離**。報告はデプロイに影響しない |
| 結果はビルドログ | ジョブサマリに一覧が残る |

- **ゲート（落ちたら赤）**: check-orphan-entries / check-duplicate-placements /
  check-growth-analysis / bracket:test / analytics:test / upcoming:test / club:verify
- **報告のみ（赤にしない）**: verify-bracket-layout / check-identity-health /
  check-upcoming-tournaments → `$GITHUB_STEP_SUMMARY` に出力

`verify-bracket-layout` は現在250件で赤なので、**あえてゲートに入れず報告側に置いた**
（赤い CI を常態化させないため）。250件が解消したらゲートへ昇格させる。
これは本文の非対称ルール「**締める方向の変更は自由**」の最初の適用にあたる。

ローカルで CI と同じ手順を通しで実行した結果: **ゲート7本すべて PASS・合計3秒**
（CI では checkout と `npm ci` を足して1〜2分の見込み）。
