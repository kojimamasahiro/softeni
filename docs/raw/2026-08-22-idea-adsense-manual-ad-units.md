# アイデア: AdSense手動広告枠の実装と密度設計

## 状況

Idea Backlog。2026-08-22時点、密度設計の方針は固まったが `AdUnit.tsx` 自体は未実装。
発散フェーズは概ね収束し、次の一歩は実装着手（ページ種別の優先順位・段階導入の測定設計）。

## 目的

AdSenseの自動広告（インタースティシャル・ページ内自動挿入）を嫌ってオフにし、現在は下部
アンカー広告のみに絞った運用にした結果、広告売上が旧水準の約1割まで落ちた。課金以外の
収益源として、レイアウトを崩さずにコンテンツ内に広告を戻す方法を検討する。

## ユーザーが興味を持った点

> google adsenseのインタースティシャルやキーワードの広告が嫌でページ下部に張り付いている
> アンカーバナーのようなもののみにしたら広告売り上げが1割くらいになった。
> コンテンツの途中に表示される広告もAdSenseの自動広告だと元々持っているページのレイアウトが
> 崩れたので非表示にした。

> 「未実装のAdSense手動枠を作る」
> 広告をどれくらい載せるかなど検討したい。

## 想定運用 / なぜこのスコープか

`docs/adsense-ui-proposal.md`（2026-06-12、Status: Proposal・未実装）に、自動広告に頼らず
`AdUnit.tsx` という手動枠をページ区切りに固定配置する設計が既にある。自動広告でレイアウトが
崩れた原因（挿入位置を制御できない・高さ確保がない）は、この手動枠設計（`min-height` で
CLSをゼロにする）であれば回避できる。したがって「新しいアイデア」というより、**既にある
未実装の設計を、密度の歯止めを付けた上で実行に移す**というスコープになる。

段階導入・対照群比較は、このプロジェクトが回遊施策で既に確立している型
（[circulation-verification.md](../wiki/circulation-verification.md)）と同じものを流用する。
AdSenseのページビュー数・ページRPM・推定収益は、そのランブックの指標に既に組み込まれている。

## わかっていること

- AdSense自動広告（自動挿入）によるレイアウト崩れが理由で、コンテンツ内広告を非表示にした
  （ユーザー発言）。
- アンカー広告のみの運用で、広告売上が旧水準の約1割に低下（ユーザー発言。定量値はユーザーの
  体感でありAssumption）。
- `docs/adsense-ui-proposal.md` に手動 `AdUnit.tsx` の設計案が既にある（未実装）。CLS対策の
  `min-height` 事前確保、SPA遷移対応（`router.asPath` キーでの再pusha）、ページ種別ごとの
  配置案（選手ページ2枠・チームページ2枠・試合詳細ページ3枠）、共通ルール（1ビューポートに
  2枠以上同時表示しない・薄いページは枠①のみ）が既に文書化済み。
- Google Lighthouse の Publisher Ads Audit（公式）: 広告はビューポート垂直方向で
  **最大30%**が閾値（モバイルはページ全体、デスクトップはセクション単位で判定）。
- 業界の実務目安: デスクトップ長文で4〜5枠・短文で3〜4枠、モバイルは「ファーストビュー1枠＋
  本文中1〜2枠、画面内に同時に2枠出さない」。
- Googleは2016年に「1ページ3枠まで」というAdSenseポリシー上の枠数上限を撤廃済み。現在は
  枠数そのものではなく広告密度・UXが基準（枠を増やしすぎると離脱率上昇でページRPM自体が
  下がる副作用も実務上報告されている）。
- ページ種別の規模: 選手結果ページが1,916枚で最大母数（`circulation-verification.md`の
  実測）。試合詳細ページ（`beta/matches-results/[matchId]`）はカードが縦に並ぶ長尺構成。
- `adsense-ui-proposal.md`の元設計の枠数（選手2・チーム2・試合3）は、上記の外部基準
  （デスクトップ3〜5枠目安・30%ルール）とほぼ整合している。問題は枠数設計ではなく
  「自動広告任せで高さ確保がなかった」実装面だった可能性が高い。

## 課題・未解決

- `AdUnit.tsx` 自体は未実装。
- どのページ種別から着手するか未確定（選手結果ページが最大母数で最有力候補）。
- 段階導入の測定期間・合否閾値の具体設計（`circulation-verification.md`のCTR閾値
  5%/1%のような、RPM/CLSに対する自サイト実測ベースの閾値は未定義）。
- AdSense管理画面側の自動広告設定（ページ内フォーマットのオフ・アンカー位置bottom等、
  `adsense-ui-proposal.md` §3 の推奨設定）が実際に反映済みかの再確認。

## 目指したい方向性

`adsense-ui-proposal.md`の設計を土台に、選手結果ページ（最大母数）から主力枠1つを
段階導入する。密度の上限はビューポート30%ルールと「同時に2枠出さない」を歯止めとし、
1枠ずつ入れてCWV/ページRPM/推定収益を確認してから次の枠を追加する
（`circulation-verification.md`と同型の運用）。

| ページ種別 | 推奨枠数 | 根拠 |
|---|---|---|
| 選手結果ページ（最大母数） | 1（→様子見て2） | プロフィール直後の主力枠のみでまず投入、母数が大きく効果測定しやすい |
| チームページ | 1〜2 | 元提案通り、年度ブロックが多いページのみ2枠目 |
| 試合詳細ページ（長尺） | 2〜3 | カード間に挟む形。末尾枠は任意 |
| 薄いページ全般 | 0〜1 | コンテンツ量が枠を支えられない場合は入れない |

含めたもの:

  → `wiki/monetization.md`「手動広告枠」の配置原則

  → `ADR-016` の Context / Alternatives
- Lighthouse Publisher Ads Audit と枠数上限撤廃（2016）の外部基準 → 同上の配置原則と ADR

落としたもの（理由つき）:

- **「選手結果ページ（最大母数）から着手」という方向性** — 対照群と衝突するため不採用。
  ユーザー確認の結果、掲載面は PV 順（選手一覧・大会結果・大会一覧・news展望）に差し替えた。
  不採用の理由自体は `wiki/monetization.md`「選手結果ページに枠を置いていない理由」として残した。
- **「推奨枠数」表のチームページ・試合詳細ページ行** — 今回の掲載面に含まれず、PV 上位でもない。
  第2段階以降の候補として ADR の Open Questions に一行だけ残し、表は持ち込まなかった。
- **業界の実務目安（デスクトップ4〜5枠等）** — 出典が個社ブログで、当サイトの1ページ1枠という
  現状の判断には効かない。Lighthouse の公式基準だけを wiki に持ち込んだ。
- **広告売上が約1割に落ちたという定量値** — ユーザー体感で計測値ではないため、
  Assumption と明示したうえで ADR の Context にのみ残し、閾値設計には使っていない。
