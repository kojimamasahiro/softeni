# アイデア: ユーザーの課題を体系的に見つける

## 状況

Idea Backlog。発散フェーズ（2026-09-06）。**未着手**だが、使える信号の棚卸しは済んでいる。
最初の一歩（GA4のサイト内検索クエリを読む）は**今日から実行できる**状態にある。

## 目的

これまで見つけてきた課題は「**データが壊れている**」型（不一致250件、IDずれ、名寄せ漏れ）に偏っていた。
機械で検出でき、正解がはっきりしているからである。

一方で、**ユーザーが使いにくいと感じている／欲しいものが見つからない**という型の課題は、
一度も体系的に探していない。これまでの UX 改善（一覧表現、節の階層化、広告位置）は
すべて**作り手が気付いた範囲**で、ユーザー側の信号から出発したものではない。

> これを解決したらユーザーがもっと使ってくれる、という課題を見つけたい

## ユーザーが興味を持った点

原文（2026-09-06）:

> ユーザーの課題を発見したい。クラッシュだけでなく、**UXとして使いにくい**とか、
> こういった課題を解決したら**ユーザーがもっと使ってくれる**などの課題。

「課題発見をAIに任せたい」という同日の関心
（[自律的改善](./2026-09-06-idea-autonomous-improvement-agent.md)）の続きだが、
対象が**データの正しさ**から**ユーザーの体験**へ移っている。

## 想定運用 / なぜこのスコープか

本サイトは**静的サイト・ログイン無し・大半が検索流入**である。したがってユーザーは
「Google で問いを持って来て、答えが得られたか得られなかったか」という形でしか現れない。
アンケートもインタビューもできない規模なので、**残された痕跡から読む**しかない。

同日の自律的改善スレッドで得た教訓を先に適用する:

> **測定器を作ったら、まず「この信号は人の目に届くか」「一致は記録されるか」を確かめる。
> 率の計算はその後。**

そのため本アイデアは、施策より先に**「何が観測できて何が観測できないか」の棚卸し**から始める。

### 最有力: サイト内検索のクエリが1ヶ月分眠っている

`/players`（選手を探す入口）は検索語を URL に反映する。

```
src/pages/players/index.tsx:156
  // 検索語を URL に反映する。共有・履歴・計測が効くようになる。
  router.replace({ pathname: '/players', query: next ? { q: next } : {} }, undefined, { shallow: true, scroll: false });
```

`src/pages/_app.tsx` は `routeChangeComplete` で `page_view` を送っており、
`page_path: url` にクエリ文字列がそのまま入る。shallow routing でもこのイベントは発火する。

```
検索語のURL反映: 2026-08-09 から
page_view の SPA 対応: 2025-05-18 から
```

したがって **GA4 に `/players?q=<検索語>` が約1ヶ月分溜まっている。** そして
[回遊検証ランブック](../wiki/circulation-verification.md) が言うとおり **GA4 は一度も読まれていない。**

これは「ユーザーが自分の言葉で何を探したか」の直接の記録で、
**検索して0件だった語＝サイトに無いもの**が分かる可能性がある。
検索インデックスは9,391組なので、0件になった語は「収録していない選手」か「表記が違う」かの
どちらかで、**どちらも具体的な打ち手に直結する**。

（注意: 同意していないユーザーの `page_view` も cookieless で届くので、
**クエリの一覧としては同意率の影響を受けにくい**。人数は数えられないが、語は読める。Assumption・要確認）

### 既にある資産

- **ランブックの型が2つある** — [M4検証](../wiki/highschool-seo-m4-verification.md)（GSC）と
  [回遊検証](../wiki/circulation-verification.md)（GA4/AdSense）。どちらも
  「当時の文脈を覚えていなくても実行できる」ことを目的に書かれている。**本アイデアの成果物も
  この型に揃えること。**
- **UX Writing のルール**（[ux-writing.md](../wiki/ux-writing.md)）— 見つけた課題を直すときの表記の正。
- **`out/` の静的解析の実績** — 2026-08-15（学校ページの回遊）と 2026-09-01（一覧表現）で、
  ページを実測して課題を数値化した前例がある。

## 手順（他の人がそのまま実行できるように）

### 手順0. 前提の確認（所要10分）

1. GA4 のプロパティにアクセスできること（`NEXT_PUBLIC_GA_ID` = `G-1K5LX0RGJ7`）。
2. GSC のプロパティにアクセスできること。
3. **同意率を確認する**。GA4 の `consent_accept` / `consent_decline` イベント数を見る
   （`lib/analytics.ts` の `trackConsentChoice`）。人数を語るときはこの比率を必ず添える。

### 手順1. サイト内検索のクエリを読む（最優先・所要30分）

GA4 → レポート → エンゲージメント → ページとスクリーン →
**「ページパスとスクリーンクラス」ではなく「ページパス + クエリ文字列」**を選ぶ
（無ければ探索レポートで `page_path` を次元にする）。

1. `/players?q=` で始まる行を**表示回数の多い順**に並べる。
2. 上位50語をコピーし、**実際にサイトで検索してみる**。
3. 3つに仕分ける:

   | 仕分け | 意味 | 打ち手 |
   |---|---|---|
   | **0件になる** | 収録していない or 表記が違う | 収録の穴 / 別名の追加 |
   | **出るが目的の人ではない** | 同姓同名・並び順の問題 | 絞り込み・並べ替えの改善 |
   | **出る** | 問題なし | — |

4. **0件になった語を最優先の課題リストとする。** 記録は下記テンプレへ。

### 手順2. GSC の「取りこぼし」を読む（所要30分）

GSC → 検索パフォーマンス → 過去3ヶ月。

1. **表示回数が多く CTR が低い**ページを抽出する（目安: 表示100以上・CTR 1%未満）。
   → タイトル/説明が検索意図とずれている疑い。実際の検索語と title を突き合わせる。
2. **順位が11〜30位のクエリ**を抽出する。
   → 需要はあるが届いていない。ページが無いのか、弱いのかを見る。
3. Google の**関連検索**を実際に引いて、GSC に出てこない言い回しを拾う
   （「ソフトテニス 全中 歴代」はこの方法で見つかった）。

### 手順3. 行き止まりページを数える（所要30分・コード）

`out/` を静的解析し、**本文リンクが極端に少ないページ**を種別ごとに数える。
前例は [学校ページの回遊](./2026-08-15-idea-highschool-school-page-cross-links.md)
（`hs:school → hs:school` の横リンクが0本・698枚の68%が本文リンク10本以下）。

同じ走査を全種別へ広げ、**「着地しても次に行く先が無いページ」の在庫**を出す。

### 手順4. 課題リストにまとめて優先順位を付ける

**打ち手のコストと、影響するページ数の2軸**で並べる。判断材料は:

- 影響するページ数（`out/` から数える）
- 検索需要（GSC の表示回数）
- 打ち手のコスト（新規URLが要るか、既存ページの節追加で済むか）

**新規URLを作る案は原則あとまわし**（[ADR-010](../adr/ADR-010-retire-result-articles-consolidate-to-hub.md) の
「薄いページを増やさない」方針）。

### 手順5. 記録（必須）

`docs/raw/YYYY-MM-DD-user-problem-findings.md` に以下の形で残す。

```markdown
## 計測期間: YYYY-MM-DD〜YYYY-MM-DD
## 同意率: X%（母数N）
## サイト内検索（手順1）: 上位50語のうち 0件 N語 / 目的外 N語
##   0件だった語: （そのまま列挙）
## GSC の取りこぼし（手順2）: 低CTRページ N件 / 11〜30位クエリ N件
## 行き止まりページ（手順3）: 種別ごとの件数
## 課題リスト（手順4）: 優先順位つき
## 次のアクション:
```

## 課題・未解決

- **GA4 でクエリ文字列が実際に取れているかは未確認。** `page_path` に `?q=` が入る実装には
  なっているが、GA4 側の設定（クエリ文字列の除外設定など）で落ちている可能性がある。
  **手順1の最初にこれを確かめること。空振りならここで止まる。**
- **同意していないユーザーのクエリが届いているかも未確認**（Assumption）。届いていなければ
  母数がかなり小さくなる。
- `/players` 以外の検索（`/teams`・`/tournaments` 等）は URL に反映していない。
  同じ実装を広げるかは要判断（1行で済むが、計測対象が増える）。
- **スクロール深度・タップ位置は計測していない。** 「どこで詰まったか」は現状わからない。
  入れるべきかは、手順1〜3で足りるかを見てから決める。
- 定性的な声（`/contact`）をどう扱うか。件数が少ないので統計にはならないが、
  1件が示す構造は大きいことがある。

## 目指したい方向性

**まず手順1（サイト内検索のクエリ）だけをやる。** 理由:

1. **既に1ヶ月分のデータがある**（新たに計測を仕込む必要がない）
2. **ユーザー自身の言葉**なので、作り手の思い込みが入らない
3. **0件だった語は、そのまま打ち手になる**（収録の穴 or 別名の追加）
4. 空振りでも30分で分かる

ここで何か出れば、手順2〜3へ広げる。出なければ、計測を足す（スクロール深度等）か、
別の入口（`/contact` の声）を試す。

**この順序は「作るより先に、あるものを読む」という同日の教訓に従っている。**
自律的改善スレッドで最も費用対効果が高かったのは、新しい検出器を作ることではなく
**既にある検出器を走らせる**ことだった（休眠していた検出器を1回走らせて250件の不一致を発見）。
GA4 は同じ構図にある——**実装済みで、一度も読まれていない。**

## 追記1（2026-09-06・同日）: GitHub Actions で自動化できる範囲の切り分け ＋ 0件判定を実装

「github actions で自動化できるものはあるか」という問いから切り分けた。

### 切り分け

| 手順 | 自動化 | 必要なもの |
|---|---|---|
| GA4 から検索クエリを取得 | ○ | GA4 Data API ＋ サービスアカウント（Secret）。`google-analytics-data` パッケージ |
| **0件判定（クエリ → 結果件数）** | **○ 今すぐ・認証不要** | 検索インデックスがコミット済みなので依存が無い |
| GSC の低CTR・11〜30位クエリ | ○ | Search Console API ＋ サービスアカウント（Secret） |
| `out/` の静的解析 | △ | **ビルドが要る（CF実測で約9分）**。CI は現在ビルドしていない |
| 優先順位付け・記録 | ✗ | 人の判断 |

**認証が要るものと要らないものが、ちょうど「取得」と「解釈」で分かれる。**
取得は API + Secret、解釈はローカルで完結する。

### 先に「解釈」だけ作った

`scripts/check-search-misses.mjs`（`npm run check:search-misses`）。
クエリの一覧を受け取り、**0件になる語**を洗い出す。

- 照合は画面と同じ実装（`src/pages/players/index.tsx`）:
  スペース区切りの語が**すべて** `searchText` に含まれるものが結果。
- 入力は「1行1クエリ」「クエリ,回数」「GA4 のページパス（`/players?q=...`・URLエンコード可）」を受ける。
  **GA4 の書き出しをそのまま流せる**ようにするため。
- 0件の語に加えて、**30件超ヒットの語**も出す（探している人にたどり着けていない疑い）。
- 終了コードは常に 0。**これは発見の道具であって、合否のゲートではない。**

動作確認（模擬データ）:

```
語の種類: 6 / 検索回数の合計: 310
**0件だった語: 2 種類（検索回数 55・全体の 17.7%）**
30件超ヒット（絞り込めていない疑い）: 2 種類
     30回  早稲田（75件）
     25回  ソフトテニス（1183件）
```

**なぜ取得より先に解釈を作ったか**: 手順1がそもそも空振り（GA4 側でクエリ文字列が
落ちている）かもしれない。空振りなら API 連携は無駄になる。
**手で1回書き出して流してみれば30分で分かる。** 同日の教訓「作るより先に、あるものを読む」。

### GA4 のデータ保持期間に注意（要確認）

GA4 のイベントデータ保持は**既定で2ヶ月**（14ヶ月に変更可）。既定のままなら
**2026-08-09 からのクエリは 2026-10-09 前後で消え始める**（Assumption・プロパティ設定を確認すること）。

もし消える設定なら、これは追記6の線引きでいう「**再生成できない記録**」にあたるので、
**定期的に取得してリポジトリへ書き戻す価値がある**（`review-snapshot.yml` と同じ形）。
逆に14ヶ月設定なら急がない。**まず設定を確認すること。**

### 自動化するとしたらの順序

1. **手で1回試す**（手順1）。空振りならここで終わり。
2. 出るなら **GA4 Data API での取得を Actions 化**し、`check-search-misses.mjs` に流して
   週次でジョブサマリに出す。保持期間が2ヶ月なら**取得結果もリポジトリへ書き戻す**。
3. GSC も同じ形で足す。
4. `out/` の静的解析はビルドが要るので最後。頻度も低くてよい（構造は毎日変わらない）。

## 追記2（2026-09-09）: 同意の地域分けと dev 除外で、前提が2つ変わった

同日、Cookie 同意を地域で分け（[ADR-018](../adr/ADR-018-consent-by-region.md)）、
**日本からのアクセスはバナー非表示・`analytics_storage` granted** になった。あわせて
**開発環境（`next dev`）では GA4 を読み込まない**ようにした。本アイデアの前提が2つ動く。

### 変化1: セッション単位の指標が「×」から「日本については○」になった

上の「信号の棚卸し」の表で **×** としていた行:

> | セッション単位の指標 | 直帰率・滞在時間など | **×** | 同意がデフォルト拒否で `client_id` が安定せず…… |

これは **2026-09-09 以降の日本からのトラフィックについては当てはまらない**。`_ga` が発行され
`client_id` が安定するので、直帰・滞在時間・セッションあたり閲覧数が読める。訪問者の大半が
日本なので、実質「読めるようになった」と考えてよい。

ただし:

- **2026-09-09 より前のデータには当てはまらない。** 本アイデアの出発点である
  「2026-08-09 以降に溜まっている検索クエリ」は**すべて旧レジームのデータ**。
  セッション系の指標をこの期間について読んではいけない。
- 広告ブロッカーと Safari ITP による `client_id` の不安定さは残る。ゼロにはならない。
- 非免除地域（EEA/UK 等）は従来どおり。

**帰結**: 「ページ内で詰まった場所」は依然として計測していない（表のもう1つの ×）が、
「着地して何もせず離脱したか」は 2026-09-09 以降のデータなら素直に読める。
手順3（行き止まりページ）は `internal_link_click` 比だけでなくセッション系でも裏を取れる。
