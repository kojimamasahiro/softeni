# インカレ2022 のエントリー抽出（見開きスキャンPDF・赤線＝棄権つき）

日付: 2026-09-10
対象: `2022_B08_40.pdf`（三笠宮賜杯全日本学生選手権大会 2022年度、16ページ・A3横）
成果物: `tools/incare-2022/{doubles,singles}-none-{boys,girls}.initialPlayers.json`
（ダブルス 男子527ペア・女子358ペア＝1,770名 / シングルス 男子142名・女子114名）

## 何が難しかったか（ユーザーの申告）

- 画像PDF（テキスト層ゼロ）
- **見開きで2ページ分が1ページに載っている**
- 男子ダブルスは PDF p5〜p8 に527ペア
- **棄権に赤線が引かれていて文字が見えにくい**

女子は後から追加依頼で PDF p10〜p13（358ペア）。

## PDFの素性

- 全16ページ、A3横（1191×842pt）、`pdfplumber` の文字数は全ページ **0**
- 各ページ1枚の画像、3307×2338px・8bit **RGB**（＝A3 200dpi）
- 男子ダブルス p5-p8（冊子の44/45, 46/47, 48/49, 50/51ページ）
- 女子ダブルス p10-p13（同 54/55 〜 60/61）

## レイアウト

1ページ＝見開き2ページ。**各印刷ページに2サブ列があるので、1画像に4サブ列**。

```
[左ページ]                          [綴じ]      [右ページ]
A: No. 氏名 (大学   ...ブラケット...   |   C: No. 氏名 (大学  ...ブラケット...
   ...ブラケット... 氏名 (大学 ) No.:B      ...ブラケット... 氏名 (大学 ) No.:D
```

- 男子: 1サブ列33件（B列のみ32件）×16 = **527**
- 女子: 1サブ列22〜23件 ×16 = **358**
- 1エントリー＝2行（ペアの2選手）。大学名とエントリー番号は**1行目の高さ**に置かれる
  （行間の中央ではない。ここを中央だと思って切ると全セルが半行ずれる）
- エントリー間ピッチ: 男子 約57.3px / 女子 約81.5px。ペア内2行間は約28.7px、
  2行が1つの連結ブロック（高さ約51px）として検出できる

### 氏名欄は「姓2枠＋名2枠」の固定グリッド

`[s1][s2][s3][s4]`（スロット間ピッチ 約47px）。

- **姓は左詰め**（1文字→s1のみ、2文字→s1+s2、3文字以上→s1に圧縮して詰める:
  `隈田原`=s1に「隈田」+s2に「原」、`八十川`、`小野田`、`四月朔日`）
- **名は右詰め**（1文字→s4のみ、2文字→s3+s4、3文字以上→s3に圧縮:
  `孝二郎`=s3に「孝二」+s4に「郎」、`亜人夢`、`日向翔`）
- 姓が長いと名が押し出されて s4 だけに圧縮されることがある
  （`四月朔日／海翔`、`北川／アンナ璃咲`、`ミヒニャック／杏`）
- **カタカナ氏名も同じ規則**（`ミヒニャック`、`ジャン瑠加`、`シュレスタ`型）

つまり `docs/wiki/data-import.md` のパターン2（固定テンプレートスロット型）に近いが、
**姓＝左詰め・名＝右詰めという整列規則が明確**なので、スロット占有だけで
「姓が何文字か／名が何文字か」が機械的に決まる（下の検算に使った）。

## 実際にやったこと

### 1. 赤インクの分離（棄権の機械検出＋文字の復元）

RGBスキャンなので赤ペンは色で分離できる。**これが今回いちばん効いた。**

- 赤マスク: `redness = R - max(G, B)`
- **棄権の検出**: 赤マスクの連結成分のうち「幅>150px・高さ<40px」を横線とみなす。
  男子21本・女子7本を検出した。**ただしこれは不十分だった（下記「棄権マークの追記」）**
- **文字の復元**: 単純に `redness > 25` を白で塗ると、**赤線と黒文字が重なった画素まで
  白くなり、字の上端が欠ける**（`濱村` が `濱柯` に化けた）。
  条件に **`min(R,G,B) > 85`（＝どのチャンネルでも暗くない画素だけ消す）** を足すと、
  赤線の下の黒画素が残って字が読めるようになる。膨張も同じ条件でガードする

赤線は「エントリー行の氏名〜大学名〜番号を横切る1本」なので、
**線のy座標→エントリー番号のマッピングだけで棄権リストが機械的に作れる**。

### 2. エントリー単位に切り出して区切り線を入れる

素朴に「N件ぶんの帯」を切ってLLMに読ませると、**s3が空のときに隣の行の字を
自分の行だと誤読する**事故が起きる（実際に281番を `大年吾・長島優奨` と誤読した。
正しくは `大年優吾・長島奨`）。

対策として、**1エントリー＝1セルに切り出し、セル間に黒い区切り線を挿入した縦長シート**
を作った。これで行とエントリーの対応が視覚的に確定する。

セルのアンカーは**大学名列の周期**ではなく、**氏名2行が融合した連結ブロック**
（高さ約51px）を使うほうが安定した。大学名列は列によって検出が揺れる。

1シート = 8〜11セル、拡大率1.75〜2.0倍。画像の長辺は1568px以下に収める
（それを超えると受け取り側で縮小されて解像度が落ちる）。

### 3. スロット占有による機械検算（転記ミスの自動検出）

上の「姓＝左詰め・名＝右詰め」から、**転記した姓・名の文字数と、画像のスロット占有は
1対1で対応する**：

- `s2 に字がある ⟺ 姓が2文字以上`
- `s3 に字がある ⟺ 名が2文字以上`

これを全エントリーで突合した。結果:

- 男子 1,054名中 不一致3件 → すべて誤検出（インク量が閾値付近／`四月朔日`の圧縮）
- 女子 716名中 不一致3件 → すべて誤検出（`アンナ璃咲`・`ミヒニャック`の圧縮、ゴミ点）

**この検算が281番の実際の誤読を捕まえた。** 目視だけでは気づけなかった。

### 4. ページ内スキュー

女子 p11（`pg-010`）だけ **シアー約 -0.042（≒ -2.4度）** の傾きがあり、
セル横断でスロット位置が最大60px流れる。セル単位の切り出し（高さ67px）では
ドリフトが4px程度なので読取りには影響しないが、**列全体を集計するスロット検出が壊れる**。
`cv2.warpAffine` のシアー補正を入れて解決した。他ページは -0.005〜-0.010 で無害。

傾きの実測は「列の上1/3と下1/3のインク横方向プロファイルを相互相関」で十分だった
（インターハイの回転角スイープより軽い）。

### 5. tesseractは使っていない

`docs/wiki/data-import.md` の方針どおり、氏名はセル画像をLLMが直読した。
200dpiのゴシック印刷は等倍〜2倍で十分読める。

## 棄権マークの追記（2026-09-10・ユーザー指摘を受けて）

**当初は「赤い横線（取り消し線）」だけで棄権を検出していたが、これは不十分だった。**
棄権の本体は**赤ペンの「R」**で、取り消し線は必ずしも引かれない。

- 男子は21件すべてが「Rつき＋取り消し線あり」で、線ベースの検出と一致した
- **女子には「Rだけで線が無い」エントリーがある。** ユーザー指摘の93番がそれで、
  検算のため全サブ列を目視で総ざらいしたところ 231・232・323 も同じ型だった
  （7件 → 11件）

Rの位置は一定しない。

- 男子: 番号の左（余白側）と、ブラケットの枝の先の両方に書かれることがある
- 女子: エントリーの印字の右（A/C列は ")" の直後、B/D列は番号の直後）
- 縦位置も行の中心から +10〜+30px ずれる（手書きなので一定しない）

**機械検出は男子だけ安定する。** 男子のRは連結成分の面積が570〜790と大きく、
得点の数字（130〜260）と面積だけで分離できる。女子のRは小さいものがあり
（93番は 15×31px・面積185）、得点の数字と重なるので面積では分けられない。
女子は**サブ列ごとに「番号＋ブラケット枝ゾーン」だけの細い帯を作って目視**した。
低倍率（0.5倍程度）だと231・232を見落としたので、**1.5倍以上に拡大すること**。

どちらのエントリーのRかは、**ブラケットの枝が赤でトレースされているか**で決まる。
勝ち上がった側の枝は赤で上書きされ、棄権側は点線のまま残る
（323/324なら324の枝が赤、323は点線＋R → 323が棄権）。

**女子の棄権リストは「全16サブ列を目視で1回さらった」結果であり、
機械検算による裏取りはできていない。** 結果（matches）を入力するときに
PDFのRマークと突き合わせて確定させること。

## 同一人物が複数エントリーに出るときの扱い（既存の確立済みルール）

**片方のエントリーが棄権し、その選手が別のエントリーに選手変更で入る**のは競技上ふつうに
起きる。同姓同名の別人ではなく、同一人物が正当に2エントリーに登場する。

**扱いは2026-08-13に確立済み**（[2026-08-13-player-name-variants-review.md](./2026-08-13-player-name-variants-review.md)
の「修正中に見つかった別件」）。当時 `participants` の `id` が同一ファイル内で重複している
ファイルが2件見つかり、ユーザーの説明でこのパターンだと判明した。

| ファイル | 選手 | 棄権した側 | もう一方 |
|---|---|---|---|
| `zennihon-championship/2022/doubles-none-boys` | 中本圭哉（福井県庁） | entryNo 58（2回戦敗退・`retired: true`） | entryNo 93 |
| `zennihon-championship/2023/doubles-none-boys` | 笹井悠月（木更津総合） | entryNo 24（1回戦敗退・`retired: true`） | entryNo 87 |

ルール:

1. **`entries` は両方残す。** 枠は2つ実在するので `playerIds` に同じ id が入るのが正しい
2. **`participants` は1行に畳む。** participants は**人の一覧**であって**エントリー枠の
   一覧ではない**ので、1人1行
3. 棄権側は `matches` に `retired: true`（スコアは相手の 5-0）、`results` は「N回戦敗退」
4. 参照は壊れない。`entries[].playerIds` は id 文字列、`matches`/`results` は entryNo で
   参照しており、participants を配列の添字で参照している箇所は無い

**教訓（当時の記録のまま）**: 「同一ファイル内の id 重複」は必ずしもデータ破損ではない。
