# AdSense 手動広告枠の実装（2026-08-23）

前提メモ: [2026-08-22-idea-adsense-manual-ad-units.md](./2026-08-22-idea-adsense-manual-ad-units.md)

## このセッションでやったこと

未実装のまま残っていた `AdUnit.tsx`（原案は 2026-06-12 の `docs/adsense-ui-proposal.md`）を
実装し、PV上位4面に1枠ずつ設置した。スロットIDは未設定なので**まだ広告は1つも出ていない**。

## 掲載面が原案から変わった経緯

原案の掲載面は「選手詳細2枠・チーム2枠・試合詳細3枠」、08-22 のアイデアメモの方向性は
「選手結果ページ（1,916枚＝最大母数）から1枠」だった。

実装に入る前に、選手結果ページが [circulation-verification.md](../wiki/circulation-verification.md)
の**対照群**として指定されている（「選手結果ページは触らない」）ことに気づいたため、
着手先をユーザーに確認した。回答は

> PVが多いのは、選手一覧ページ、大会結果、大会一覧、newsの展望の順に多いので、
> それらに広告をいい感じに入れたい

だった。この4面はいずれも対照群と重ならないので、対照群の衝突は自然に解消した。
（回遊施策自体はまだ未実装＝`data-link-module` を持つモジュールが `src/` に無く、
ベースラインも未取得なので、順序の入れ替えコストは今ならゼロだった。）

## 実際に置いた位置

初期配置は原案どおり「ファーストビュー回避」で、スクロール下方に置いた。

| ページ | 初期位置 |
|---|---|
| `/players/` | 「出場数の多い選手」表の直後 |
| `/tournaments/<...>/<gender>/` | トーナメント表の直後 |
| `/tournaments/` | 最初の年度ブロックの直後 |
| `/news/<articleId>/` | 最初のカテゴリ節の直後 |

**同日、ユーザーの指示でファーストビュー内へ全面的に移した**（下の「ファーストビューへの移動」節）。
上表は初期配置の記録であって現在の配置ではない。現在の配置は
[wiki/monetization.md](../wiki/monetization.md) が正。

`/tournaments/` は年度ブロック・フィルターバーの生成が `TournamentSearchTable` の内部に
あるため、差し込み口をコンポーネントに足し、**何を差し込むかはページ側が決める**形にした
（表のロジックが広告を知らないようにするため）。移動に伴い差し込み口も
`afterFirstGroup`（最初の年度ブロックの後）から `afterFilters`（フィルターバーの後）へ
置き換えた。

## 実測でわかったこと（設計に効いた）

### `data-full-width-responsive="true"` はレイアウトを壊す

最初 `true` で実装したところ、モバイル（375px）で AdSense が `ins` に

```
margin-left: -16px; width: 375px; height: 375px;
```

を当てた。つまり **PageLayout の左右パディングの外へはみ出し**、確保した
`min-height: 280px` も超える（＝レイアウトシフトが出る）。これは「自動広告でレイアウトが
崩れたから手動枠にする」という今回の目的と真っ向から衝突する。

`false` にしたところ `display: block; height: 280px;` に収まり、本文カラム幅・
確保済み高さと一致した（aside の実測 294px = 280 + ラベル14px）。CLS ゼロ。
収益目的で `true` に振るなら CWV を見る前提の実験として扱う、と ADR に書いた。

### SPA 遷移で `ins` を作り直す必要がある

サイドナビから `/tournaments/` → `/players/` とクライアント遷移して DOM を確認したところ、
広告 aside は1つ、その中の `ins` も1つで、`data-adsbygoogle-status="done"` が付いていた。
`ins` に `key={router.asPath}` を付けてノードごと作り直しているため、描画済みノードへの
再 push（"already have ads in them"）にならない。

なお同時に `body` 直下に slot 無しの `ins.adsbygoogle`（`data-ad-status="unfilled"`）が
1つあるが、これは自動広告の下部アンカー枠で手動枠とは無関係。

### ハイドレーション不一致は出なかった

`ins` をマウント後にだけ描画する実装にしたため、コンソールに React の警告・エラーは無し
（出ていたのは React DevTools 案内・HMR・`AdSense head tag doesn't support data-nscript
attribute` の3つだけで、いずれも無害）。2026-07-05 の #418 → `no_div` の再発条件を
構造的に避けられている。

## ファーストビューへの移動（同日・ユーザー指示）

「1st view で表示されるようにしたい。選手一覧は出場数の多い選手の上がいい」という指示で、
4面すべての枠をファーストビュー内へ移した。原案 `adsense-ui-proposal.md` の
「ファーストビューには置かない」を明示的に覆す変更。

移した先は各ページの「主目的の操作・リード文を終えた直後」で、h1 の上や主目的の操作より
上には置いていない。375×812（モバイル）での枠上端の実測:

| ページ | 移動後の位置 | 枠上端 | 枠下端(=上端+280) |
|---|---|---|---|
| `/players/` | 検索ボックスの直後・「出場数の多い選手」の前 | 402px | 682px |
| `/tournaments/<...>/<gender>/` | リード文の直後・年度/カテゴリ切り替えの前 | 408px | 688px |
| `/news/<articleId>/` | リード文の直後・最初のカテゴリ節の前 | 460px | 740px |
| `/tournaments/` | フィルターバーの直後・件数と年度ブロックの前 | 492px | 772px |

4面とも下端が 812px 未満＝枠全体がファーストビューに収まる。

### 大会結果ページだけ一度やり直した

最初は「年度・カテゴリ切り替えの**後**」に置いたが、実測で top=628px となり、枠の下半分
（628+280=908 > 812）が折り返しの下に落ちた。切り替えUIの**前**へ移して 408px になった。

これで分かったのは、**「ファーストビュー内」は節の順序を1つ変えるだけで簡単に破れる**
ということ。見た目で判断せず 375×812 で枠上端を測ること。実測値は wiki の掲載面テーブルに
列として持たせ、配置を触ったら測り直す運用にした。

### 受け入れたリスク

280px / 812px = 34% で、Lighthouse Publisher Ads Audit のビューポート垂直方向30%の目安を
モバイルでは超える。1ページ1枠を守る前提で許容している。2枠目を足すときはこの数字が制約になる。

### ローカルで unfilled → 畳み込みが動くことも確認できた

移動作業中に localhost で `data-ad-status="unfilled"` が付き、`aside` の `class` が空
（`my-8` が外れる）・高さ0まで畳まれた。未配信時に枠ごと消える経路が実際に動くことを
本番前に確認できた（localhost には広告が返らないため、結果的に良いテストケースになった）。

## 残していること

- ~~スロットIDが空~~ → **同日中にユーザーが4ユニットを発行し、ID を反映済み**
  （playersIndex 5268770947 / tournamentResult 8677583249 / tournamentsIndex 8402251079 /
  newsArticle 4306103716）。デプロイすれば4面同時に配信が始まる。
  当初案の「1面ずつ有効化」はこの時点で崩れている。面別RPM比較はユニットが分かれているので
  成立するが、CWV・回遊が悪化したときの原因面の切り分けはできない
  （切り分けたい場合は `AD_SLOTS` のキーを空文字に戻して1面ずつ消し込む）。
- なお管理画面のコピペ用スニペットは `data-full-width-responsive="true"` だが、
  上記の実測により `AdUnit.tsx` では `false` を維持している。この食い違いは意図的。
- 段階導入の合否閾値は暫定値（CLS 0.1 / 推定収益2週比較 / 回遊20%）。自サイト実測ベースの
  値ではない。1面目の実測が出たら差し替える。
- AdSense 管理画面側の設定（ページ内フォーマットのオフ・アンカー下部・ビネットオフ・
  除外URL）が実際に反映済みかは未確認。手動枠とページ内自動挿入が併存すると密度の
  歯止めが崩れるので、ここは前提条件。
- `next build`（静的エクスポート）は完走を確認済み（exit 0）。ただし回したのは `next build`
  単体で、`npm run build` の prebuild（データ生成スクリプト群）は既存の生成物をそのまま
  使ったため未実行。データ生成側と組み合わせた完走は本番デプロイ時に確認すること。
