# score 入力の自動推定（レシーブ失敗・シングルス）と動画時刻の配置変更

日付: 2026-08-11
状態: 実装済み（`/beta/matches/[matchId]/input`）。**DB migration の適用が必要**（`docs/sql/receive-order.sql`）。

## きっかけ

原文: 「サーブとレシーブは基本的に誰が行うかわかると思うので、レシーブミスの場合は誰が失敗したかと
どちらが得点かは一旦自動入力で入力されるようにしたい。他にも入力から推定できるものは自動入力して
ほしい。ただし、確定はこちらが行う」「開始を記録、終了を記録などの時間に関するものはサーブ情報の
上にしたい」。

## 実装前の状態（確認した事実）

- サーブ側は既に算出できていた: `getCurrentServingTeam` / `getCurrentServingPlayerIndex`
  （`lib/serveHelpers.ts`）。`games.initial_serve_team` と `initial_serve_player_index` が
  ゲーム開始時に保存されている。
- **レシーブ側の情報は一切無かった**。`games` にレシーブ順の列が無く、
  「レシーブ失敗のとき誰が失敗したか」はデータから決まらない状態だった。
- 自動入力は一部だけ存在: サービスエース（サーブ選手・サーブ側得点・ラリー数1）、
  ダブルフォルト（サーブ選手・相手得点・1stフォルト・ラリー数1）、
  レシーブ失敗のラリー数2、関与選手＋結果タイプ→勝者チーム（`determineWinnerTeam`）。
- 「開始を記録／終了を記録／クリア」はフォーム**最下部**（送信ボタンの下）にあった。

## スコープの決定（ユーザー選択）

- レシーバーの特定: **ゲーム開始時にレシーブ順も選ぶ**（DB列追加。過去のレシーブ失敗からの
  逆算・選手は自動入力せずハイライトのみ・画面上だけで保持、は不採用）
- 自動入力の見せ方: **通常の選択と同じ見た目**（「推定」バッジ等は付けない）
- 自動化の範囲: レシーブ失敗＋**シングルスの関与選手**まで。
  「結果タイプごとのラリー数初期値の拡張」「ミス系の得点チーム確定の穴埋め」は不採用。

## レシーブ交代ルール（Assumption）

ソフトテニスのダブルスでは**ゲーム開始時にレシーブ順が決まり、そのチームがレシーブする
ポイントごとに2人が交互に受ける**、というルールで計算している。競技規則の条文までは確認して
いないため Assumption 扱い。実運用で外れるケースが出たら見直す（外れても、推定値を手で
選び直せば記録内容は正しくなる）。

ファイナルゲームは2ポイントごとにサーブ／レシーブのチームが入れ替わるため、
「そのチームがレシーブした回数」を数えて交互に割り当てる。
`initial_receive_player_index` は**第1ポイントのレシーブチームについてのみ**意味を持ち、
途中からレシーブに回るチーム（＝第1ポイントのサーブチーム）は 0 番目の選手から始まる扱い。

実測（`getCurrentReceivingPlayerIndex`、`initial_receive_player_index = 1`）:

- 通常ゲーム（サーブ権A固定）: p1..p5 のレシーバー index = `1, 0, 1, 0, 1`
- ファイナルゲーム: p1..p6 = `1, 0, 0, 1, 1, 0`
  （p1-2 はB受け=1,0／p3-4 はA受け=0,1／p5-6 はB受け=1,0）

## 実装

1. `docs/sql/receive-order.sql`（新規）: `games.initial_receive_player_index`（0/1、null許容）を追加。
   **Supabase 側で手動適用が必要。** 未適用のままだと `games` PATCH が失敗する。
2. `lib/serveHelpers.ts`: `getCurrentReceivingTeam` / `getCurrentReceivingPlayerIndex` を追加。
3. `ServeSelection.tsx`: 「最初にレシーブする選手を選択」を追加（レシーブ側がダブルスのときのみ表示）。
   `onServeTeamSelected(team, playerIndex, receivePlayerIndex)` に第3引数を追加。
4. `lib/pointInference.ts`（新規）: `inferPointData(data, context)`。
   **空欄だけを埋める**（手で選んだ値は絶対に上書きしない）方針で以下を補完:
   - 結果タイプ＋関与選手 → 勝者チーム
   - サービスエース → サーブ側得点・サーブ選手・ラリー数1
   - ダブルフォルト → 相手得点・サーブ選手・1stフォルト・ラリー数1
   - **レシーブ失敗 → サーブ側得点・レシーブ選手・ラリー数2**
   - **シングルス（1チーム1人）→ 結果タイプ＋勝者チームから関与選手が一意**
   - `serving_team` も埋める
5. `useMatchInputController`: `buildPointInferenceContext()` を追加し `pointInferenceContext` を公開。
   **編集モードでは「次のポイント」ではなく編集対象ポイントのサーブ／レシーブを使う**
   （`editingPoint.game_id` からゲームを引き直す）。これは既存の
   「編集中もサービスエースが `getCurrentServe()`（＝次のポイント）を見ていた」という
   取りこぼしの修正にもなっている。
6. `PointInputForm`: すべての `setPointData` を `applyPointData`（＝推定を通す）に置換。
   レシーブ失敗ボタンだけは `loser_player` / `winner_team` を一度空にしてから推定に入れ直す
   （別の結果タイプで選んだ選手が残るのを防ぐため）。
7. `PointInputForm`: 「開始を記録／終了を記録／クリア」と動画時刻の手入力を
   **サーブ情報の上**（フォーム先頭）へ移動。区切りを押さえてから中身を入力する順序に合わせた。

## 追記: migration 未適用時の 500（2026-08-11）

初回動作確認で `PATCH /api/matches/[matchId]/games/[gameId]` が 500 になった。原因は
`docs/sql/receive-order.sql` 未適用で `initial_receive_player_index` 列が無かったこと。

対応:

- `games/[gameId].ts`: 列が無いエラー（PGRST204 / 42703）を検出したら、
  レシーブ順を外して再実行し、ゲーム開始自体は通す。console.warn で適用を促す。
  この場合レシーブ順は保存されないので、レシーブ失敗の推定は 0 番目の選手固定になる。
- `games/index.ts`: insert から `initial_receive_player_index` を外した（既定 null なので不要で、
  未適用環境でも insert が通る）。

## 追記: 「レシーブ失敗でサーブのチームが関与になる」報告（2026-08-11）

報告: レシーブ失敗を押すと、関与選手でサーブ側の選手が選択される。

調査:

- `inferPointData` を実データ（`public/data/beta-matches/matches/*.json`）で再現した結果、
  `loser_player` にはレシーブ側が入っていた。
  例: `initial_serve_team = B` のゲームで `p1: サーブ=B 片岡 / レシーブ=A 中平` →
  `loser_player = 'A-0-中平 慎吾'`。
- ダブルフォルト→レシーブ失敗の順に押す経路でも、レシーブ側に入れ直されることを確認。
- コード上、`receive_error` で `loser_player` にサーブ側が入る経路は見つからなかった。

対応（原因特定のための可視化＋編集モードの不整合修正）:

- サーブカードの表示を `getCurrentServingPlayer()`（＝常に「次のポイント」）から
  `pointInferenceContext` に切り替えた。**編集モードでは編集対象ポイントのサーブになる。**
  これまで編集中はサーブカード自体を隠していたため、
  「自動推定が何をサーブ／レシーブと見なしているか」が画面から確認できなかった。
- 同カードに「レシーブ: チーム X 選手名」を追加。
- レシーブ失敗を選ぶと、関与選手の上に
  「レシーブ失敗：レシーブ選手が自動選択されています／サーブ: … ／ レシーブ: …」を表示。
- 手動サーブ選手選択は編集モードでは出さない（編集対象ポイントのサーブは記録済みのため）。

これで画面上のサーブ／レシーブ表示と推定に使う値が必ず一致する。
表示が実際と食い違う場合は、`initial_serve_team` / ゲーム番号によるサーブ交代 /
ファイナルゲーム判定のいずれかがずれていることになり、切り分けができる。
