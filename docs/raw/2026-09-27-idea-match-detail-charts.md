# アイデア: 試合詳細ページのグラフ化と score 機能の需要の確かめ方

> **適用範囲: 混在**。「測れる読者に先に合わせる」という判断と需要の確かめ方は汎用。
> グラフの中身（ポイント単位の点差・決まり方・ラリー数）はソフトテニス固有。

## 状況

Idea Backlog。**発散フェーズ**（2026-09-27）。スマホ幅のモックアップを1試合の実データで作った段階。実装はしていない。
主な読者はまず観戦者、有料化は記録の道具の一般公開時、本体で見せる主役は「データから分かること」、と確定（末尾の追記）。ナビに「試合分析」を出した。

## 目的

試合詳細ページ（`/matches/[matchId]`、実体は `src/pages/beta/matches-results/[matchId]/index.tsx`）の
データ部分は、ほとんどが「◯件」の縦並びと表で、傾向が読み取りにくい。グラフにして分析しやすくしたい。

ただし検討の途中で、グラフより手前の問い（**そもそも誰がこのページを必要としているか**）が
確かめられていないことがはっきりしたので、需要の確かめ方も同じノートで扱う。

## ユーザーが興味を持った点

原文（2026-09-27）:

> スコア詳細のページで、データに関する部分をグラフなどを使って、データ分析がしやすいようにできないか検討したい

> スマホでも見れるようにしたい。
> まずは1試合の詳細ページでいいが、成長分析ページと完全に独立しないようには考慮したい。

score 機能の経緯（ユーザーの説明、原文）:

> 大元は試合データを集める時にユーザーからの投稿で補完できるようにしようとしたが、規模が大きくすぐにはできないので諦めた。
> 次に個人やチーム内でこのスコア機能を使えば、分析まで行えて成長記録として使えるようにしようとした。
> その成長記録がどういったものかを見せるために公開された動画で記録していっている最中である。
> そして、有料機能として展開できないかと思っている。
>
> どちらかというと開発者側の思惑から作っている機能であるので、ユーザーニーズと一致していないかもしれない。

> 検証はできる環境にはいないので難しい

最後の発言が方針を決めた。選手や顧問に直接話を聞けないので、
**ネット上に残っている反応と、サイト内で測れる数字だけで判断する**前提で組み立てる。

## 想定運用 / なぜこのスコープか

### 有料化までに成り立つ必要がある前提

| # | 前提 | 状態（2026-09-27） |
|---|---|---|
| 1 | 他人の試合の分析を見たい人がいる（観戦者・保護者） | GA4 で測れる。未読 |
| 2 | 自分の試合を分析したい選手・顧問がいる | 未確認 |
| 3 | 自分で記録する手間をかけてくれる | **いちばん危ない**。記録の道具は他のアプリがすでに複数ある |
| 4 | お金を払う | 未確認。競合の料金は下記 |

グラフで見やすくすることが効くのは主に1と2。有料化を左右する3と4は、グラフでは確かめられない。

### 仮の方針

- **試合詳細ページの主な読者は、まず観戦者（メディアとして読む人）にする。**
  GA4・Search Console で成果が測れ、有料化が崩れても広告と検索流入に効く（ADR-003 の「閲覧公開＝メディア」側の出口）。
- **有料の道具にする道は残し、反応を測る入口だけ置く。** 反応が無いうちは記録の道具側に手をかけすぎない。
- ページは2段にする: 上＝誰が見ても分かる図（点差の推移、得点の内訳）、下＝振り返り用（ラリー長、率の比較、成長分析への入口）。
- 判断の期限を決める（例: 3か月で入口の押下と共有がほぼ無ければ、有料化は保留してメディアに絞る）。
  **数字は仮で、ユーザーが決める**。

### 直接話を聞かずにできる確かめ方

| 方法 | 分かること | 手間 |
|---|---|---|
| 競合アプリのストアのレビューを読む | 何を求め何が不満か、有料への反応 | 小（2026-09-27 に実施、下記） |
| GA4 で試合ページ・成長分析ページ・共有ボタンの数字を見る | 前提1 | 小 |
| 詳細ページに「自分の試合も分析したい方へ」の入口を置き、押された回数だけ数える | 前提2 | 小。個人情報は集めない。押した先は既存の `/contact` |
| X で「動画を送ってくれたら分析します」と無料で募集する | 実際の利用者と反応 | 中（発信が要る） |

読み取れること（Assumption）:

- **流れのグラフや決め球の集計は、競合がすでに持っている。** グラフそのものは差別化にならない。
- 競合で不満が出ているのは **試合をまたいだ集計（選手・ペア別）** と **アプリを入れていない人への共有**。
  score 機能は成長分析（試合をまたぐ）と Web ページ（URL で誰でも見られる）を最初から持っているので、
  **詳細ページと成長分析ページのつながり**と**共有しやすさ**が差別化になりうる。
- 料金は **買い切り800〜1,000円か月400円** が相場で、月額には抵抗がある。有料化するなら単価は低い前提で考える。
- 前回の調査（2026-09-17）では、有料の採点票アプリがスポーツ有料ランキング2位だった。記録の道具にお金を払う人はいる。

## 課題・未解決

- 主な読者を観戦者にする方針でよいか（ユーザー確認待ち）。
- 判断の期限と基準の数字。
- 「自分の試合も分析したい方へ」の入口を置くか、置くならどの文言で、押した先をどうするか。
- 成長分析との重ね方: 詳細ページの率に過去の範囲を重ねるのは、公開の許可がある選手・ペアだけ（ADR-004）。その場合の見せ方。
- 試合をまたいだ集計が競合の不満点なら、詳細ページより成長分析ページの方を先に良くすべきか。
- 実装方針: グラフのライブラリを入れずインライン SVG（Core Web Vitals への影響を避ける。monetization の CWV 改善案と関係）。
  ダークモード、`src/**` の絵文字禁止（ux-writing.md）、装飾 SVG の `aria-hidden` に合わせる。
- 共有リンク（2026-09-25 実装）との関係: 流れのグラフから1本のラリーを共有できるようにするか。

## 追記: 方針の確認と裾野の広げ方（2026-09-27）

ユーザーの発言（原文）:

> 読者はまずは観戦者がいいが、実際はプレイヤーに使ってもらえるようにしたい。そのためにまずは観戦者をターゲットにして裾野を広げたい。そもそもSEOやサイト内導線などまだ力を入れていない部分がある。
> そのため、GA4での数値はまだまだ未定な部分が多い。
>
> 有料化は基本行うが、有料にする場合はこのスコア機能を一般に公開したタイミングであるので、今は公開していないのでそもそも有料にするものがない。

確定したこと:

- 主な読者は**まず観戦者**。最終的な狙いはプレイヤーに記録の道具として使ってもらうこと。
- 有料化は**記録の道具を一般に公開するときに行う**。今は有料にするものが無いので、「3か月で判断」の期限の案は取り下げる。
- GA4 はサイト内導線・SEO に手を入れる前なので、数字をそのまま判断材料にしない。

現状（2026-09-27 実測）: 公開27試合のうち26試合が siteLink つき。逆引きで選手39人・大会ページ14件から
「スコア詳細のある試合」節にリンクされている（`public/data/beta-matches/reverse/*.json`）。

提案した見立て（Assumption、ユーザー未確認）:

- ソフトテニスの観戦者はほぼプレー経験者か保護者・顧問なので、観戦者からプレイヤーへの流れは無理が少ない。
  観戦者向けのページにも「自分の試合でも（準備中）」の入口を最初から置き、押下数を道具公開の判断材料にする。
- 試合1件を名指しで検索する需要は小さいので、裾野を広げるのは次の順:
  1. 本体サイト（選手ページ・大会結果ページ）からの導線を強くする
  2. 記録する試合を、見に来る人が多い順（検索されている選手・主要大会の決勝）に選ぶ
  3. 外に広まる単位（名場面・1本のラリーの共有・X 投稿）
  4. 試合ページ自体の SEO は後回し
- グラフ化は人を連れてくる力は弱く、入ってきた人を次の試合や成長分析へ進ませる役。1〜3と組み合わせて効く。
- 当面見る数字: 公開試合数、選手・大会ページ→試合ページの `internal_link_click`、共有ボタンの押下、GSC の試合 URL の表示回数、入口の押下。

## 追記: 本体とスコアサイトの整理、見せるものの転換（2026-09-27）

### 本体とスコアサイトの現状（実測）

- `score.softeni-pick.com` は DNS 未設定で、公開されていない。スコア関連のページはすべて本体にある。
- 本体の `/matches/[id]` は掲載大会配下のネスト URL を canonical にしている。`/matches/growth` は noindex。
  `/growth/[slug]`（上岡選手・上岡丸山ペアの成長記録）は index 対象でナビにも出ている。
- wiki の一部（score-analysis.md・beta-matches-results.md・project-overview.md・public-pages.md）が
  「score mode＝score サブドメインの閲覧専用公開面」と書いていて、ADR-003（score サブドメイン＝記録の道具）と食い違っていた → 修正した。

### ユーザーの判断（原文）

> スコアサイトの閲覧専用の設定は、ユーザーが個別で登録した試合をプライベートで見るために必要ではないか？
> 3番はまだお試し期間ということで出さなかったが今回から出すように変更したい
> 4番はユーザーが登録した試合を載せるのはリスクがあるので、まだ本体サイトには載せない方針にしたい。

> 5番に関して思ったことがあるが、youtubeに公開されている試合しかスコアしかないからスコアより動画を見にいくのではないかと思った。そうなるとスコア機能としては弱いので、やはりスコアを見に来るのはあくまで副次的なもので、メインはスコア機能から得られる情報を使ったデータ活用によって生まれる付加価値を見てもらうように進めるのがいいのではないかと思った

> 「試合分析」で、5番の方向で進めて

### 決まったこと

- **閲覧用の score mode は残す。** 非公開の試合を見る画面は Phase 2 で要る。ただし今の外枠は静的生成で非公開の試合には使えず、
  再利用するのは `PublicMatchDetailPage` と分析ロジック（ADR-003 の追記）。
- **ナビに「試合分析」（`/matches`）を出した**（docs/ui D-026、D-011 を覆す）。`public/llms.txt` の未デプロイの score サブドメインの行も消した。
- **利用者が記録した試合は本体に載せない**（ADR-003 の追記）。本体の試合は運営が公開動画から記録したものだけ。
- **記録する試合は「人」では選ばない。** 動画が無いとスコアが取れないので、選べる余地は動画の有無で決まる。
  （前の追記の「見に来る人が多い順に選ぶ」は取り下げ。）
- **本体で見せる主役は「スコア」ではなく「データから分かること」。** 公開動画がある試合なら観戦者は動画を見るので、スコアの閲覧は副次的。

### 「データから分かること」に寄せた場合の見立て（Assumption、方向はユーザー了承済み）

| 動画では分からないこと | 今ある材料 |
|---|---|
| 試合をまたいだ変化 | 成長記録（`/growth`） |
| 場面ごとの傾向（デュース、1本目など） | 分析ロジック（重要局面） |
| 珍しい出来事・記録 | 名場面の検知、大会インサイト |
| 長い動画のどこを見ればよいか | 流れのグラフ、1本のラリーの共有 |

- 試合詳細ページの上の段は、グラフより「この試合で分かったこと」（文章）を先に置き、グラフはその根拠と動画の道案内にする。
  モックアップの流れのグラフはこの役で残す。
- 本体の主役は試合単位より**選手単位**。選手ページは検索で人が来る場所なので、「この選手の試合データから分かること」を選手ページに出すのがいちばん届く。
- 道具を公開するときの売り文句と同じ形になる（「トップ選手で分かること」→「自分の試合でも分かる」）。
- 記録は27試合で1人あたり数試合。言い過ぎないよう、件数の併記と自己比較だけの方針（2026-08-04）は守る。

### 次の候補

## 追記: ポイントの並びと「決め球とミス」（2026-09-27）
