# AdSense 掲載面の拡大とフッター枠（2026-08-25）

前提: [2026-08-23-adsense-manual-ad-units-implementation.md](./2026-08-23-adsense-manual-ad-units-implementation.md)

## 出発点

「想定より収益がありそう。もっと他のページにも載せてもいいかもしれない。
また、ページ下部であるフッターの上に載せてもいいかと思ったがどうか」（ユーザー）

## 在庫の実測（`out/` 全4,390枚）

拡大の前に、どこに何枚あるのかを数えた。**広告が載っていたのは433枚（9.9%）だけ**だった。

| 種別 | 枚数 | 全体比 | 8/23時点の広告 |
|---|---|---|---|
| `player_results` | 1,916 | 43.6% | — |
| `hs_school` | 801 | 18.2% | — |
| `tour_year` | 423 | 9.6% | あり |
| `team_year` | 316 | 7.2% | — |
| `jhs_team` | 303 | 6.9% | — |
| `stleague` | 177 | 4.0% | — |
| `tour_hub` | 127 | 2.9% | — |
| `hs_pref` | 94 | 2.1% | — |
| `team_hub` | 67 | 1.5% | — |
| `jhs_pref` | 47 | 1.1% | — |

上位2種別（合計62%）が回遊検証に縛られており、ここを開けないと拡大の効果は限定的だと分かった。

## 判断1: 回遊検証は諦めなくてよかった（前回の自分の制約が過剰だった）

8/23 に「選手結果ページは対照群だから触るな」と書いたが、これは過剰な制約だった。

ランブックの判定式は **（学校ページの変化）−（選手結果ページの変化）** で、水準差ではなく
**変化の差**を見る。したがって要件は「対照群に広告を入れないこと」ではなく
**「測定期間中に両群が別々に変化しないこと」**。両群へ同時に入れて定常化させれば判定は成立する。

ベースライン取得は平常期の2026年9月末予定。今日が8/25なので約5週間あり、間に合う。
この整理で全ページの62%が解禁された。

**残る制約**: ベースライン取得後・測定期間中は `player_results` / `hs_school` の広告設定を
一切触らないこと。片側だけ動かすと壊れる。ランブック側にも運用ルールとして書き戻した。

## 判断2: フッター枠は「ページごとに貼る」のをやめた

`AppShell` の `<main>` と `{footer}` の間に**1箇所だけ**置き、`FOOTER_AD_PAGE_TYPES`
（`lib/ads.ts`）の許可リストで出し分ける方式にした。面を増やすのが**リスト1行**になる。

判定に既存の `getPageType()`（回帰テスト `npm run analytics:test` 済み）を使ったのが効いた点:
**判定がパス基準なので、`/matches/*` と `/beta/matches-results/*` のように実体が同じ
コンポーネントでも beta 側だけ除外できる**。ページ側に手を入れずに済んだ。

## 判断3: 種別の許可リストだけでは AdSense ポリシー違反面を作ってしまう

dev で確認していて `/tournaments/local/osaka/` に広告が出ているのを見つけた。このページの
本文は「現在登録されている大会はありません。」だけ（`<main>` 実測**78文字**）。
種別としては `tour_hub` なので許可リストを通ってしまう。AdSense は**コンテンツのない
ページへの掲載を禁じている**ので、これは出してはいけない面。

種別で一括許可する方式の穴だった。`out/` 全体を測って実態を把握した:

| 種別 | 枚数 | `<main>` 本文の中央値 | 最小 |
|---|---|---|---|
| `tour_hub` | 127 | 207 | **78** |
| `team_year` | 316 | 332 | 142 |
| `player_profile` | 23 | 406 | 244 |
| `stleague` | 177 | 486 | 396 |
| `jhs_team` | 303 | 562 | 246 |
| `jhs_pref` | 47 | 571 | 418 |
| `team_hub` | 67 | 730 | 261 |
| `hs_school` | 801 | 1,216 | 798 |
| `player_results` | 1,916 | 2,419 | 1,600 |

対策として **`main.textContent` の文字数（空白除去）が400未満なら枠を出さない**歯止めを
`AppShell` に入れた。閾値は上の分布から選んだ:

| 閾値 | 除外枚数 |
|---|---|
| 150 | 51 |
| 200 | 127 |
| **400** | **417（9.6%）** |
| 600 | 809 |

400 なら空の `/tournaments/local/*`（78文字）と結果の乏しいチーム年度ページを外し、
成績表が1つでも載っているページ（中学チーム 中央値562文字）は残る。
**除外リストを保守しなくてよく、データが増えれば自動的に広告が出るようになる**のが利点。

判定はクライアント（マウント後）で行う。サーバー側に本文量を知る手段がないため。
その結果フッター枠だけ SSR HTML に含まれないが、位置がページ最下部なので通常の閲覧開始位置
では見えている要素が動かず CLS にならない。ファーストビュー枠は従来どおり SSR で高さを確保。

## 実測での確認

| ページ | `<main>` 文字数 | 枠数 | 位置 |
|---|---|---|---|
| `/tournaments/local/osaka/`（空） | 78 | **0** | 歯止めが効いた |
| `/secondaryschool/shizuoka/seiminamiclub/`（薄い） | 246 | **0** | 同上 |
| `/highschool/boys/tochigi/yaitachuuou/` | 1,731 | 1 | フッターのみ(5,113px / 全高5,612px) |
| `/players/1/results/` | 4,107 | 2 | 596px と 8,164px |

許可リストの除外も SSR HTML への fetch で確認: `/privacy/` `/contact/` `/about/` `/faq/`
`/beta/matches/` は枠なし、`/` `/highschool/` `/rankings/` `/teams/` `/secondaryschool/` は枠あり。

1ページ2枠になる面の同一ビューポート判定（375×812）:

| ページ | 枠1 | 枠2 | 間隔 |
|---|---|---|---|
| 選手結果 | 596px | 8,164px | 7,568px |
| 大会結果（**最短の1枚**） | 388px | 1,466px | 1,078px |
| news 展望（最短の1枚） | 428px | 3,902px | 3,474px |

最短の大会結果ページでも間隔1,078px > 812px なので2枠が同時に画面へ入ることはない。
薄い種別（高校学校・中学チーム・チーム年度など）にはファーストビュー枠を置かず
フッター枠だけにしてあるのも同じ理由。

## 選手結果ページのファーストビュー枠が596pxと低い理由

他の面（402〜492px）より低い。ヘッダーに主要大会タイル（`PlayerMajorResults`）が入るため。
タイルは2026-07-20の決定で「文章の流れを保ちつつファーストビューには収まる位置」に
置かれており、その上に広告を差し込むとタイルが折り返しの下へ落ちる。
**既存の決定を優先して枠を下に置いた**結果、280pxのうち216pxが可視、下64pxが折り返し下になる。

## 残していること

- `AD_SLOTS.playerResults` と `AD_SLOTS.footer` が空。管理画面でユニットを2つ作って
  貼るまで、拡張分は1枚も配信されない。
- **下部アンカー広告とフッター枠の重なりが未確認**。モバイルのアンカーは `position: fixed`
  で最下部に貼り付くため、フッターまでスクロールすると「フッター枠280px + アンカー約50px」が
  同一画面に並ぶ（812pxの41%）。ローカルでは自動広告が配信されないので本番でしか見られない。
  見苦しければアンカーを切るかフッター枠を切るかを決める。
- 9月中旬までに `player_results` / `hs_school` を定常化させること（9月末のベースライン用）。
