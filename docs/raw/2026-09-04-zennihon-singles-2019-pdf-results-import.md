日付: 2026-09-04
入力: `2019_A02_40b.pdf`（12p, ユーザー提供）
出力:
- `tools/zennihon-singles-2019/singles-none-{boys,girls}.initialPlayers.json`
- `data/tournaments/details/zennihon-singles/2019/singles-none-{boys,girls}.json`
- `data/tournaments/information/zennihon-singles.json` に2019年度を追記
スクリプト: `scripts/pdf/zennihon_championship_results.py`（既存、`SCORE`/`_ret`/`_val` を
本セッションでランタイムパッチ。恒久化は未実施 — Open Questions 参照）

前段の `tournament-pdf-to-players` でのエントリー抽出は同日の会話内で完結（raw note化せず）。
本ノートはその続きの結果（matches）抽出と、抽出過程で発覚したエントリー抽出側の並び順バグの

## 大きな誤解: 「ラウンド1のドローだけのページ」ではなかった

最初、p3-6（男子）/p9-12（女子）を「1回戦だけのフラットな対戦リスト」と誤認して
initialPlayers を作った（行の左右を1回戦の対戦相手とみなした）。実際は**そのページ単体で
1回戦から準々決勝まで完結する赤い実線のトーナメント表**だった。

正しい構造（男子の例、62エントリー/ページ）:

- 各ページは左31名・右31名の2ブロックに分かれ、**ブロック内の隣接エントリーどうし**が
  1回戦の対戦相手（同じ行の左右ではない）
- 各ブロックは31名を6ラウンドかけて1名まで絞り込み、最後に左ブロック優勝者×右ブロック
  優勝者が対戦して**そのページの優勝者**を決める
- **そのページの優勝者が、そのまま準々決勝の出場者**（p1/p7のスコア記入表の準々決勝は、
  必ず同一ページ内の2エントリーどうしの組み合わせになる。男子QF1=`1 vs 48`は両者ともp3、
  QF2=`78 vs 94`は両者ともp4、という具合）
- 256枠（248エントリー、8不戦勝）× 4ページ = 全体のドロー

これに気づく前は「p2/p8『ベスト64』ページが2回戦以降を継続しているのでは」と考えたが、
それも誤り。p2/p8は**1・2回戦の内容が重複する再掲**で、取り込みには不要（2017年度
天皇杯と同じパターン。[data-import.md](../wiki/data-import.md)既記載）。

### エントリー抽出（initialPlayers）側の並び順を作り直した

上記の誤解により、先に作った `initialPlayers.json` は**選手名・所属は正しいが1回戦の
対戦ペアが間違っていた**（同じ行の左右でペアにしていたが、正しくは同じブロック内の
隣接エントリー）。`tools/tournament3` の `buildBracket()` は配列を `players[i]` vs
`players[i+1]` で機械的にペアにするため、並び順の誤りがそのままブラケット表示の誤りになる。

修正手順:

1. `scripts/pdf/zennihon_championship_results.py` の `_own_lines`/`_frames`
   （点線・実線のベクター矩形を追跡して1回戦の組を復元する関数。詳細は
   [2026-09-02のノート](2026-09-02-zennihon-championship-2017-2019-results-from-pdf.md)）を
   両ブロック（L/R）に適用し、不戦勝を含む正しい1回戦の並びを復元
2. `rows_and_scores()` が返すエントリー番号と、既存の氏名抽出（行の中点で姓名分割する
   独自ロジック）を行の y 座標で突き合わせて `entryNo → 選手情報` の対応表を作る
3. 256枠（4ページ×左右2ブロック×32枠）の配列を組み立て、不戦勝の枠には JSON `null` を
   明示的に入れる（`tools/tournament3` の `newMatch()` が `players[i] ?? byePlayer` で
   拾う前提）
4. `id` は不戦勝を除いた実選手の連番。**このIDは元PDFの entryNo と完全に一致する**
   （男女とも entryNo が 1 から欠番なく連続しているため。詳細は Assumption 参照）

修正後: 男子248名+不戦勝8枠=256枠、女子223名+不戦勝33枠=256枠。

## 結果（matches）抽出

### 1回戦〜準々決勝: ドローページ自体を `--loser-only` 方式で解く

各ページが「そのページ単体で1回戦から準々決勝まで完結する」ことが分かったので、
`parse_draw_page_loser_only(page, last_round=6, pad=5)` を8ページ（p3,4,5,6,9,10,11,12）に
そのまま適用した。`pad`（敗者スコアの持ち主判定のy許容）は既定20だと行ピッチ23.3ptに対して
広すぎ隣の枠のスコアを拾ってしまうため、**pad=5〜6程度に詰める必要があった**
（既定のインターハイ/天皇杯より1ページのエントリー数が多く行ピッチが狭いため）。

8ページとも成功。QFの勝者は全ページ、p1/p7のスコア表側の準々決勝と一致した
（詳細は下記「検算」）。

### 準々決勝〜決勝: p1/p7のスコア記入表

p1（男子）/p7（女子）は準々決勝・準決勝・決勝の詳細を記録したスコア記入表。
1ブロック=1試合で、丸数字が勝者の本数・裸数字が敗者の本数（天皇杯と同じ丸数字規約）。
ブロックの構造は「サマリ行（勝者-敗者の総本数）→氏名行→ゲームごとの明細行（複数）」。
**明細行の意味（何本目の何のスコアか）は判読しきれなかったが、`data/tournaments/details`
のスキーマは試合ごとに1組の勝敗本数しか持たないため、サマリ行の値だけで足りる。**

### スコアの左右位置と勝者の対応がページによって信頼できない

p1（男子）はサマリ行の「circled値の物理位置（x≈263=先に印字された選手の欄）」が
そのまま勝者と一致し、7戦(QF4戦+SF2戦+F1戦)すべてで矛盾なく成立した。

**p7（女子）は準々決勝4戦すべてで逆転していた**（circled値の位置は先に印字された選手の
欄なのに、実際に勝ち上がったのは後に印字された選手）。準決勝2戦・決勝1戦は逆転していない。
原因は特定できていない（同一テンプレートで印字位置バグとは考えにくいが、他に説明がつかない
— Open Questions参照）。

このため**「サマリ行の位置」から勝者を決めるのをやめ、常に「次のラウンドの参加者リスト」
から勝者を逆算する**方式に切り替えた:

- 準々決勝の勝者 = ドローページ側の該当ページの優勝者（上記の通り8ページとも一致、
  かつこちらはベクター線を追跡した独立読み取りなので、この不一致の影響を受けない）
- 準決勝の勝者 = 決勝ブロックの出場者2名のどちらか（氏名行の entryNo を直接読むだけなので
  位置解釈に依存しない）
- 決勝の勝者 = **PDF内に次のラウンドが無いので上記の方法が使えない**。Web検索で外部確認した
  （下記「検算」）
- スコアの値自体（何本-何本か）は「circled=勝者の本数、裸=敗者の本数」で常に読み取り、
  上で決めた勝者に割り当てる（位置と選手の対応が壊れていても、値のペア自体は正しく読める）

### `R0`（棄権, R前置）表記

女子p11（QF3手前）で `R0` という1トークンに遭遇。`zennihon_championship_results.py` の
`SCORE` 正規表現・`_ret`/`_val` は `4R`（数字→R）の並びしか想定しておらず、`R0`
（R→数字）はスコア語として認識されず脱落し、「L側のスコアが1個足りない」で
`parse_draw_page_loser_only` が失敗した。本セッションではモジュール関数を実行時パッチして
`R` が前後どちらに来ても拾うようにした（恒久化は未実施、Open Questions参照）。

### エントリー抽出側のバグをもう1件発見: 非対称最終行

女子p9は左ブロック27名・右ブロック28名（左右非対称。他の7ページは全て左右同数）。
自分の行氏名抽出ロジック（2名ペアで parens×2 を前提にする `parse_row`）は、
右ブロックの最終行（1名だけの行、parens×1）を認識できず1行分黙って欠落させていた。
その結果、entryNo 55（本当は `山田優菜`, 三重・松阪興産）が、y座標最近傍マッチングで
1つ手前の行 entryNo 54（`十河まゆ`）の情報を誤って引き継いでしまい、**同一選手が
entryNo 54・55の2枠に重複して入る**という形で症状が出た
（`normalize-team-names.mjs --dry-run` の「同一IDへ統合された参加者」警告で発覚）。

検出方法として有効だったのは、**各ページで「氏名行としてパースできた行数×2」と
「rows_and_scores() が返すエントリー番号の総数」を突き合わせる**こと（8ページ中この
1ページだけ54≠55で不一致）。この突き合わせをしていなければ、`build()`/`check()`
（`data/tournaments/details` 側の自己検査）は「同姓同名の選手が2試合に出た」という
見た目上つじつまの合うデータとして通してしまい、**気づけなかった可能性が高い**
（`check()` は選手の重複そのものは検査しない）。

## 検算

- **準々決勝の勝者**: ドローページ側（ベクター線追跡）とp1/p7スコア表側（circled値、
  ただし女子は位置反転を補正）を独立に読み、男女とも8戦全て一致
- **決勝の優勝者**: PDF内に検算材料が無いため、Web検索で外部確認した。
  - 男子: 船水颯人（Yonex公式ニュース「船水颯人が全日本シングルスで3連覇達成！」で確認）
  - 女子: 林田リコ（東京女子体育大学）優勝、早川日向（ナガセケンコー）準優勝、との検索結果で確認
    （Wikipedia「全日本シングルスソフトテニス選手権」の言及に基づく要約）
- **repo側の自己検査**: `tournament_results_common.check()` が男女とも0件、
  `node scripts/check-tournament-entries.mjs` / `check-orphan-entries.mjs` /
  `check-duplicate-placements.mjs` / `npm run bracket:verify` を通し、いずれも
  本大会に起因する指摘なし（`bracket:verify` の唯一の不一致は無関係の既存データ
  `highschool-championship/2013`）

## Assumption

- initialPlayers の `id` が元PDFの entryNo と完全一致するという前提で、結果側の
  `entries`/`matches` の参照にも entryNo をそのまま使っている。男女とも entryNo が
  1から欠番なく連番であることを機械的に確認した上での運用（8ページ全てで
  `paired_rows_parsed*2 == rows_and_scores() の総数` が成立することを検証済み、
  女子p9の1件を除く。p9も修正後は成立を確認）
- `data/tournaments/information/zennihon-singles.json` の2019年度エントリーの
  「第26回」表記と `sourceUrl` は上記の通り推測（Assumption）
