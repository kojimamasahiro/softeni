# Claude不在時のローカルLLM代替 — 設計メモ

`tournament-insight` / `tournament-pdf-to-players` / `tournament-venue-data` の3skillを、
Claudeが使えなくなっても同等の結果が出せるようにする。今回は**設計のみ**（3skill並行）。
実装フェーズは別途、優先度を決めてから着手する。

## 前提として棚卸しした現状（今回の調査で判明）

3つのskillは「LLMがどれだけ要るか」がまったく違う。調査の結果、想定と食い違う点が2つあった。

| skill | 決定的スクリプトの現状 | LLMの役割 | ローカル化の状態 |
|---|---|---|---|
| tournament-venue-data | **既に実装済み**（`scripts/venue-agent/`） | 会場テキスト→JSON構造化の狭い判断のみ | ✅ 動作確認済み（`test_regression.py` 5/5 pass） |
| tournament-pdf-to-players | **未実装**。SKILL.mdが前提とする `scripts/extract_tournament.py` はリポジトリ全体を検索しても存在しない | 本来ほぼ不要（座標ベースの決定的抽出） | ❌ 新規実装が要る。しかもLLMなしで作れる |
| tournament-insight | 生成(`generate-story-yaml.mjs`)・検証(`verify-story-text.mjs`)は健在 | YAML→散文の執筆のみ | ❌ ローカルLLMラッパーが無い。新規実装が要る |

つまり「3skillを均等にローカル化する」のではなく、venue-dataは**現状確認だけで実質完了**、
残り2つが本命の新規実装になる。

## 共通方針

このプロジェクトのADR-005/ADR-012が敷いた役割分担をそのまま踏襲する。ローカルLLMに変えても
この分担は変えない（変えるとADR-005が守ろうとした「誤った事実を公開しない」が崩れる）。

| 工程 | 担当 | ローカル化してもここは変えない理由 |
|---|---|---|
| 事実の抽出 | スクリプト（決定的） | LLM（クラウドでもローカルでも）に数えさせると間違える |
| 狭い構造化判断 | LLM（ローカル可） | テンプレ処理では表記ゆれ・文脈依存の判断ができない |
| 事実の検証 | スクリプト（決定的） | 人のレビューは「もっともらしい誤り」を素通りする。モデルが変わるほど重要度が増す |
| 公開判断 | 人 | 最終責任。ここは自動化しない |

ローカルLLMは9B〜14Bクラスで、クラウドのClaudeよりtool-use・長文指示追従が弱い。
このため**LLMに渡す判断の粒度を、クラウド版よりさらに狭くする**のが設計の核。
venue-agentが「1施設ぶんのテキスト→JSON」までしか頼まず、ツール呼び出しを使わない設計に
しているのは、まさにこの理由（`llm_client.py` のコメント参照）。同じ流儀を他2つにも適用する。

## A. tournament-venue-data（現状確認のみ）

`scripts/venue-agent/` が既にこの思想で実装済み。

```
PDF →(pdfplumber)→ 「会場」節テキスト ★人に見せる
   →(Ollama qwen2.5:9b-instruct)→ 施設ごとのJSON
   →(checks.py: 決定的)→ prefecture/address突合・郵便番号/電話番号の桁チェック・surface語彙チェック
   → draft-*.json（要確認フラグ付き）
   →(人)→ apply → data/tournaments/information/*.json
   →(決定的)→ 全件検算を再実行
```

`test_regression.py` を実行し、SKILL.md記載の実例（福山市/福知山市の誤記、東舞鶴公園のTEL桁落ち、
未知surface表記の検出）が5/5とも正しく検出されることを確認済み。モデル(qwen2.5:9b-instruct)を
呼ばない部分だけのテストなので、Ollama未セットアップでも通る。

### 残タスク（要判断・今回は設計のみ）

READMEの「既知の限界」に3点が明記済みで、これは実装当時から意図的な保留。今回追加で判断が要るのは
「どこまで埋めるか」のみ:

1. `venue-candidates.json` とのconfidenceマッチング（日付だけの照合で誤マッチが出る問題）は未実装のまま。ローカルLLM化の対象に含めるかは要判断。
2. 会場が日別・種目別に分かれているかの一次判定は現状LLM任せ（`split_by`）。9Bの判定精度をどこまで信用するかは実データで検証してから決める。
3. 施設マスタ切り出し（3回以上出現で寄せる基準）は`venue-agent`のスコープ外のまま。

**このskillは実装フェーズに回すタスクがほぼ無い。** 次にやるべきは「実際にOllamaをpullして、
本物の要項PDFで通しリハーサルする」という運用確認であって、コードの新規実装ではない。

## B. tournament-pdf-to-players（新規実装・LLM不要）

SKILL.mdの「抽出の仕組み」節が既にそのまま仕様書になっている。座標ベース抽出＋辞書照合＋
姓名分割ヒューリスティックで、**判断が要る箇所が無い**ため、Claudeの現在の役割は実質
「スクリプトを書いて実行し、チェックポイントで人に見せる」という進行管理だけ。ここはLLMでなく
ふつうのCLIで代替できる。

### 提案するファイル構成

```
scripts/pdf-to-players/
  extract_tournament.py   # CLI本体（SKILL.md「抽出の仕組み」節をそのまま実装）
  prefectures.py          # 47都道府県の略称→正式名称辞書
  layouts.py              # COL_SPLIT / DOUBLES_SIDES を大会レイアウトごとに定数管理
  test_regression.py      # 既知の実例（3文字姓・ひらがな名・団体戦番号ズレ）を固定化
```

- `--pages` / `--category`（doubles/team自動判定、誤判定時は明示）/ `--out` はSKILL.md通り。
- `COL_SPLIT` と `DOUBLES_SIDES` はハードコードでなく `layouts.py` の辞書＋CLI引数で上書き可能にする。
  SKILL.mdが「別レイアウトでは1ページ目確認で崩れが分かるので、その時に座標を実測して調整する」と
  明言している通り、レイアウトごとに校正し直す運用が前提のため。
- レポート項目（`duplicate_ids` / `missing_ids` / `prefecture_not_in_dict` /
  `entries_missing_2nd_player` / `review_name_split` / `order_mismatch_warnings`）は
  venue-agentの `checks.py` と同じ「決定的チェック＋要確認フラグ」パターンで実装する。
- 人への確認ステップ（1ページ抽出→OK→全ページ→最終レポート）は `venue_agent.py` の
  `confirm()` と同じ `input()` ベースのパターンを流用する。

### OCR経路

`ocrmypdf`（内部tesseract、`-l jpn`）でテキスト層を付与してから同じCLIに通す薄いラッパーを
別途用意する。SKILL.md自身が「v1では設計方針の記載に留めている」としている通り、実データが
出るまで実装を急がない。

### ローカルLLMの出番はあるか

基本的に無い。唯一候補になり得るのは `review_name_split`（3文字姓・ひらがな名など曖昧な
姓名分割）への提案だが、件数が少なく人が見れば済むレベル。**v1はLLM無しで作り、実運用で
人手負担が大きければ追加検討する**（このプロジェクトの「小さく確認して拡張」の流儀に合わせる）。
→ 3skillの中でいちばん「ローカルLLM」を要らなくする設計そのものが答えになる。

## C. tournament-insight（新規実装・既存スクリプトを再利用）

決定的な生成・検証部分（`npm run story:generate` / `npm run story:verify` /
`npm run check:orphans` / `check-tournament-insights.mjs`）はNode.jsスクリプトとして
既に存在し、Claudeが居なくてもそのまま動く。**変更不要。**

新規に作るのは、venue-agentと対になる「insight-agent」。LLMに渡す指示は
`docs/story-yaml/PROMPT.md` のテンプレートをそのまま使う。

### 提案するファイル構成

```
scripts/insight-agent/
  insight_agent.mjs   # CLI本体（既存Node資産と揃えて.mjsにする）
  prompts.mjs          # PROMPT.mdの完了版/進行中版テンプレートを文字列化
  lint.mjs             # 禁止語チェック（下記）— 現状スクリプト化されていない穴
```

流れ:

1. `npm run story:generate -- -t <id> -y <year> --no-records -o /tmp/for-llm.yaml` を内部で呼ぶ
2. YAML丸ごと＋`prompts.mjs` のシステムプロンプトをOllamaに渡す（`format: json` は使わず、
   `## 選定` → `## 投稿N` の出力フォーマットのままテキストで受ける。散文はJSON強制と相性が悪い）
3. **禁止語チェックを新規に追加する**（`lint.mjs`）。「強豪」「名門」「王者」「悲願」「雪辱」
   「復活」「圧巻」「驚異的」「注目の」「実力者」等をPROMPT.mdから正規表現化して機械検出する。
   現状これはPROMPT.mdに文章で書いてあるだけで、照合スクリプトの対象外（`verify-story-text.mjs`は
   事実の数値・固有名詞しか見ない）。**ローカルLLMは指示追従がクラウドより甘くなりがちなので、
   この穴を埋めるのが実装フェーズの優先度トップ**になる。
4. `npm run story:verify -- -t <id> -c <全種目カンマ区切り> draft.md -q` を自動実行し、
   ERROR/WARNをそのまま人に提示する
5. `state` は常に `draft` のまま出力する（既存の `check-tournament-insights.mjs` が
   `draft`/`review` をprebuildでスキップする運用と一致させる。人が `published` に上げるまで
   自動公開しない）

### モデル選定（16GB Mac、qwen2.5系で統一する場合）

venue-dataの「狭い1件構造化」よりも要求が高い（複数ストーリーの取捨選択、経年文脈の統合、
140字の日本語記事として破綻なく構成する）。品質基準は「下書きで十分・人が必ず手直し」と
確認済みなので、以下を第一候補にする。

- **qwen2.5:14b-instruct**（Q4_K_M量子化、実測約9GB）。9Bより構成力・指示追従が上がり、
  16GB機でもOS込みで動く現実的な上限。
- 日本語の自然さを追求するなら `Llama-3.1-Swallow-8B-Instruct` のような日本語継続事前学習
  モデルも比較対象にする価値がある（Qwenより日本語散文が自然になることがある一方、
  事実制約の遵守率はQwenの方が安定する可能性もあり、実装時に両方試して比較する）。
- 32Bクラスは16GB機だとQ4でも他アプリを圧迫するため基本除外。品質が足りない場合のみ検討。

### 既存PROMPT.mdをローカルモデル向けにどう削るか

PROMPT.mdはクラウドLLM想定の長い指示文（絶対の制約・構成・書き方・出力形式）。9B〜14Bは
指示追従が甘くなりやすいため、実装時に次を機械チェック側へ移す設計にする（人力目視に
依存させない）:

- 出力に必ずstory idが併記されているか → 正規表現で `used:` 行の有無をチェック
- `related` で結ばれたストーリーが1本にまとまっているか → 生成YAML側の`related`情報と
  出力の`used:`を突き合わせて分割漏れを検出
- 禁止語 → 上記 `lint.mjs`

優先順位の目安（今回の調査で判明した「現状の空白」の大きさ順）:

実装後は、SKILL.mdに書かれている「実際に踏んだ落とし穴」の実例（就実の集計漏れ、

将来ローカルモデルを差し替えたときに壊れたことへ気づける。

# 2026-08-14 追記: 実データ検証と、それによる設計の修正

上の設計を公開済みインサイト24本（全417主張）に当てて実測したところ、**優先順位を入れ替える
必要のある事実が3つ出た**。以下は推測でなく、すべて `scripts/verify-story-text.mjs` を
実データに対して走らせた結果。

## 1. 「照合を通っている」の中身が想定より薄い

`npm run check:orphans` 相当の prebuild 照合は24本すべて通る（ERROR 0 / WARN 0）。
ただし内訳を型別に数えると、**実データと事実を突き合わせている主張は26.4%しかない**。

| 主張の型 | 件数 | 割合 |
|---|---|---|
| 年が掲載範囲内か（範囲の確認のみ） | 162 | 38.8% |
| 固有名詞が掲載データに存在するか（存在の確認のみ） | 145 | 34.8% |
| 年×成績の照合 | 49 | 11.8% |
| スコアの照合 | 42 | 10.1% |
| 連続年数の照合 | 19 | 4.6% |

上2つは**文の事実が誤っていても通る**（名前が実在すること・年が範囲内であることしか見ていない）。
「417件が照合済み」は「417件の事実が検証済み」ではない。

## 2. 記事の主語＝「今年誰が優勝したか」が1件も照合されていなかった

公開済み24本の**冒頭文が、24本すべてで未照合だった（0/24）**。

原因は語順。抽出パターン (a) は `(\d{4})年` の直後に助詞を挟んで成績語が来る形しか拾わないが、
PROMPT.md の構成指示「**今年何が起きたか**を最初に書く」が生む語順は

> 2025年のインターハイ男子団体は岡崎城西が優勝しました。

で、年と成績のあいだに大会名・種目・主体が挟まって網から漏れる。
**PROMPT.md の指示と照合スクリプトの抽出パターンが噛み合っていない**という、
どちらか片方を読んでいるだけでは見えない種類の穴だった。
SKILL.md の「年を省略したり修飾を挟むと網から漏れる」という注意書きは、
自分自身のプロンプトが生む語順には向けられていなかった。

→ **対処済み**。`verify-story-text.mjs` に抽出パターン (a2) を追加した（年がちょうど1つの
断片に限り「&lt;主体&gt;が優勝／準優勝し」を年に結び付ける）。結果は **0/24 → 23/24**、
公開済み24本の ERROR/WARN は 0 のまま、主張総数は 417 → 440。
残る1本は冒頭が「決勝が尽誠学園同士の対戦になりました」で成績語を含まないため、これは正しい挙動。

## 3. 注入テスト: 機械照合が捕まえる誤りは8種中2種だけ

「ローカル9〜14Bがやりそうな逸脱」を正しい本文に注入して、照合が落とせるかを実測した。

| 注入した誤り | (a2)追加前 | (a2)追加後 |
|---|---|---|
| ① 評価語の混入（強豪・悲願） | 素通り | 素通り → **lint.mjs で検出** |
| ② 年の取り違え（2024→2023） | 素通り | 素通り |
| ③ 連続年数の水増し（3→4年連続） | 検出 | 検出 |
| ④ スコア改竄（2-1→2-0） | 素通り | 素通り |
| ⑤ 実在しない学校名の捏造 | 素通り | 素通り |
| ⑥ 推測の混入（優勝候補・とみられる） | 素通り | 素通り → **lint.mjs で検出** |
| ⑦「初優勝」の偽装 | 素通り | 素通り → lint.mjs が WARN |
| ⑧ 成績ラベルすり替え（優勝→準優勝） | 素通り | **検出**（(a2)の効果） |

素通りの理由もそれぞれ構造的なもので、正規表現を足せば済む話ではない:

- **②**: 1文に複数の主体が出ると「1人でも一致すれば OK」という規則（ダブルスのペアのための
  意図的な設計）が働き、隣の主体が正しければ誤った帰属が通る。
- **④**: スコアは「その数字の試合が登場人物の関わる形で実在するか」しか見ない仕様（コメント記載済み）。
- **⑤**: 主語は既知の名前リストとの一致で拾うため、**存在しない名前はそもそも主張として
  抽出されない**。捏造した固有名詞は警告ゼロで通る。ローカルモデルでは実在する確率が
  クラウドより高い失敗で、ここが現状いちばん危ない。

## 設計の修正: 優先順位を入れ替える

元の優先順位は「1. lint.mjs の禁止語チェックが急務」だった。**これは間違い。**
禁止語（①）は8種の逸脱のうち**唯一、事実の誤りでないもの**＝体裁の問題で、
公開済み24本での出現も0件だった。一方で ②④⑤ は ADR-005/ADR-012 が防ごうとしている
「誤った事実の公開」そのものであり、しかも現状は警告すら出ない。

修正後の優先順位:

1. **照合の網の粗さを埋める**（②⑤が本命）。特に⑤「未知の固有名詞を検出する」は
   `verify-story-text.mjs` に `--report-unknown-names` 相当を足せば実現でき、
   ローカルモデル移行の前提条件に近い。②は「1文に複数主体があるとき、帰属が曖昧なら
   OK でなく WARN に落とす」で緩和できるが、既存の正しい本文が WARN 化しないかの実測が要る。
2. **lint.mjs（実装済み・下記）**
3. pdf-to-players の `extract_tournament.py`（LLM不要・変更なし）
4. venue-data は運用リハーサルのみ（変更なし）

## 実装したもの

### `scripts/verify-story-text.mjs` — 抽出パターン (a2) を追加

上記2の対処。公開済み24本で回帰確認済み（ERROR 0 / WARN 0 を維持、冒頭文 0/24 → 23/24）。

### `scripts/insight-agent/lint.mjs` — 新規

設計どおり新規作成したが、**中身は禁止語チェックだけにしなかった**。検査は4種:

| 検査 | 水準 | 内容 |
|---|---|---|
| 評価語 | ERROR | PROMPT.md の禁止例を核に43語。「強豪」「悲願」「圧巻」「優勝候補」「死闘」等 |
| 推測 | ERROR | 「とみられる」「期待される」「来年」「今後」「悔し」等11パターン。PROMPT.md の「推測を書かない」「これから起こることの予想を書かない」の機械化 |
| used | ERROR | story id の併記が無い本文を弾く（ADR-012 が公開の必須条件にしている） |
| 照合カバレッジ | WARN | **各文を1文ずつ照合器にかけ、「実データと突き合わせた主張が0件の文」を名指しする**。存在確認・範囲確認しか付かない文＝誤っていても通る文が可視化される |

4つ目が実質の主眼。1〜3は既知の制約を機械に移しただけだが、4つ目は
**「この文は機械が守っていない」を書き手に見せる**もので、上の 1. の穴が埋まるまでの
当面の防波堤になる。

## 追加実装（同日）: ⑤未知の固有名詞の検出

### 仕組み

照合器は**既知の名前と一致した語しか主張として抽出しない**ため、捏造された固有名詞は
主張にすらならず警告ゼロで通る。つまり照合器の中を直しても塞がらない。
本文側から「知らない名前が出ていないか」を見るしかない。

1. `verify-story-text.mjs` に `--list-names` を追加（実在する人名・所属・**姓名の断片**をJSONで返す）。
   姓名の断片まで返すのは、本文が「亀安・関口組」のように姓だけで呼ぶため。
   これが無いと正しい表記まで「知らない名前」になる。
2. `lint.mjs` 側で、本文から既知の固有名詞を最長一致で伏せ、ひらがな・数字・記号を落とし、
   残った漢字・カタカナのうち定型語彙表に無い文字を報告する。

持っておけば、そこに無い文字＝固有名詞の可能性が高い、と言える。

1. **左右の境目も列も「行ごとの投票」で決めるように変えた。** 文字の占有幅を union する
   従来の方法は、**見出しの1行がページを横断しているだけで列が全部融合する**。
   全中の団体戦ページは見出しが本文と同じ字の大きさで、フォントサイズによる除外も効かなかった。
   行単位で数えれば見出しは1票にしかならない。
2. **「ほぼ全部の行が空けている帯のうち、いちばん幅の広い帯」を左右の境目にした。**
   完全に空いている帯だけを見ると、氏名の文字と文字の間の14ptを境目に選び、
   右段の氏名を途中で切っていた。
3. **姓と名の境目は「右端の列だけが明らかに広い」ことで決める。** 姓は1文字ずつの狭い
   スロット（7〜16pt）、名はまとめて広い枠（30pt前後）。決め手が無い側は反対側の境目を
   鏡像で写す（ブラケット表は左右対称）。
4. **所属と都道府県が交互に入る列**を専用ラベルにし、行ごとに中身で振り分けてペア内で共有。
   ブロック付き表記（`近畿・滋賀県`）は後ろの県名だけを取る。
5. **ページごとに独立して処理するようにした。** 全ページの列をまとめて意味づけすると、
   あるページの座標が別のページの判定を狂わせる（1ページ目だけ通したときと
   1-2ページを通したときで結果が変わる、という形で表面化した）。

結果、**個人戦4ページとも32エントリーを正しく抽出**した（先頭・32番目の姓名、所属、
都道府県まで確認済み）。下部の再掲枠は `duplicate_players` として報告される。
PDFをfixtureとしてリポジトリに置き、回帰テストに組み込んだ（**32/32 → 64/64 pass**）。

### さらに追記: 団体戦ページも通した（同日）

p5-6 も通るようにした。**25チームずつ clean で抽出**（レポートに要確認項目ゼロ）。
回帰テストは **64/64 → 78/78 pass**。

詰まっていた原因は、想定と違って左右の境目ではなく**見出しの判定**だった。

- `body_chars` は「最頻フォントサイズの1.5倍より大きい字＝見出し」としていた。
  女子団体戦ページは**チーム名12.7pt・都道府県8.2pt**で、最頻は都道府県の8.2pt。
  1.5倍＝12.3pt を超えるチーム名が**丸ごと見出し扱いで消えていた**（所属が全部空になる）。
- 直し方: 見出しは「大きい」だけでなく「**全体のごく一部**」でもある。
  最頻の1.3倍より大きく、かつ文字数が全体の1割未満のサイズ階級だけを落とすようにした。
  女子団体戦なら16.4pt（22文字・5%）は落ちて、12.7pt（162文字・37%）は残る。

他に2つ直した:

- **団体戦は2行で1エントリー**（1行目にチーム名、2行目に都道府県）。1行1エントリーと
  みなすと件数が倍になり県が全部欠ける。個人戦のペアと同じ要領で束ねるようにした。
- **表の本体の外にある行**（見出しと、下部の「優勝」再掲枠）を、
  **エントリー番号の並びの範囲**で判定して落とすようにした。落とした行は必ず表示する。
  個人戦の再掲枠は番号が付いているので本体として拾われ、`duplicate_players` で報告される
  （番号の有無で自然に扱いが分かれた）。

なお、長いチーム名の1文字目が落ちる問題（`北広島大曲中学校` → `広島大曲中学校`）は、
列の検出しきい値を 8% → 4% に下げて解決した。列の範囲を「割り当たった文字まで広げる」
という直し方も試したが、**隣の列を飲み込んで別ページが壊れた**ので採らなかった。

**この検証で、ローカルLLMを使わない判断がさらに強まった。** 引っかかった5点はどれも
「LLMに列の意味を聞けば解決する」種類ではなく、**幾何の取り方そのものの問題**だった。
LLMに列サンプルを見せても、見出しで融合した列は融合したままである。

## 方針の修正: 「未知の様式への融通」と「自力で直せること」（同日・ユーザーの指摘を受けて）

ここまでの実装は**あなたが心配していることを増やす方向**だった、という指摘を受けた。

指摘は2点:

1. **未知のレイアウトに当たったときの融通は期待したい**
2. 気にしているのは**実施手順と、何か困ったときに自力で直せるかどうか**

それまでの作りは「崩れたら `--gap` / `--y-tol` を人が振る」前提で、
実際こちらも全中のPDFで何度も手で振っていた。これは
**運用する人に幾何の理解を要求する**設計であり、Claude不在で回すという目的に反する。

### 直したこと1: パラメータの自動調整（`tuning.py`）

何通りか抽出して**結果を採点し、いちばん良かったものを採る**ようにした。
採点にLLMは要らない。この領域には「正解らしさ」を機械が測れる手掛かりがあるため:

- 都道府県の欄が47都道府県辞書に当たるか（列が1つずれると当たらなくなる）
- エントリー番号が連番として素直か
- 所属が空でないか
- ダブルスなら、ペアが2名そろっていて姓と名の両方が入っているか

**列がずれた抽出はこれらがまとめて崩れる**ので、点数が素直に効く。

実測:

| 対象 | 結果 |
|---|---|
| 2段組の一覧・全中の個人戦4ページ・団体戦2ページ | いずれも**1通り目（既定値）で点数1.00**。総当たりに入らず即決 |
| ドロー表でない書類（STリーグの結果表） | 15通り試して最高0.71。診断「所属がほとんど空です」を出力 |

これで、未知の様式に当たったときの手順が
**「座標を実測して調整する」から「もう一度実行する」**に変わった。

### 直したこと2: LLMを本当の切り札にした

それまでの `--llm` は「確信度の低い列だけ上書き」で、盤面が崩れているときには効かなかった。
**点数が目安(0.75)を下回ったときだけ、列の判定を丸ごとLLMに聞く**ようにし、
改善したときだけ採用する（採否は必ず表示）。Ollamaが無ければ黙って規則の結果で続ける。
既定でオンにし、止めたいときだけ `--no-llm`。

ここで、追記3に書いた「LLMは要らない」という結論を一部修正する。
**検証済みの様式では要らない。未知の様式に対する保険としては要る。**
違いは、LLMを常時使うか、規則が失敗したときだけ使うか。

### 直したこと3: 実施手順書（`RUNBOOK.md`）

座標やコードの話を一切出さずに作業が回ることを目指した文書を追加した。
READMEは仕組みの説明として残し、冒頭で RUNBOOK へ誘導する。

盛り込んだのは、点数の読み方（3段階だけ）、出力3ブロックの見方、

そして**「どうしても通らないときは無理に自動化しない」**という一節。
この作業の目的は間違ったデータを入れないことであって、全部を機械で取ることではないため。

回帰テストの位置づけも書いた。実PDF3種類で件数と中身を固定してあるので、
**直したつもりが別を壊したときに気づける**——これが「自力で直せる」の土台になる。

## 方針の再修正: 語彙を足して対応しない（同日・2023年のPDFでの失敗を受けて）

2023年の全中ドロー表で点数0.56となり、所属の列を氏名の列と取り違えた。
原因は**学校名の略称**——2024年版は `朝桜中学校` だが2023年版は `西郷第一中` `南中` で、
`_TEAM_HINT` の語彙（`中学` 等）に当たらず「所属らしさ」が測れなかった。

最初の対応は語彙に `.中$|.高$|.小$` を足すことだったが、
**「アドホックな固定対応はしないでほしい」と指摘を受けて撤回した。** 指摘は正しい。
次のPDFが `〇〇クラブJr` と書けば、また語を足すことになる。

### 撤回して分かったこと: 構造的な手掛かりだけで足りた

「所属と都道府県が交互に入る列」の判定は、**所属側の語彙を知らなくてもできる**。
都道府県が半分程度しか当たらないこと自体が手掛かりになるため
（都道府県だけの列なら1.0近くまで当たる）。条件を
`pref_ratio > 0.25 かつ (team_ratio > 0.25 または pref_ratio < 0.7)` にしたところ、
語彙の追加を外しても2023年版が通った。架空の書き方（`西郷Jr` / `ABC ソフテニ` / `みなみ`）でも通る。

**決定的な層は構造的・統計的な手掛かりだけで判断し、語彙表に頼る判断はLLMへ回す**、
という線引きを明文化した。47都道府県の辞書は語彙表ではなく閉じた実在の集合なので例外。

### LLMを「提案する側」にした（修復ループ）

もう一点の要望「うまくいかなかったらローカルLLMが調整してくれるように」に対応した。
それまでのLLM呼び出しは一発勝負で、外れたらそれきりだった。

`tuning.repair()` を追加し、次の形にした:

1. LLMが全列のラベルを提案する
2. **機械が採点する**（`score_entries`）
3. 目安に届かなければ、**採点の内訳をフィードバックしてもう一度提案させる**
   （「都道府県として読める値が取れていません。都道府県を含む列に prefecture を付けてください」）
4. 既定3回まで（`--llm-rounds`）

**採否を決めるのは常に機械で、LLMの自己申告は使わない。** 改善しなければ規則の結果を使う。
ADR-012の「LLMが書き、機械が検証する」と同じ形をパラメータ調整に持ち込んだことになる。

一発で当てさせず内訳を見せて直させるのは、9〜14Bクラスに対しては
そのほうが当たるという見立てによる（実モデルでの検証は未了）。

### Ollama無しでも検証できるようにした

`repair()` の「提案する側」は差し替え可能にしてある。回帰テストでは提案を差し替えて、
**モデルの賢さではなく採否の仕組みが正しいか**を固定した:

- 壊した状態（点数0.00）に正しい提案を与えると採用され1.00になる
- 目安に届いたらそれ以上聞かない（1回で止まる）
- 出鱈目な提案は採らず、上限3回まで聞き直す
- 2回目以降のプロンプトに採点の内訳が入っている
- 接続できなければ規則の結果を返す

回帰テストは **81/81 → 88/88 pass**。2024年版6ページと一覧型PDFの点数は1.00のまま。

### 未検証

**実際のOllamaでこのループを回していない。** 提案の質（9Bがフィードバックを読んで
直せるか）は実機で確かめる必要がある。仕組みが正しいことだけを固定した状態。

### 詰まっていたのは、知能を要する判断ではなく普通のバグ2つだった

| 症状 | 原因 | 性質 |
|---|---|---|
| 2人の氏名が1文字ずつ交互に混ざる（`松猪坂股健拓人海`） | 行のまとまりを**直前の文字**とだけ比べていたため、少しずつずれた文字が数珠つなぎになり10pt以上離れた行が融合していた | 一般的なバグ。まとまりの**先頭**と比べる形に直して解決 |
| ペアが全部1人ずつに割れる | エントリー番号を見た瞬間に新しいエントリーを始めていた。番号がペアの**2行目**に来る様式で全滅する | 一般的なバグ。番号は「識別子」であって「区切り」ではない、と直して解決 |

  退化した解釈が1.00を取っていた。エントリー番号の列を失っていること自体を減点して緩和。
