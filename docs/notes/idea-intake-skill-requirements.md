# アイデア受付・要求整理 skill 要件定義

> 本書は skill 実装のための要件をまとめたもの。実装（SKILL.md の作成）は適用先プロジェクトの環境で行う。
> 適用先固有の情報（リポジトリ構成、既存 Wiki の場所、チーム体制）は「11. 適用時に埋める項目」を参照。

---

## 1. 背景と目的

### 背景

非エンジニアがプロダクトへの要望・アイデアを持ったとき、現状はエンジニアに直接口頭で相談する形になっている。この結果：

- **エンジニア側** — 「これって実現できますか？」という曖昧な質問で頻繁に割り込まれる。文脈スイッチのコストが高く、質問の多くは「それは既にできる」「前に検討して見送った」で終わる
- **非エンジニア側** — 相談すること自体に心理的コストがある。断られると次から言い出しにくい
- **組織** — 口頭でやりとりされた要望と判断理由が残らない。同じ議論が繰り返される

### 目的

非エンジニアとエンジニアの間に **緩衝材** を置く。両者は直接会話せず、skill とリポジトリ内の markdown を介する。

1. 非エンジニアが気兼ねなくアイデアを投げ込める場を作る
2. その場で片付くもの（既存機能で解決／過去に判断済み）を skill が処理し、エンジニアへの到達を防ぐ
3. エンジニアに回るものは、下調べ済み・判断ポイントが絞られた状態にする
4. すべての要望と判断理由をリポジトリに蓄積し、後から束ねて価値を高める

### 設計思想

本 skill の本当の資産は **蓄積される知識** であって、分析パイプラインそのものではない。
10 回目の相談が 1 回目より速く鋭くなることを目指す。

## 2. 対象ユーザー

### 主たる利用者：プロダクトに精通した非エンジニア

PdM、CS リード、事業側の担当者など。**エンドユーザーの生の要望をそのまま扱うことは想定しない。**

この前提から導かれる設計上の含意：

| 特性 | 設計への反映 |
|---|---|
| プロダクトの用語・機能は理解している | 過度に噛み砕かない。対等なトーンで話す |
| 「使い方を知らない」ケースは少ない | 仕分けの重みを「既に検討済み」「別の手段で解ける」側に置く |
| 解決策の形で持ってくるが、筋は通っている | 目的への巻き戻しは行うが、否定ではなく「確認」のトーンで |
| 複数のユーザーの声を既に束ねている場合がある | 「実際に聞いた声」か「本人の推測」かは区別して記録する |
| 実現可能性への関心が高い | 下調べ結果はある程度詳しく返してよい |

### 二次的な利用者：エンジニア

投稿には関与しない。棚卸しの結果と、昇格して回ってきた案件だけを見る。

---

## 3. スコープ

### やること

- アイデア・要望の受付
- 既存機能・過去の判断との照合
- 「それは本当に要求か」の仕分け（1 ラウンドの深掘り）
- 既存コードを踏まえた実現可能性・運用コストの下調べ
- リポジトリ内 markdown への記録
- 蓄積されたアイデアの棚卸しと昇格判断の支援

### やらないこと

- **実現可能性の断定** — skill は「できます／できません」と言い切らない（詳細は 6.3）
- 工数の絶対値見積もり
- 実装の可否決定そのもの（最終判断はエンジニア／意思決定者）
- 実装作業

## 4. 全体フロー

```
投稿（形式自由）
  ↓
【工程0】照合（自動・質問なし）
  ├→ 既存機能で解決する      → 回答して終了
  ├→ 過去に判断済み          → 理由を提示、状況変化を確認
  └→ 該当なし                → 次へ
  ↓
【工程1】深掘り（質問3問まで・1ラウンドのみ）
  ├→ 不具合                  → バグとして別ルートへ
  ├→ 運用・別手段で解ける    → 提案して終了
  ├→ 目的が曖昧              → 保留として記録
  └→ 真の要求                → 次へ
  ↓
【工程2】下調べ（自動・質問なし）
  実現可能性 / 運用コスト / 確度ラベル付与
  ↓
【工程3】記録（目的で索引）
  ↓
【工程4】棚卸し・昇格（別タイミング・手動起動）
  ↓
エンジニアへ
```

**重要な設計上の分離** — ユーザーに質問する工程（1）と、skill が自律的に調べる工程（0, 2）を分ける。
体感の重さを決めるのは前者だけなので、後者はいくら厚くしても投稿体験を損なわない。

---

## 5. 工程0：照合（自動）

### 位置づけ

**照合をフローの先頭に置く。** 一般的な要求分析の順序（要求分析 → 既存システム分析）とは逆だが、以下の理由による：

- ユーザーへの追加質問が不要（一行のアイデアでも類似検索には十分）
- その場で会話を完結させられる唯一の工程
- 実運用ではここで終わる相談が最も多いと想定される

「聞いてすぐ答えが返る」体験を最初に作れるかどうかが、この仕組みが使われ続けるかを左右する。

### 照合先と応答

| 照合先 | 判定 | 応答 |
|---|---|---|
| 既存コード・機能 | 既に実現できる | 使い方を返して終了。あわせて「発見性の課題」として1行記録 |
| 蓄積された過去の判断 | 過去に検討し見送った | 判断理由を提示し、状況が変わったかだけ確認 |
| 設計思想・ADR | 方針と衝突する | 早期に伝える。ただし却下ではなく「方針変更の提案」として扱う |
| 既知の制約・失敗事例 | 抵触する | 制約を説明し、代替案を提示 |
| — | 該当なし | 工程1へ |

### 出力の書き戻し

照合の過程で新たに判明したこと（既存機能の発見しにくさ、ドキュメントの不足など）は記録する。
同種の記録が一定数たまったら、それ自体が別の課題として浮上する。

## 6. 工程1：深掘り（1ラウンド）

### 目的

**「これは要求か」の仕分け。** 良し悪しの評価ではない。

要求工学的に「要求ではない」ものが混ざったまま下流に流れると、実現可能性や価値の議論が空回りする。ここで一度だけ掘る。

### 仕分けのパターンと行き先

| パターン | 行き先 |
|---|---|
| 真の要求 | 工程2（下調べ）へ |
| 実は不具合 | バグとして即エンジニアへ（別ルート。むしろ歓迎される） |
| 運用ルール・既存の別手段で解ける | 手順を提案して終了 |
| 解決策が要求の顔をしている（XY 問題） | 目的に巻き戻し、より小さい／適切な要求として再定義 |
| 特定個人の好み（他に困っている人がいない） | 保留として記録 |
| 目的が定まっていない | 保留として記録。「また困ったら教えて」 |

**原則：「それは要求ではありません」とは言わない。すべてどこかに着地させる。**
仕分け結果は失格判定ではなく行き先の振り分けとして扱う。

### 質問

**3問まで。一度に1問ずつ。**

核となるのは **「直近でそれが必要になった具体的な場面を1つ」**。抽象的な要望が具体的なエピソードに落ちた瞬間、正体がほぼ割れる。

補助的な問い（必要に応じて選ぶ）：

- 今はどうやって凌いでいるか（回避策の有無 → 重要度と、既に解決している可能性が分かる）
- 他に同じことで困っている人はいるか / それは実際に聞いた声か、推測か
- これが無いまま放置すると、いつ・何が困るか（緊急度の確認）

### 深掘りを省略してよい場合

- 工程0 で完結した場合
- 投稿時点で目的・場面・影響範囲が既に明示されている場合（精通した利用者では十分ありうる）

**深掘りは工程4（昇格）の前処理でもある。** 目的が抽出されていないと、後述する「目的の合流」による昇格が機能しない。

## 7. 工程2：下調べ（自動）

### 原則：断定せず、根拠と確度をセットで返す

skill が「できます」と言って実際にできなかった場合、非エンジニアとエンジニア双方の信頼が一度に失われる。この仕組みにとって致命的なので、**可否の断定は行わない。**

代わりに、エンジニアが **ゼロから調べる** のではなく **検証する** 側に回れる状態を作る。負担の質が変わり、間違っていても責任範囲が明確なので摩擦にならない。

### 確度ラベル（必須）

すべての記述に付与する。

| ラベル | 意味 |
|---|---|
| 🔍 確認済み | 実際にコード・ドキュメントを読んで確認した |
| 💭 推測 | 類似事例からの推定 |
| ❓ 要エンジニア判断 | skill では判断できない |

### 実現可能性の調査項目

- 触ることになりそうなモジュール・ファイル
- 似た実装が既に存在するか（存在すれば工数が下がる根拠になる）
- 衝突しそうな制約・設計判断（ADR 等）
- 外部依存の増減

**規模の表現は相対比較とする。絶対工数（「3日」等）は出さない。**
理由：当たらないうえ、外れたときに信頼を損なう。「以前実装した ○○ 機能と同程度」という形なら、過去の実績が根拠になり、外れても致命的でない。

### 運用コストのチェックリスト

定量化せず、該当すれば旗を立てるだけでよい。これだけでエンジニアの判断材料になる。

- [ ] 新しいデータを永続的に保存するか
- [ ] 定期的な手作業が発生するか
- [ ] 問い合わせ・サポート対応が増えそうか
- [ ] 外部サービスへの依存が増えるか
- [ ] 誰かが内容を継続的に更新する必要があるか
- [ ] 障害時の影響範囲が広がるか

### 非機能要求の確認

非エンジニアが自発的に言及しない領域であり、後から発覚して手戻りになる原因の筆頭。
下調べの中で該当しそうなものだけ確認する（全項目を毎回聞かない）。

- 個人情報・機微情報を扱うか
- データ量が大きく増えても成立するか
- 誰が見られるべきで、誰が見るべきでないか
- 法令・社内規程に関わるか

## 8. 工程3：記録

### 保存先

適用先リポジトリ内の markdown。Git 履歴に残ることで、いつ誰が何を言い、どう判断したかが追跡可能になる。

```
docs/ideas/
  index.md                        ← 目的別の索引
  YYYY-MM-DD-<slug>.md            ← 個別のアイデア
```

### ファイル形式

```markdown
---
status: backlog            # inbox / backlog / promoted / done / parked
purpose: <目的。解決策ではなく>
requested_by: <要望者>
requested_count: 1         # 同趣旨の要望が来た回数
source: heard | assumed    # 実際に聞いた声か、本人の推測か
promote_when: <再検討・昇格の条件>
related: [<関連ファイル>]
---

## 困りごと（本人の言葉のまま）

## 要求

## 受け入れ基準
（どうなったら満たされたと言えるか。事後評価の基準になる）

## 下調べ
- 🔍 <確認済みの事実>
- 💭 <推測>
- ❓ <要エンジニア判断>

## 運用コスト
<チェックリストの該当項目>

## 未確定事項
```

### 索引の原則

**解決策ではなく目的で索引する。** 解決策で並べると、後述する「目的の合流」による昇格が発見できない。

### 受け入れ基準を必ず書く

「どうなったら成功と言えるか」を記録時点で言語化する。これが無いと事後評価（将来拡張の Learning）が機能しない。
書けない場合、それ自体が「目的がまだ曖昧」という診断になる。

## 9. 工程4：棚卸しと昇格

### 起動方法

手動起動を基本とする（棚卸し専用の skill を別途用意する形も可）。
加えて、新規投稿のたびに既存バックログとの重複・目的の重なりを自動でチェックする。

### 昇格の4類型

| 型 | 内容 |
|---|---|
| **再燃** | 別の人・別の機会に同趣旨の要望が繰り返し来た。回数がそのまま需要の証拠になる |
| **目的の合流** | 見た目は別々のアイデアが、掘ると同じ目的を指している。束ねると1つの本質的な課題になる |
| **土台の共有** | 別機能だが同じ基盤を必要とする。基盤を1回作れば複数が一度に解決し、一件あたりのコストが下がる |
| **条件成立** | 「○○ になったら再検討」と設定した前提条件が満たされた |

**「土台の共有」が最も価値が高い。** 単独では見送られる小さい要望が複数集まることで、基盤への投資判断に化ける。個別対応の繰り返しを構造的に回避できる。

### 昇格トリガー（個別案件をエンジニアに回す基準）

**規模ではなく、不可逆性と波及で判定する。**
「高いが取り消せる変更」より「安いが取り消せない変更」のほうが慎重な検討を要する。

**エンジニアに回す：**

- 新しいデータを永続的に保存する
- 既存の挙動を変える／既存ユーザーに影響する
- 一度出すと引っ込められない（ユーザーが依存する、外部に公開される）
- 設計思想・ADR と衝突する
- 外部サービス依存が増える
- 継続的な手作業運用が発生する
- 要望者が誰か曖昧、または伝聞のみ

**回さない（記録のみ、または即実施）：**

- 表示・文言・配置の変更
- 影響範囲が閉じている
- 後から取り消せる
- 上記トリガーに該当しない

見積もり時間は単独では昇格理由にしない。

### エンジニアへ渡すパッケージ

エンジニアが **5分で判断できる形** に絞る。曖昧な質問のための文脈スイッチこそが最大の負担なので、ここの整形が効く。

```
やりたいこと: （目的。解決策ではなく）
今の困りごと: （本人の言葉のまま）
似ている既存機能: （skill が調査済み）
関係しそうな場所: （推測。断定しない）
運用コスト: （チェックリスト該当分）
聞きたいこと: （1つだけ）
```

### 棚卸しレポートの構成

- 回す案件（判断してほしい点を明示）
- 積んだまま
- 昇格候補（4類型のいずれかに該当したもの、根拠つき）
- 条件成立したもの

## 10. 対話設計の原則

### 気軽さを守るための規則

**深さは選ばせず、昇格させる。** 冒頭で「簡易分析とフル分析どちらにしますか」と聞いた時点で失敗。利用者に適切な深さは判断できないし、選択を迫ること自体が心理的コストになる。常に最速レーンから始め、必要な場合のみ skill 側の判定で深める。

### 工程ごとの予算

skill 内に数値で明記しないと、必ず出力が過剰になる。

| レーン | 追加質問 | 出力量 |
|---|---|---|
| 照合のみで完結 | 0〜1問 | 5行以内 |
| 深掘りあり | 3問まで（1問ずつ） | 15行以内 |
| 下調べまで実施 | 追加なし | 項目ごとに簡潔に |

### 出力形式は深さによらず一定

```
【結論】 進める / 条件つきで小さく進める / 今は記録のみ
【理由】 1〜2行
【次の一手】 具体的な行動
（詳細は求められたら）
```

分析の途中経過を先に出さない。利用者が求めているのは結論であって思考の実況ではない。

### 却下体験の設計

**トリガー設計と同等に重要。** 一度「それは却下です」と言われると、人は二度と相談しなくなる。分析の正しさよりも相談の継続性のほうが長期的な価値が高い。

- **「却下」という状態を持たない。** あるのは「今はやらない ＋ 再検討条件」のみ
- **必ず何かを持ち帰らせる。** 代替案、当面の回避策、または再検討の時期。手ぶらで返さない
- **要求に含まれる有効な観察を切り出して肯定する。** 解決策は採らなくても、そこにある問題認識はたいてい正しい
- **コスト提示を拒否の道具にしない。** 「高いから無理」ではなく「この規模だがどうか、小さい代替はこれ」という選択肢の提示として使う

### 開発コストによる希望度の確認

要望の強さを測るには、コストを提示してから聞き直すのが有効。無料だと人は何でも欲しがる。

- **段階的な選択肢を並べる** — 「フル版 / 簡易版 / 運用で凌ぐ」。簡易版で満足するなら、元々そこまで強い要求ではなかったと分かる。同時に「何を削ると困るか＝コア」が判明する
- **他の要求と競わせる** — 単独で聞くと全部「欲しい」になる。「これを進めると、先に言っていた別件は後回しになる」という形で並べる
- **運用コストも値札に含める** — 「作った後、毎月これだけの手間が続く」
- **放置した場合のコストを聞く** — 答えられない要求は、まだ機が熟していないことが多い

### アンチパターン（skill に禁止事項として明記する）

- 開口一番「目的は何ですか」と聞く（解決策の形で来るのが正常。こちらが巻き戻す）
- 一度に複数の質問を並べる
- 技術的制約をそのまま説明する（「何ならできるか」に翻訳する）
- 全工程を必ず通す
- 分析の途中経過を出力する
- 実現可能性を断定する
- 過度に噛み砕く（対象はプロダクトに精通した利用者）

## 11. 要求工学からの取り込み

本 skill は要求工学（requirements engineering）をベースにしているが、実運用の軽さを優先して取捨選択している。

### 採用したもの

| 要素 | 反映先 |
|---|---|
| 要求と解決策の分離（XY 問題対策） | 工程1 の仕分け |
| ゴール指向要求分析の考え方 | 目的での索引、目的の合流による昇格 |
| 非機能要求の引き出し | 工程2 のチェック項目 |
| 検証可能性（受け入れ基準） | 記録フォーマットの必須項目 |
| ステークホルダーの確認 | 「誰の要求か」「実際の声か推測か」 |
| トレーサビリティ | Git 履歴＋ related フィールド |
| 要求の重複・衝突検出 | 工程0 の照合、新規投稿時の類似チェック |

### 意図的に見送ったもの

| 要素 | 理由 |
|---|---|
| 形式的な要求仕様書の作成 | 重すぎる。気軽さを損なう |
| 詳細なユースケース記述 | 同上。必要なら昇格後にエンジニアが行う |
| 定量的な価値評価・スコアリング | 精度が出ないわりに手間がかかる。相対比較と昇格類型で代替 |
| 曖昧語の機械的検出 | 対象が精通した利用者のため優先度低。将来検討 |

外部の既存手法（Shape Up の Pitch、Oxide の RFD 状態設計など）からの取り込み候補は、
現時点では未採用とし「15. 検討観点」に整理してある。

## 13. 将来拡張

現時点では実装しないが、蓄積が進んだ後に価値が出るもの。

- **判断基準の逆算** — 見送り理由が一定数たまったら要約し、無意識に守っている判断原則を言語化する。次回以降の判断が高速化し、知識ベースの中核ページになる
- **予測と実績のキャリブレーション** — 「同程度と見積もったが実際は大きかった」「価値が高いと判断したが使われていない」を蓄積し、見積もりと価値判断の癖を可視化する
- **条件成立の自動検知** — `promote_when` を観測可能な形で書き、条件成立時に自動で浮上させる。保留が死蔵にならない
- **説明資料の生成** — 「なぜ今は作らないか」を要望者や上位者に説明する文書を、記録から生成する
- **アイデアのクラスタリング** — 個別には小さい要望群から、未解決の大きなテーマを発見する

## 15. 検討観点（現時点では未採用）

既存手法を調査した結果、取り込む価値がありそうな要素を記録しておく。
**ただし、いずれも導入すると記録項目や状態が増え、「気軽に投げられる」という最重要要件を損なうリスクがある。**
まず本書の内容で運用を始め、実際に不足を感じた時点で個別に判断する。

### 15.1 Shape Up の Pitch 構成（Basecamp）

「形を整えた案を意思決定の場に出す文書」の型。5つの構成要素からなる。

| 要素 | 内容 |
|---|---|
| Problem | 現状ではうまくいかないことを示す**単一の具体的なストーリー**。これを baseline と呼び、解の適合性を測る物差しにする |
| Appetite | 見積もりではなく「**どれだけ時間を使いたいか**」。問題定義の一部として先に宣言し、制約として扱う |
| Solution | 粗くてよいが解の骨格。**問題だけで解が無いものは渡せない**（探索を間違ったレベルに押し付けることになる）。ただしワイヤーフレームは作らない |
| Rabbit holes | 深掘りすると危ない箇所を先に潰す。数行で足りることが多い |
| No-gos | Appetite に収めるために**意図的に除外するもの** |

Pitch は非同期が既定で、事前のコメントは**可否判断ではなく「穴を突く・欠けた情報を足す」ため**に行われる。

**採用を検討する価値がある点**

- **単一の具体的ストーリー＝baseline** — 深掘りで聞く「直近で困った場面」をそのまま事後評価の物差しにできる。受け入れ基準を別途書かせるより自然で、非エンジニアにも書ける
- **Appetite** — 希望度確認の最短経路。skill が工数を推定する必要が減るため「断定しない」方針と相性が良い。ただし非エンジニアが時間を数字で宣言するのは難しいので、既に設計済みの「フル版／簡易版／運用で凌ぐ」の3択が、Appetite を答えられる形に変換したものと位置づけられる
- **Rabbit holes / No-gos** — 下調べの出力先として適している。コードを読んで見つけた「ハマりそうな箇所」はまさに rabbit hole
- **解が無いものは渡せないという警告** — 目的抽出だけでエンジニアに回すと不十分になる可能性がある。粗い解の候補を2〜3案出して要望者に選ばせる形が現実的か

**懸念**

- 記録項目が5つ増える。投稿の心理的コストが上がる
- Solution を skill が独断で決めてよいかは要検討
- Shape Up は「バックログを持たない、採用されなかった Pitch は捨てる」という立場であり、本書の「積んで束ねる」設計とは思想が逆。文書の書き方だけを借り、思想は借りない

### 15.2 Oxide RFD の状態設計

IETF の RFC 3 の精神（「磨かれているより時宜を得ていること。最小の長さは1文」）を引き継いだ、社内文書の状態モデル。

| 状態 | 意味 |
|---|---|
| prediscussion | 議論には耐えないが場所取りとして存在。高速に反復中 |
| ideation | **トピックの記述だけ。能動的に更新される期待が無い。誰でも拾って進めてよい** |
| discussion | 活発に議論中 |
| published | 合意・方向性になった。以後も更新可 |
| committed | 実装完了。「将来こうしたい」ではなく「**実際にどう動くかの説明**」に変わった |
| abandoned | 実現不可能と判明、または無視すべきもの。**削除はしない** |

その他の仕組み：中身が空でも早期に番号を予約する／メタデータは4つだけ／**labels に正準セットを定義**して自由記述にしない／状態を機械可読な形で出力する／プロセス自体を同じ仕組みで管理する。

**採用を検討する価値がある点**

- **ideation 状態** — 「トピックだけ／更新の期待なし／誰でも拾ってよい」はアイデアバックログの正しい状態表現。特に**所有権を開放している**点が重要で、「投げた人が育てなければならない」という暗黙の負担が消える。気軽さの要件と直結する
- **committed の存在** — 実装後、記録が「案」から「現状の仕様説明」に変わる。アイデア記録がプロダクト知識に昇華する導線が状態遷移として組み込まれており、知識ベースへの書き戻しと噛み合う
- **abandoned を削除しない** — 「却下という状態を持たない」方針の裏付け。呼称は `parked` 等に置き換えてよい
- **正準ラベル＋自由記述の purpose の二段構え** — purpose の自由記述だけでは表記が揺れて束ねられない可能性がある
- **早期の番号予約** — 会話中に「あの件」と指せるようになり、related フィールドの参照キーが安定する

**懸念**

- 状態が6つは多い。運用者が使い分けられないと形骸化する
- RFD は書き手がエンジニア前提（AsciiDoc、branch、PR）。借りるなら**状態モデルだけで、操作は skill が代行する**形にする必要がある

**もし採用する場合の状態モデル案**

| 状態 | 意味 |
|---|---|
| `ideation` | 受け付けただけ。整理されていない。誰でも拾ってよい |
| `shaping` | 深掘り・下調べ中 |
| `ready` | 整った。エンジニアの判断待ち |
| `promoted` | エンジニアに回した／着手が決まった |
| `committed` | 実装完了。以後は現状仕様の説明として読む |
| `parked` | 今はやらない ＋ 再検討条件つき |

### 15.3 その他の参考

- **PR-FAQ / Working Backwards（Amazon）** — 作る前に完成時のプレスリリースと想定 FAQ を書く。FAQ 部分が非機能要求や運用上の懸念を先出しさせる
- **Type 1 / Type 2 決定（Bezos）** — 「不可逆性で判定する」昇格トリガーの典拠
- **ADR** — 既に導入していれば、アイデア記録とフォーマットを揃え相互リンクする価値がある
- **Buy a Feature（Luke Hohmann）** — 予算を渡して機能を「買わせる」手法。「他の要求と競わせる」の元ネタ
- **Kano モデル** — 「無いと困る／あると嬉しい／あると驚く」の区別。深掘りの補助質問に使える
- **ITIL のインシデント／サービス要求の分離** — 「実は不具合」を別ルートに流す設計の一般形
