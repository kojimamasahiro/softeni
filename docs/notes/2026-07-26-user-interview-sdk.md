# メモ: ユーザーインタビュー自動化SDK（Android）

> このメモは softeni-pick 本体とは別製品の検討。意図的に `docs/wiki/idea-backlog.md` の索引には
> 載せていない（索引の責務はsofteni-pickのプロダクト領域に限るため）。単独で読める1枚として管理する。

## 状況

発散フェーズ（2026-07-26 起票）。主軸は仮決めで **(b) ペイン発見基盤**。

## 目的

**「何を解決すべきか」の発見をAIに代替させる。**

前提となる世界観: 解決方法はAIが大きく代替するようになる。一方で「何を解決しないといけないか」は
まだ人間が決めている。ここが次のボトルネックになるので、ペインの発見自体を自動化したい。
ユーザーインタビューの自動化は、その第一歩として選んだ具体的なアプローチ。

## ユーザーが興味を持った点（原文）

> 本当にやりたいことは、ユーザーインタビューの自動化である。
> loggerで一定の異常を見つけたらそのユーザーにユーザーインタビューをSDKからしたい。

> これからはペインが重要となってきて解決方法などはAIが多くを代替してくれる。一方で何を解決しないと
> いけないかは人間が決める必要がある。そんな時に必要なのはペインを発見すること。そのペインをAIが
> 発見できるようになればいいと思っている。

## 想定するかたち

Androidアプリに組み込むlogger型SDK。

1. アプリ側は普通にイベントを流す（logger as the integration surface）
2. SDKが端末内で「異常」を検知する（同一操作の3回失敗、rage tap、dead tap、画面ループ、
   CTA前の長い逡巡 など）
3. 検知したユーザーに、その場で対話を開始する
4. 対話の結果を **構造化されたペインデータ** として吐き出す ← これが製品の本体

主軸を (b) に置いたので、成果物は「ユーザーが成功したか」ではなく **ペインのデータセット**。
KPIは回答率と、発見されたペインの新規性・粒度になる。
「お困りですか？」と助ける機能 (a) は、(b) を成立させるための対価／入場券として位置づける。

## わかっていること

### 検知はAI不要

トリガ検知はルールで足りる。Datadog RUM の frustration signals は「1秒スライディングウィンドウ内に
同一要素を3回以上クリック」「静的要素へのクリック」「JSエラー直前のクリック」といった粒度で
すでに定義・実装されている。Contentsquare も rage tap / dead tap / looping / hesitation を
モバイルの摩擦シグナルとして扱っている。

→ **AIが必要なのは「何を聞くか（質問生成）」と「答えをどう構造化するか」だけ。** ここを切り分けると
SDK本体は大幅に軽くなる。

### オンデバイスAIの現実（2026年7月時点）

- 経路は Gemini Nano / AICore、アプリからは **ML Kit GenAI APIs**（Summarization, Proofreading,
  Rewriting, Image Description）。自由な対話には **Prompt API**（Alpha）が要る。
- **Nano 4 は 12GB RAM + フラッグシップSoC相当が要件**。Pixel 10系、Galaxy S26系、一部の
  Oppo/OnePlus/Xiaomi 上位機に限られる。
- → SDKとして配布するなら三段フォールバックが前提: **トリガ検知はオンデバイス完結 → 対話生成は
  Nanoがあれば端末内、無ければクラウド、それも不可なら発火しない**。
- 「ログを端末外に出さない」はプライバシー訴求として強く、クラウド前提の既存SaaS
  （Sprig, Maze, UserTesting系）に対する明確な差分になり得る。

### 既存プレイヤー

- 摩擦シグナル検知: Datadog RUM, Contentsquare, FullStory
- 詰まり検知→ポップアップ質問: すでに実在する（「同じボタンを10回押したら自動でポップアップ」）
- AIモデレートインタビュー: Maze, UXArmy, UserIntuition, Great Question ほか多数
- → **要素技術はどれも新しくない。** 新規性は組み合わせの側にある（後述）。

## 差別化の仮説

1. **オンデバイス完結によるプライバシー** — 行動ログを外に出さずにインタビューが成立する。
   規制業種（金融・医療）や、そもそもログ送信に抵抗のあるアプリに刺さる可能性。
2. **汎用loggerであること** — 既存はWeb中心／専用計測タグ前提。アプリが既に流している
   イベントログの文脈をそのままLLMに渡して質問を生成できるなら、導入コストが桁で違う。
3. **割り込み順序の設計** — 下記「最大の難所」参照。ここが本当の発明になり得る。

## 最大の難所: 割り込み

**詰まっている人に質問するのは、感情的には最悪のタイミング。**
「先に助ける → 解決した直後に聞く」という順序にできれば、(a) が (b) の入場券として機能する。
逆にここを間違えると、SDKを入れた側のブランドを毀損する。導入判断に直結するので、
製品の中核リスクであり中核バリューでもある。

## 課題・未解決

- **誤検知**: 3回失敗を「わかっていない」と断定できるか。電波が悪いだけ、意図的な連打、
  ゲーム的操作など。誤発火のコストが非対称に高い。
- **深掘り**: インタビューの本体は追い質問。1問返すだけならNanoでできるが、小型モデルで
  マルチターンの深掘りが成立するかは未検証。
- **既存手段との比較**: 「セッションリプレイ + LLM要約で十分では」という反論への答えがまだない。
  リプレイは"何が起きたか"は取れるが"なぜか"は取れない、が反論の骨子になるはず（要検証）。
- **回答率**: 端末上の割り込みに実際どれだけ答えるか。ここが低いとデータセットが成立しない。
- **検証環境**: 自前で試せるAndroidアプリのトラフィックがない。最初の検証対象をどう確保するか。

## 目指したい方向性

まだ発散フェーズ。次に効きそうな一歩の候補:

- 「先に助ける→後で聞く」の対話フローだけを、SDKなしでプロトタイプして体感を確かめる
- 誤検知の許容ラインを決める（発火閾値の設計が製品の質をほぼ決めるため）
- 「ペインの構造化データ」の出力スキーマを先に書いてみる。出力が決まると必要な入力が逆算できる
